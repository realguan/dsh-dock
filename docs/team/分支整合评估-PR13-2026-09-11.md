## 3. git 看不见的三处语义冲突（真正的风险）

### S1（高）客体 patch 写入绕过 `PatchFile`：保真与备份**双缺**

- **分支做法**：`plugins.rs` 把 patch 写入器裂成纯内核 `parse_patch_entries` / `render_patch_entries`
  （供宿主/客体共用），客体侧再经 `guest::write_home_files` 投递。
  `render_patch_entries` = **头部注释 + `serde_yaml::to_string(seq)` 整数组重序列化**。
- **分支自述**（`plugins.rs` 注释原文）：「序列化会丢其余位置注释，**已知代价**」
  ⇒ **行间注释仍会丢**，即本团队 task-26 修掉的那个 bug 在分支里仍在，只是被拆成了两半。
- **备份**：`guest.rs::write_home_files_script` 只有 `base64 -d > tmp` + `mv -f`（原子），
  **无备份**；宿主侧 `write_patch_entries` 亦无备份。
- **后果（合并后）**：三条客体写路径 `set_plugin_disabled_in_guest` /
  `copy_plugin_config`(客体) / `mcp.rs`(客体) 都会**丢行间注释且不落 `.bak`**；
  而 AGENTS §6 刚登记「**统一走 `plugins.rs::PatchFile`**」⇒ **登记当场失真**。
- **反证（好消息）**：分支**已有** `guest::backup_file`，且已在 `.credentials.yaml`
  （`credentials.rs:385`）与 `settings.yaml`（`dsh_settings.rs:59`）上用了——
  **只是没用在 `cordis.patch.yml` 上**。修复路径现成，不是从零造。

## 6. 建议的整合方案（4 步，须按序）

**第 0 步（lead 独占，单写者）**：在 `master` 上执行合并，机械解掉 6 文件 15 块；
规则 = **取我方 §7 压缩 + 接受分支退役回收 + 保留分支实质新增**，其余按"两边都要"。

**第 1 步（rust-core）— 核心设计，S1 的唯一正解**：
把 `PatchFile` 裂出**文本进出**内核，让宿主与客体**共用同一份保真语义**：

- `from_text` 提为 `pub(crate)`；新增纯函数 `render() -> Result<String, String>`；
- `write(path)` 保持不变语义 = `backup_before_overwrite(path)? + atomic_replace(render())`；
- **客体路径** = `读客体原文 → PatchFile::from_text → 变更 → render() → guest::backup_file(rel)
  → guest::write_home_files(原子)`；
- **删除**分支的 `parse_patch_entries` / `render_patch_entries` / `write_patch_entries` /
  `apply_save_mcp_server`（§6「不得再写第二份」）；
- 回归判据（**回退真实现即红**）：客体写入后，未改动条目的行间注释逐字节仍在 + 目标旁有 `.bak-<unix秒>`。

**第 2 步（docs-contract）**：§7 回收至 ≤40（S2）· §6 保真条目覆盖客体路径 · ADR-0016 入 §9 索引 ·
`docs/broadcasts.md` **倒序双落**（两轮条目都在，最新在上）· `docs/contracts/README.md` 两行合并 ·
分支 `wsl-guest-management.md` 契约纳入台账。

**第 3 步（qa-verify）**：独立验证 = 四闸门（宿主/win-gnu clippy + fmt + test）+ 前端
+ S1 保真不变量 + §4 零损失清单逐项 + AGENTS 双预算 + 分支 15 笔的测试仍在（含 `#[cfg(unix)]` 守卫）。

> **不建议** rebase 分支到我们的 master（会重写他人 15 笔并需 force-push 到他人分支）。
> **建议**把分支合并进 master：合并后其提交即从 base 可达，**PR #13 会自动标记为已合并**。
