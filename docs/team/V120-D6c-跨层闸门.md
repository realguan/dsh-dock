## 2. 闸门实现（复用既有范式，不新造机制）

**范式来源**：`updater.rs::app_update_event_name_matches_frontend_constant` 已用
`include_str!("../../frontend/src/types/events.ts")` **从 Rust 侧读前端源码**。
本闸门同法读 `frontend/src/stores/clientUpdateStore.ts` —— 于是**两侧都在同一断言内**，
任一侧改动都可判。

### 2.1 提取链（纯文本，无新依赖）

| 步骤 | 做法 |
|:---|:---|
| 取函数体 | `pub fn run_download_and_install(` → `/// 同步执行一次版本检查` 之间 |
| **抹注释** | 行注释 + 块注释 → 空格（保留换行）。**必须**：函数体注释里多处提到 `ClientUpdate::Checking` 等字样，不抹会误当发射点 |
| 取**两个分支视图** | 找 `#[cfg(target_os = "windows")]` / `#[cfg(not(…))]` 块（花括号配对），把另一支整段抹为空格 |
| 提取发射 | 扫 `set_state(` → 圆括号配对取实参 → 抓 `ClientUpdate::<变体>` |
| 判**相邻对** | 见 §2.2 |

### 2.2 「运行时相邻」的模型（三条规则，缺一会假阳/假阴）

**这是本闸门唯一需要设计的地方**——把源码里的线性出现序变成**真实运行时相继对**：

1. **`return;` 终结分支**：某次发射之后、下一次发射之前出现 `return;` ⇒ 它是**终止性备选**
   （如 `Ok(None) => UpToDate`）。它与"当前落空路径状态"**结成一对**（备选也是迁移），
   但**不更新**落空路径状态。⇒ 这既覆盖了 `Checking → UpToDate`，
   又让**跨过 return 的** `Checking → Downloading` 被覆盖（**后者正是 D6b 缺的那条边**）。
2. **兄弟分支互斥**：同一 `match` 的两个分支之间的发射**不是相继**（互斥）。
   由 `arm_blocks`（`=> {` 开的块，分配唯一 id）+ `sibling_arms`（分支栈同长、前缀同、末位异）判定。
   ⇒ 消掉 `failed → failed`（末段 `Ok(())=>Failed` 与 `Err(e)=>Failed` 两个兄弟分支）这类**假对**。
3. 其余相邻即相继。

**为何需要规则 2**（自测发现）：仅用规则 1 时，Windows 视图会多出一对
`failed → failed`；而前端表 `failed: ["checking","idle"]` **不含自环** ⇒ **假阳红**。
它**不是**真实相继（两个分支互斥，第二个不可能接在第一个之后）。

### 2.3 实际提取结果（与设计一致，逐对人工核对）

| 分支 | 提取到的相邻对 |
|:---|:---|
| **Windows**（8 对） | `checking→upToDate`、`checking→failed`、**`checking→downloading`**、`downloading→downloading`、`downloading→failed`×2、`downloading→installing`、`installing→failed` |
| **非 Windows**（6 对） | `checking→upToDate`、`checking→failed`、**`checking→downloading`**、`downloading→downloading`、`downloading→done`、`done→relaunching` |

**两分支确实不同**（Windows 有 `installing`、非 Windows 无）——由
`cross_layer_extractor_separates_the_two_branches` 钉住，**防遮蔽逻辑失效导致"只测一条路径还全绿"**
（正是 qa-verify §6.2 那类"绿得没有信息量"）。

### 2.4 相位名归一（一处曾差点写错）

提取器拿到的是 **Rust 变体名**（`Checking`），前端表用的是 **serde 相位名**（`checking`）。
首版直接比较 ⇒ 14 对全部"不被接受"（假红）。现经 `rust_phases()` 由 **serde 取生产真值**
（9 个变体 → 相位名）做归一，**不手抄**——改了 `rename_all` 闸门即随之生效。

## 3. 三条断言

| 断言 | 钉住 |
|:---|:---|
| `frontend_transitions_accept_every_emitted_pair_per_branch` | **双向闸门本体**：每个运行时相邻对都必须在前端表内有边；失败时点名「[分支] from → to」 |
| `frontend_phase_names_match_rust` | **相位名集合相等**（防键拼写错 ⇒ 事件静默丢）+ 表**值**里的相位名必须合法（防 to 侧拼写错 ⇒ 该边永不生效） |
| `cross_layer_extractor_separates_the_two_branches` | 提取器自检：两分支结果必须不同、且 `installing` 只在 Windows 侧 |

断言文案写明：**两侧须同步**（改前端表或改 Rust 发射序），并说明本闸门从 Rust 侧读前端源码。

## 6. 未决 / 风险（**闸门自身的有效边界**，如实登记）

1. **只覆盖 `run_download_and_install` 这一处发射点**。若将来**别处**（如 `run_check`）
   也发 `app:update`，本闸门不会自动纳入。**缓解**：`run_check` 的发射已由更早的
   `emitted_sequence_advances_monotonically`（手抄序列）覆盖，但那仍是手抄；
   若要彻底，应把提取器泛化为「扫全模块的 `set_state`」并同样分支化——**属独立意图**。
2. **文本级推断控制流的固有边界**：模型（§2.2）覆盖了本函数的三种形态
   （早退备选 / 兄弟分支 / 常规相继）。若将来出现**循环、`?` 早退、闭包回调里的跨帧发射**
   等结构，模型可能**漏对（假阴）或假阳**。缓解：断言 `pairs` 非空 + 两分支不同（§2.3/§3）；
   但**不声称绝对**。若发射面显著复杂化，应改为**运行期回放**（把真实事件序列喂给前端
   `applyUpdateEvent` 的等价模型）而非文本推断。
3. **前端表的两处宽松边不被本闸门约束**：本闸门只保证"Rust 实际发的对都被接受"，
   **不**保证"前端表没有多余边"。实测两表有 25 处宽严差异——那是刻意的：
   Rust `transition_allowed` 是**告警用的宽松模型**，前端表是**派发用的严格白名单**，
   二者语义不同，故**不做全表等价断言**（那会产生大量假红）。
4. **前端 seam 测试仍是手抄序列**（`clientUpdateSeam.test.ts` 的 `WINDOWS_SEQUENCE` /
   `NON_WINDOWS_SEQUENCE`）。本闸门从 Rust 侧闭合了同一缺口；两侧现在是**双保险**，
   但**前端那份手抄序列未与本闸门同源**——若前端要同样去手抄，可 `?raw` 读 `updater.rs`。
   **属 frontend 域，未动**。
