## 1. 逐条归位判定（AI 本机 / 必须真机）

| 项 | 判定 | 依据（实测） |
|:--|:--|:--|
| **taskkill 回退路径：运行时行为** | ❌ **必须 Windows 真机**，且**可达性存疑** | 本机 `command -v wine` / `taskkill` 均**不存在**；该分支为 `#[cfg(not(unix))]`，macOS 上不编译更不执行。且代码注释自述它是「Job Object **未覆盖到的极端情形**」（装配失败 + 壳横死）——**属防御性冗余** |
| **taskkill 回退路径：参数构造正确性** | ✅ **AI 本机可验（且可闸门化）** | 参数是纯数据 `["/PID", pid, "/T", "/F"]`。**实测**：同形的 `shell::windows_kill_args` 其测试 `windows_kill_args_cover_whole_tree` **未 cfg 门控**，在 macOS 上真跑 → `1 passed` |
| **WSL 客体 wrapper：脚本形态与常量一致性** | ✅ **AI 本机可验** | `guest_boot_script` 带 `#[cfg(any(windows, test))]`，**测试可在 macOS 跑**。**实测**：`guest_boot_script_parameterizes_profile_safely` → `1 passed` |
| **WSL 客体/宿主双路径：运行时收口** | ❌ **必须 Windows + WSL 真机** | 需 `wsl.exe` 与真实发行版；本机无 WSL |
| **Windows 目标的编译 + lint** | ✅ **AI 本机可跑（已存在）** | **实测**：`cargo clippy --target x86_64-pc-windows-gnu --all-targets -- -D warnings` → exit 0；且该 target 的 dep-info **确实列出** `src/lifecycle.rs`/`src/executor.rs`，证明 Windows-only 代码**真的被编译**（非静默跳过） |

> **方法论要点（复算必读）**：判定「某项本机可验吗」不能只看「函数是否在 macOS 可跑」，
> 还要看**测试是否被 `#[cfg]` 排除**。`#[cfg(any(windows, test))]` 是**本仓库的关键范式**——
> 它让 Windows 专属的逻辑（脚本文本、参数构造）**在 macOS 上也能测**。这也是 E2/E3 可闸门化的地基。

## 3. 机器闸门评估（本任务重点）

**结论：两条都能做成机器闸门，且都是「改测试不改生产行为」的低风险升级。**
判据 = 二者都是**纯数据/纯文本**，不需要 Windows 运行时。

### E2（建议）：`taskkill` 回退参数纯函数化 —— 覆盖契约 §5 行 7

- **现状缺陷（实测）**：`lifecycle.rs::reap_pid` 的 Windows 分支**内联**构造
  `vec!["/PID", pid, "/T", "/F"]`；同形构造在 `shell.rs::windows_kill_args` 有纯函数 + 测试。
  ⇒ **同一语义两处实现，只有一处被测试覆盖**——而契约 §5 行 7 点名的恰是**回退路径**。
  少一个 `/T` 即退回「只杀壳层、node 续跑」的老漏洞（`shell.rs` 注释明载该史）。
- **建议**：在 `lifecycle.rs` 内新增 `reap_args(pid) -> Vec<String>` + 跨平台 `#[test]`，
  `reap_pid` 改调它。
- **⚠️ 必须避开的陷阱**：**不得**改调 `shell::windows_kill_args`——`shell.rs` 已依赖 `lifecycle`，
  反向依赖会成**模块环**，并破坏「`lifecycle` 是零 `crate::` 依赖叶模块」这一单向性前提
  （该前提正是 spawn 闸门单向性证明的地基，task-29 §4.2 已论证）。
- **收益**：契约 §5 行 7 由「纯函数单测覆盖不到回退路径」→**本机可跑的机器闸门**；
  零生产行为风险（等价搬移）。**建议另派独立任务**（AGENTS §8.1 一次一个意图）。

### E3（建议）：客体停止位常量 ↔ wrapper 字面量 —— **新发现的静默不一致风险**

- **现状缺陷（实测）**：宿主侧用常量 `GUEST_STOP_FILE`
  （`teardown` 内 `touch {GUEST_STOP_FILE}`），而客体 `guest_boot_script` 与既有测试
  **都写死字面量** `/tmp/dsh-dock-stop`：

  ```text
  executor.rs:524  const GUEST_STOP_FILE: &str = "/tmp/dsh-dock-stop";   ← 宿主用
  executor.rs:577  guest_boot_script(...)  内含 "rm -f /tmp/dsh-dock-stop …"  ← 客体用字面量
  executor.rs:1303 assert!(plain.contains("/tmp/dsh-dock-stop"));        ← 测试也断言字面量
  ```

- **风险（为何值得闸门化）**：三者仅靠**人肉纪律**一致。改常量而不改字面量时，
  **宿主 touch 的路径与客体轮询的路径已不是同一个**，而**现有测试因为断言的也是字面量仍会绿**
  → 停止位永不生效，只剩硬杀路径兜底，且**无人发现**。这与本仓库反复踩的
  「静默不一致」同族（对照 AGENTS §7 IPC 三处同步）。
- **建议**：把该测试断言由字面量改为常量（`contains(GUEST_STOP_FILE)` / `contains(GUEST_READY_FILE)`）。
  改动**仅测试断言**，该测试本机可跑（**实测 PASS**）。
- **收益**：常量漂移**立刻红**；零生产行为风险。**建议另派**。

> **两条都属「改测试」而非「改契约」**——契约 §6 已用 §E2/§E3 指针指过去，
> 落地后请实现方同步回填 `child-lifecycle.md` §5 行 7。
