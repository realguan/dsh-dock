## 1. 缺陷链路（引 D5 §6.2，已独立核对代码）

```
关于页「检查更新」 → commands/update.rs::check_updates
  → boot::refresh_update_ui(app, state)          ← 本次修的唯一位置
      → updates::check_now(&data_dir)            ← 只探宿主（无世界参数）
      → boot::emit_update → app:update 事件
  → 前端 lib/events.ts:43 setVersions(...)       ← 覆盖关于页刚播种的世界感知结果
```

⇒ **WSL 模式下点一次「检查更新」，关于页从客体版本退回「未检出」**——把 D5 的修复
在真实使用中打回原状。

**为什么不能"在 commands/update.rs 里另写一份"**：那会造出**第二实现**（emit + 托盘刷新），
本仓库已有三次同族返工教训（task-34/36/37/40 的重复实现线）。故本任务只在 `boot.rs` 收口，
**复用 rust-mgmt 已导出的两个函数**。

新增 `boot::update_ui_tests::refresh_update_ui_routes_through_world_aware_status`，


### 2.1 为什么这条判据用**源码文本闸门**（而非行为单测）

`refresh_update_ui` 的入参是 `tauri::AppHandle`；本仓**无 Tauri 测试基建**
（AGENTS §5：不引 dev-dependency），单测环境起不出 Tauri 运行时 ⇒ 该函数**不可直接单测**。
而本缺陷是**调用点缺陷**——判据就是"那条调用长什么样"。源码文本闸门正是对症的机器闸门
（同 `lifecycle.rs::boot_sweeps_orphans_before_dispatching_executor` 与 spawn 闸门范式）。

**行为侧**由抽出纯函数后的三条用例覆盖（§3.2），两者互补：
文本闸门管"接线在不在"，行为用例管"接线对不对"。

> 闸门细节：CRLF 归一（v1.1.1 教训）+ 只取 `refresh_update_ui` **函数体**范围内的文本
> （`find("[..](")` → 首个 `\n}\n`），避免被文件里别处的 `world_aware_status` 字样误判为通过。

## 3. 修复

### 3.1 收口点（`boot.rs`）

```rust
/// 把「宿主基线状态」按当前世界择源；世界未定则诚实降级（不回落宿主）。
/// 纯函数 + 薄委托：自身不含任何探测/择源逻辑——两分支分别委托
/// updates::world_aware_status / updates::status_world_unresolved（复用，不新造第二份）。
pub(crate) fn status_for_world(
    base: crate::updates::UpdateStatus,
    world: Result<crate::mgmt::World, String>,
) -> crate::updates::UpdateStatus { … }

pub(crate) fn refresh_update_ui(app, state) {
    let base = crate::updates::check_now(&data_dir);
    let status = status_for_world(base, crate::mgmt::current_world(app));   // ← 收口
    tracing::info!(…);  // 其余逻辑（菜单/托盘/emit）一行未动
}
```

**为什么抽成 `status_for_world` 而不是直接把 `match` 内联进 `refresh_update_ui`**：
① `refresh_update_ui` 不可测，抽成收 `Result<World, String>` 的纯函数后可离线断言（§3.2）；
② 让"按世界择源"这一**决策**只有一处——关于页读取路径（`commands/update.rs`）与
本刷新路径共用同一语义，避免两处各自 `match` 而漂移。

**复用而非新造**（lead 硬要求）：两个分支分别调用 rust-mgmt 已导出的
`crate::updates::world_aware_status` 与 `crate::updates::status_world_unresolved`。
`boot.rs` 未新增任何探测、缓存、emit、托盘刷新逻辑。

### 3.2 新增用例（4 条）

| 用例 | 钉住 |
|:---|:---|
| `refresh_update_ui_routes_through_world_aware_status` | **复现锚**（红→绿）：接线必须在 |
| `status_for_world_local_is_unchanged` | **Local 行为不变**（交付项 3）：基线原样返回、不触碰客体 |
| `status_for_world_wsl_never_falls_back_to_host_data` | **Wsl 不得回落宿主**：宿主 `dsh.current`/`node` 不得留存；客体不可用须如实报错 |
| `status_for_world_unresolved_world_is_honest` | 世界未定（WSL 但发行版未记录）同样不冒充宿主（ADR-0016 口径） |

> **本机可验证性边界**：macOS 无 `wsl.exe` ⇒ `World::Wsl` 分支在本机必然走**探测失败**路径，
> 故这两条用例断言的是**诚实降级**这一半；**客体探测成功**那一半（真 `wsl.exe` 返回客体版本）
> **只能在 Windows 复验**——与 D5 报告的边界一致。

## 5. 未决 / 风险

1. **Windows 真机未验**（简报 §4 已裁定搁置）：客体**探测成功**分支（真 `wsl.exe`、
   客体 PATH 下 `which dsh`）**只能在真机复验**。本机证据止于纯逻辑分支与诚实降级路径。
2. **启动期多一次客体探测**：`refresh_update_ui` 也在**启动链**上被调用
   （`lib.rs` 启动线程）。改动后该路径会经 `world_aware_status` 触发客体探测——
   `world_aware_status` 的文档注释原本写着「本函数只在 `get_update_status` 里调用，
   启动链走 `refresh_update_ui`，两者互不重叠」，**本次改动使该注释的口径失效**。
   **风险已核**：① 调用点在**后台线程**（不阻塞 UI/启动）；② 客体探测有 **60s TTL 缓存**
   （`GUEST_PROBE_TTL`）+ `guest_versions_cached`，关于页随后读取命中缓存；
   ③ 最坏 30s 超时仅在 WSL 挂死时出现，且仍在后台。
   ⇒ 判定**可接受**；但 `updates.rs` 里那句注释现与事实不符，
   **建议 rust-mgmt 顺手校正**（属其域，我未动）。
3. **D5 §6.3/§6.4 的既有表达力缺口**（`ComponentUpdate.error` 文案把客体失败说成网络、
   `NodeRuntimeInfo` 无 error 槽）**本轮未动**——它们是契约形状问题，需走流程，非本任务。
4. **顺带记录**（不改）：§5.2 的注释-事实漂移，以及 spawn 闸门截断标记脆性
   （已在 task-42 报告 §8 登记，Lead 已认领为下一轮候选）。
