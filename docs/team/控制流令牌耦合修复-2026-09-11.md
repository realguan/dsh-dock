## 2. 解耦方案：**A**（判定改用稳定标识）

```ts
export const FACTORY_DEFAULT_PROFILE = "web"          // 稳定标识，非文案

export function resolveIsDefault(name: string, defaultProfile: string | null): boolean {
  return name === (defaultProfile ?? FACTORY_DEFAULT_PROFILE)
}
```

- 判据只来自两个**与文案无关**的来源：settings 的 `defaultProfile`（真实数据）与模块常量。
  依据 AGENTS §6 口径（`defaultProfile` **None 由消费方兜底 `web`；失效值不消费**——
  2026-09-11 措辞校正：原写「None/失效值读取侧兜底 `web`」与实现不符，详见
  `docs/team/待裁定清册-2026-09-11.md` C3）。本任务的 `resolveIsDefault` 与新口径完全一致：
  None → 命中 `web`；失效名 → 不命中任何候选（与 Rust `consume_default_profile` 同语义）。
- 抽成**导出的纯函数**：判定可被纯逻辑测试直接钉死（本仓库禁 RTL/jsdom，纯函数才能上闸门）。
- 同时**删除死字段** `displayProfiles[].tag` 与其中的 `"TEMPLATE"`/`defaultBadge`/`meta.tag`
  三元（无消费者；留着等于给「将来有人渲染它」预留再耦合的入口）。

**未选 B（提为模块级常量供比较）的理由**：若把 `"DEFAULT"` 提为常量、字典里仍留同名值供渲染，
两者只是"碰巧同值"——将来仍可能有人用常量去比对字典值（或反之）。A 让判定**根本读不到**文案，
是结构性隔离，不是命名规避。（且本文件存在稳定标识：profile 名。）

## 3. 行为差异真值表（穷举候选 × defaultProfile）

旧规则等价于 `name === defaultProfile || name === "web"`（只有 `web` 的 tag 是 `"DEFAULT"`）：

| defaultProfile | 候选 | 修复前 | 修复后 | 差异 |
| :--- | :--- | :--- | :--- | :--- |
| `null` | web / custom-a | true / false | true / false | — |
| `"web"` | web / custom-a | true / false | true / false | — |
| `"custom-a"` | web | **true** | **false** | ⚠️ 见下 ① |
| `"custom-a"` | custom-a | true | true | — |
| `"ghost-deleted"`（失效值） | web | **true** | **false** | ⚠️ 见下 ② |
| 其它组合 | — | — | — | — |

**差异总数 = 2**，均为「移除字典驱动分支」的直接后果：

- **① 双默认徽章（修复前的真 bug，本次一并修好）**：`defaultProfile = "custom-a"` 时，
  修复前 **`web` 与 `custom-a` 两张卡片同时显示「默认」**；修复后只有 `custom-a`。
  一张"默认"徽章标记两张卡片显然是错的——用户无法判断到底哪个会被启动。
- **② 失效默认值**：`defaultProfile` 指向已不存在的名字时，修复前 `web` 仍被标为默认，
  修复后**无卡片被标**。判定依据：Rust `resolve.rs::consume_default_profile` 对不在 webUi
  候选内的存储值**不消费**（"一律回退常规流程，不猜用户意图"）⇒ 此时并没有"将被启动的默认
  profile"，不标徽章是诚实呈现；AGENTS §6 亦登记「删除时引用清除、重命名时引用同步」，
  失效值属短暂状态。**如 lead 判应保留旧行为，改回 `|| name === "web"` 即可（一处）**，
  但那会连带恢复 ① 的双徽章。
