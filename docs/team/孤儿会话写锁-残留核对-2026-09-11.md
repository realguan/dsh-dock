## 一、一句话结论

原报告四建议中 **P0 / P1 / P2 已落地，且机制比原建议更强**（判据从「进程形状启发式」换成**内核登记锁**，
PID 复用免疫）；**真正未实施的是 P0′**（持锁者可诊断 + 一键处置）。
另有三条残留**不在原报告视野内**：① 无登记文件的**历史存量**孤儿永不可回收；② dev/prod 隔离存在一条
**硬旁路**（`DSH_HOME` 显式值优先，本机 agent shell 实测就继承着 `DSH_HOME=~/.dsh`，从该 shell 起 dev 仍共用正式 home）；
③ 孙进程缺口与 Windows Job Object 真机未验证（ADR-0015 §5 已自认，非新发现）。

| 原建议 | 判定 | 一句话依据 |
|:---|:---|:---|
| **P0** 启动期孤儿回收 | ✅ **已闭环**（判据换强） | `lifecycle.rs:737 sweep_orphans` + `lib.rs:274` 引导接线 + `lifecycle.rs:1718` 接线闸门；判据 = 内核登记锁，非「引擎路径 + `PPID==1`」 |
| **P0′** 持锁者可诊断 + 一键处置 | ❌ **未实施** | 全仓对 dsh 会话租约**零代码引用**（唯一提及是 `lifecycle.rs:23` 的禁止性注释）；`SessionItem`（`sessions.rs:26`）无持有者字段 |
| **P1** dev/prod 会话隔离 | ⚠️ **已闭环，但有一条硬旁路** | `resolve.rs:127` `dev_home_dir_name()`（dev → `~/.dsh-dock-dev`）+ `resolve.rs:100` 测试硬隔离；但 `resolve.rs:92` 的 `DSH_HOME` 显式值仍**最高优先** |
| **P2** 父死守卫 | ✅ **已实施**（否决了原报告的形态） | 生命线 watcher（unix，`lifecycle.rs:618`）+ Job Object（Windows，`lifecycle.rs:223`）+ 登记锁清扫；原报告推荐的 `NODE_OPTIONS=--require <guard>` 被 **ADR-0015 §3 方案 C 显式否决**（注入整棵 node 树，爆炸半径不可接受） |

## 二、逐条核对（含证据）

### P0 启动期孤儿回收 —— ✅ 已闭环

| 环节 | 现状 | 证据 |
|:---|:---|:---|
| 清扫实现 | 扫 `<app_data>/procs/*.lock`：**加得上锁 = 持有者已死（陈旧文件，删）**；**加不上锁 = 真孤儿（`SIGTERM` → 3s → `SIGKILL`）** | `src-tauri/src/lifecycle.rs:737-835` |
| 判定安全方向 | 三态：`Ok` = 陈旧 / `WouldBlock` = 收口 / `Error(io)` = **不可判定 → 跳过，绝不按 pid 杀** | `lifecycle.rs:719-725`（审核修正，契约 §2.3） |
| 引导接线 + 顺序 | 在 `executor_for_mode`（→ probe → 建会话）**之前**调用，且装配在任何 spawn 之前 | `src-tauri/src/lib.rs:274`（清扫）、`lib.rs:174`（`lifecycle::init`）、`lib.rs:294`（派发点） |
| 机器闸门 | 源码文本闸门钉死「接线存在 + 顺序正确」，删掉即红 | `lifecycle.rs:1718-1730` |
| 实测（本机） | 登记表实际工作：`procs/10122-9-….lock` = `{"argv0":"dsh","pid":10189,"profile":"web","role":"dsh-server","startedAtMs":…}` | `~/Library/Application Support/io.github.realguan.dsh-dock/procs/` |

**与原建议的差异（不是缺陷，是判据升级）**：原报告建议「引擎路径属于本数据目录 + `PPID==1`」；
实现改用**内核登记锁**——`PPID==1` 是「父已死」的**事后**信号，而登记锁是「子进程是否还活着」的**直接**判据，
且对 PID 复用免疫（契约 §2.1）。代价见下方 R1。

**残留**：见 R1（历史存量）、R2（跨实例不互扫）。

### P0′ 持锁者可诊断 + 一键处置 —— ❌ 未实施

- **零实现证据**：`src-tauri/src` 内对 `session.lock` 的**代码级引用为零**——唯一命中是
  `lifecycle.rs:23` 的边界注释（明令本模块绝不触碰该锁），其余全部命中都是 Rust 自己的
  `state.session.lock()`（同名 Mutex，巧合）。
- **UI 侧同样没有**：`SessionItem`（`sessions.rs:26`）有 `active` / `health_detail` / `end_state`，
  **没有**「被 PID X 占用」类字段；`frontend/src/content/zh-CN.ts` 无占用/持锁相关文案。
- **后果仍与原报告一致**：会话点不开时，用户拿到的仍是 dsh 引擎侧的英文
  `SessionAlreadyOwnedError … (gateway/internal)`，壳完全不知情、无自助出口，
  仍会诱导用户使用**有损**的「删会话」（那只是 `remove_dir_all` 顺手 unlink 了锁文件，
  对活跃会话删锁 = **丧失互斥 = 日志撕裂**，ADR-0015 §3 方案 D 否决原文）。
- **实现纪律（必须写进方案）**：P0′ 只允许「**只读探测 + 杀持有者进程**」，
  **严禁**删除/改写/主动解锁 `session.lock`（同上，方案 D）。
- **跨平台差异（容易被漏掉）**：Windows 侧 dsh 用具名内核信号量，**没有锁文件**（台账复现点 14，
  `docs/contracts/dsh-behavior-ledger.md:29`）→ flock 式探测在 Windows 上**不成立**，
  该平台只能退化为「进程/登记表诊断」，或在 UI 明说不可诊断。

### P1 dev/prod 会话隔离 —— ⚠️ 已闭环，但有一条硬旁路

- **已落地**：`resolve.rs:127-133` `dev_home_dir_name()` 以 `cfg!(debug_assertions)` 分流
  （dev → `.dsh-dock-dev`，release → `.dsh`）；`user_dsh_home()`（`resolve.rs:85-97`）解析链 =
  `DSH_HOME` → 用户 home + dev 目录名 → 兜底。
- **超出原建议的第二层隔离**：`resolve.rs:87-90` 测试构建**一律无视 `DSH_HOME`**，锁进
  `~/.dsh-dock-test`（`resolve.rs:100`）。这是审核期另一起事故（`cargo test` 起真 dsh 打开用户真实 profile，
  把正式包会话顶到超时）的修复，commit `fd227cf`。本机 `~/.dsh-dock-test` 于 2026-09-11 10:13 生成，**已生效**。
- **硬旁路（本档新发现）**：`resolve.rs:92` 的 `DSH_HOME` 显式值优先级最高（注释 §74 称"用户主权"），
  而**从 dsh 会话内启动的东西天然带 `DSH_HOME`**。本机实测（2026-09-11）：
  ```
  DSH Dock.app (pid 10122, 无 DSH_HOME)
    └─ dsh (pid 10189, 引擎档, 设 DSH_HOME=~/.dsh)
         └─ agent/bash 会话 (DSH_HOME=/Users/guan/.dsh  ← 继承)
  ```
  ⇒ 从这个 shell 里 `cargo tauri dev`，dev 仍然写**正式 home**，原事故的"放大器"重新接通。
  这也解释了为什么本机 `~/.dsh-dock-dev` **至今不存在**（隔离已落地，但从未被 dev 运行实证过）。
  → 方案见 R3。

### R1 —— 历史存量孤儿（建议：不写码，只留人工通道）

- **事实**：清扫判据是登记锁，而 ADR-0015 之前的孤儿（如原报告那 11 个）**没有登记文件**，
  因此**永远不会被自动回收**；只有人工 `SIGTERM`（原报告 §五的做法）能清。
- **为什么不补启发式清扫**：ADR-0015 的设计取向是"**不确定时宁可不收口**"（契约 §2.3：
  误杀无法挽回，漏收还有下次启动兜底）。`PPID==1 + 引擎路径` 是启发式，杀的是**任意 pid**，
  一旦路径/形态漂移（不同 tier、改名、WSL、用户自装的 dsh）就可能误杀无关进程——
  正是 ADR-0015 反复强调要避免的方向。
- **最小方案**：零代码。§四的复查命令①保持随时可跑；本档即人工通道的落点。
  若日后确认要自动化，只允许**只读计数留痕**（扫到 `PPID==1` 的引擎 dsh 就 `warn` **不杀**），
  这属独立意图，需另开任务。

### R2 —— 跨实例不互扫（建议：保持现状，文档写明）

- **事实**：`sweep_orphans(&boot_data)` 只作用于**本实例数据目录**的登记表
  （`lib.rs:274` 传的是 `app.path().app_data_dir()`）。dev 与 prod 各有自己的 `procs/`。
- **影响**：若 dev 孤儿锁死了 prod 会话（= 原事故的原始形态），只有 **dev 侧下次启动**才会回收它。
  P1 隔离落地后，这种跨域伤害只在 R3 的旁路下才可能发生。
- **建议**：不改行为（跨实例互扫需要"枚举所有实例数据目录"这一新产品概念，且与单实例锁语义冲突）；
  在契约 §2 或本档口径里写明「清扫作用域 = 本实例数据目录，跨实例伤害由 P1 隔离消除」。

### R3 —— P1 硬旁路的可观测化（推荐档 A）

- **改动**（档 A，最小）：
  - `src-tauri/src/resolve.rs`：新增**纯函数**，例如
    `pub fn dev_home_bypasses_isolation(dev: bool, resolved: &Path, release_home: &Path) -> bool`
    ——判据 = `dev && resolved == release_home`；
  - 调用点：`lib.rs` setup（`lifecycle::init` 附近，`lib.rs:174`）或 `boot.rs` 日志初始化处，
    命中即 `tracing::warn!`（结构化字段：`resolved_home` / `reason = "DSH_HOME 显式值"`）。
- **测试**（AGENTS §5）：纯函数正反例各一 + fixture 内联（真假 dev、相同/不同路径、`DSH_HOME` 未设的兜底分支）；
  零新依赖。**不改行为**，因此不触碰「用户主权最高优先」这一 `resolve.rs:74` 既有裁定。
- **档 B（不推荐本轮做）**：dev 构建**拒绝**解析到正式 home 的 `DSH_HOME`（或在 UI 提示后回退）。
  这会改 `resolve.rs:74` 已声明的优先级口径 → 需维护者裁定，并同步契约/注释；本档只登记为待议。
- **契约/IPC**：不涉及。**无需 ADR**（档 A 只加日志）。

### R4 —— P0′ 三档方案（会话占用可诊断 / 一键处置）

**共同纪律**：探测**只读**（`File::open` 只读句柄 + `try_lock`，或 unix `flock(LOCK_EX|LOCK_NB)`），
**绝不 open 写、绝不删除、绝不主动 unlock** `session.lock`（ADR-0015 §3 方案 D）。
本机实测确认：**只读句柄足以探测**（`flock` on `O_RDONLY` fd 对已持有文件返回 `EWOULDBLOCK`，errno 35），
故探测串不得出现 `O_RDWR`。判定沿用既有三态纪律 `classify_lock_result`（`lifecycle.rs:719`）：
`Ok` = 空闲 / `WouldBlock` = 被持有 / `Error` = **不可判定 → 显示"未知"，绝不引导处置**。

| 档 | 内容 | 落点 | 契约/IPC 影响 |
|:--|:---|:---|:---|
| **档 1**（最小，零新命令） | 在**已登记**的诊断命令里加一个只读聚合字段：`sessionLockHolders: Vec<{sessionId, pid, alive}>`（unix 才填；Windows 空 + 明确 `unsupported`） | `src-tauri/src/diagnostics.rs`（rust-mgmt）；命令 `get_system_diagnostics` **已登记**（AGENTS §7） | 字段增 = 形状契约变更 → **必须同步** `frontend/src/types/ipc-shapes.json`（该结构已在 `DshDiagnosticInfo` 条目内）+ TS 接口；Rust 侧闸门 `ipc.rs:335-373`、TS 侧 `frontend/src/__tests__/ipcShapes.test.ts:7` |
| **档 2**（会话页直显） | `SessionItem` 增 `lockHolder: Option<u32>`，会话维护页显示「被 PID X 占用」 | `src-tauri/src/sessions.rs:26`（rust-mgmt）+ 前端会话列表 | 同上：`ipc-shapes.json` 的 `SessionItem` 键集（`frontend/src/types/ipc-shapes.json:90`）Rust/TS 双侧同闸，漏一处测试红 |
| **档 3**（一键处置） | 新增 IPC `release_session_lock_holder`：**只对持有者 pid 做 `SIGTERM` → grace → `SIGKILL`**（复用 `lifecycle` 的收口语义；**绝不碰锁文件**） | IPC 三件套（`ipc.rs` COMMANDS / `lib.rs` handler / `capabilities/default.json`）**由 rust-core 统一落**，实现体在 rust-mgmt | 新增命令 = 三处同步（AGENTS §7）；前端 `lib/tauri.ts` 加 api 方法 + 按钮，Promise 必须 `.catch` |

**建议顺序**：档 1 先行（一次意图、可独立验证），档 2 / 档 3 视需要另开任务。
**Windows 例外**：该平台无锁文件（具名内核信号量），档 1/2/3 均需显式降级（返回 `unsupported` 而非假"空闲"）。

### R5 —— 孙进程缺口（维持 ADR-0015 口径）

ADR-0015 §5「孙进程缺口（诚实登记）」：`run_dsh_forward` → dsh → pnpm 的孙进程不在守卫内。
该 ADR 已裁定「需实施期实测确认 `dsh plugin install` 不会拉起用户长驻任务后才可放宽」，
且契约 §7 明写「**收窄容易、放宽难**：任何把作用域从『壳生的 pid』放宽到『进程组/整树』的改动，

## 四、原报告 §六 复查命令修正

> 原报告 §六 是"随时可复跑"的现场工具，其中的进程匹配串与路径**已随 ADR-0015 / dev 隔离漂移**。
> 下面每条给「判定 + 修正版」，修正版均已在本机实跑验证（输出见 §五）。

### ① 列逃逸进程 —— 判定：**仍可用，但失败方向不安全（会假空）**

原：`ps -Ao pid,ppid,command | awk '$2==1 && /dsh-dock[^ ]*\/engines\/bin\/node/ && /@deepseek-ai\/dsh\/lib\/bin\.js/ {print $1, $2}'`

- 缺陷 1（**必改**）：未加 `-ww`，macOS 的 `command` 列在**终端下会按宽度截断**——长路径被截掉后
  正则失配，输出**空**，看起来像"无孤儿"。**"报无孤儿而实际有"正是最危险的失败方向**。
- 缺陷 2：只锚 `engines/bin/node` 形态。实测本机 dsh 确实是
  `…/engines/bin/node …/global/…/@deepseek-ai/dsh/lib/bin.js …`（能匹配），
  但这是启动器 shim 的实现细节，不是契约；改按「引擎路径 + `@deepseek-ai/dsh`」双锚更稳。
- 缺陷 3：PPID 列取 `$2` 依赖 `ps` 字段顺序，加 `=` 结尾（`pid=,ppid=,command=`）可免表头干扰。

修正版：

```bash
# ① 列逃逸进程（PPID=1 且是本壳引擎起的 dsh；-ww 防截断）——空输出 = 无孤儿
ps -ww -Ao pid=,ppid=,command= | awk '$2==1 && /engines\// && /@deepseek-ai\/dsh\// {print "ORPHAN", $1}'

# ①b 全量对照（不限 PPID）：应能看到"壳活着 + 其 dsh + 其 watcher"三件套
ps -ww -Ao pid=,ppid=,command= | awk '/engines\// && /@deepseek-ai\/dsh\/lib\/bin\.js/ {print $1, $2, ($2==1 ? "ORPHAN" : "ok")}'
```

### ② 谁在持锁 —— 判定：**仍可用，但只答"谁持有"不答"是否孤儿"**

原：`lsof -c node 2>/dev/null | grep session.lock`

- 缺陷：`-c node` 只匹配进程名以 `node` 开头者（本机形态够用）；**无法区分孤儿与活壳持有者**，
  而"是否孤儿"才是决策依据（活壳持有 = 正常，孤儿持有 = 事故）。
- 修正版（把 lsof 与 `ps` 的 PPID 关联，直接给出处置依据）：

```bash
# ② 锁持有者 + 其 PPID（PPID=1 = 孤儿持有，才是事故）
python3 - <<'PY'
import subprocess
out = subprocess.run(["lsof", "-c", "node"], capture_output=True, text=True).stdout
holders = {}
for line in out.splitlines():
    if "session.lock" in line:
        f = line.split()
        holders[f[1]] = holders.get(f[1], 0) + 1
for pid, n in sorted(holders.items(), key=lambda kv: -kv[1]):
    ps = subprocess.run(["ps", "-ww", "-o", "ppid=", "-p", pid],
                        capture_output=True, text=True).stdout.strip()
    tag = "ORPHAN(父已死)" if ps == "1" else f"ok(父 {ps} 存活)"
    print(f"pid={pid} 持锁 {n} 把 PPID={ps} {tag}")
PY
```

### ③ 逐会话探锁 —— 判定：**已失效两点，必改**

原：

```python
import fcntl, os, glob
for d in sorted(glob.glob(os.path.expanduser("~/.dsh/sessions/*/*/session.lock"))):
    fd = os.open(d, os.O_RDWR)
    try:
        fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB); fcntl.flock(fd, fcntl.LOCK_UN)
    except OSError:
        print("LOCKED", d)
    os.close(fd)
```

- 失效 1（**路径**）：只扫 `~/.dsh`。dev 隔离后 dev 的会话在 `~/.dsh-dock-dev`（本机该目录尚不存在，
  脚本必须容忍）；测试会话在 `~/.dsh-dock-test`。→ 三个 home 都要扫。
- 失效 2（**打开模式**）：`os.O_RDWR`——探测只需只读；且对**只读文件**会打不开而**在 try 之外抛异常中断**。
  本机实测 `O_RDONLY` 足以判定（见 §五），改用只读更符合"绝不写 dsh 协议文件"的边界纪律。
- 失效 3（健壮性）：`open` 失败会直接崩（不在 try 内），应记 `SKIP` 而不是中断或误报 `LOCKED`。

修正版：

```bash
# ③ 逐会话探锁（三个 home 全覆盖；只读打开；open 失败记 SKIP 不误报）
python3 - <<'PY'
import fcntl, os, glob
for home in ("~/.dsh", "~/.dsh-dock-dev", "~/.dsh-dock-test"):
    files = sorted(glob.glob(os.path.expanduser(home) + "/sessions/*/*/session.lock"))
    locked = skip = 0
    for f in files:
        try:
            fd = os.open(f, os.O_RDONLY)          # 只读：绝不写 dsh 协议文件
        except OSError as e:
            skip += 1; print("SKIP", f, e); continue
        try:
            fcntl.flock(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)
            fcntl.flock(fd, fcntl.LOCK_UN)        # 空闲：立刻还回去
        except OSError:
            locked += 1; print("LOCKED", f.replace(os.path.expanduser("~"), "~"))
        finally:
            os.close(fd)
    print(f"[{home}] 共 {len(files)} 把，被占用 {locked}，跳过 {skip}")
PY
```

> 注：`LOCKED` 只表示「有活进程持有」。**是否事故要再用 ② 看持有者 PPID**——PPID=1 才是孤儿。
