## 2. 方案选择：**C（A + B）**

| 方案 | 内容 | 结论 |
| :--- | :--- | :--- |
| A | 各窗口挂载时各自 `initFromSettings()` | 必要（首帧就要正确），但**只解决冷启动**：用户在某窗口改语言后，已开着的其它窗口不会跟 |
| B | 扩展 `app:settings-changed` 载荷带 locale | **载荷已天然满足**：emit 点 `commands/console.rs::set_shell_settings` 广播的就是 `ShellSettings` **全量**（含 `locale`）⇒ **零 Rust 改动、零 IPC 新增**；但单用 B 首帧仍错 |
| **C** | **A + B** | **采用**。A 保证首帧与冷启动正确；B 保证运行期跨窗即时同步 |

**红线 3 守法的具体体现**（AGENTS §4.4）：语言状态**不跨窗共享**——每个窗口各自持有一份
Zustand store，只通过 `app:settings-changed` 事件广播收数据；`App.tsx` 内没有任何
`window.*` 全局桥或共享单例（门禁有反向断言 `not.toContain("window.__DSH_I18N__")`）。
事件授权面实测覆盖三窗口：`capabilities/default.json` `windows: ["main","about","profiles"]`。

**为什么 `initFromSettings()` 收敛到 `App.tsx` 而不是各页各写一份**：三窗口入口是同一处
（`App.tsx` 的 label 路由），集中一处即可覆盖全部窗口且不可能漏；同时删掉
`ProfileManager.tsx` 的重复调用（修复前 profiles 窗口会读两次设置：App 一次 + 自己一次）。

## 3. 首帧评估（任务要点 3，**明确回答**）

**结论：闪烁问题真实存在，已在本次修复中一并消除——采用「阻塞首帧」，成本近零。**

**首帧必错（不是「可能有」，是必然）**：`resolveSystemLocaleFrom()` 对非 `zh` 一律返回
`en-US`；而 `useI18nStore` 初始 `t: zhCN`（硬编码），`initFromSettings()` 是**异步 IPC**。
于是「系统语言 = en-US 且 settings 未设 locale」的用户，在 IPC 返回前 store 恒为 `zhCN`
⇒ **首帧必然用中文渲染**，解析完成后才整体切英文。（与 qa-verify 的独立结论一致。）

- **修复前**：`useI18nStore` 初始字典硬编码 `t: zhCN`；`App` 先渲染页面，语言初始化在
  后续 effect 中完成 ⇒ en 用户必然先看到一帧（或数帧）中文再整体切英文。
- **消除手段**：`App.tsx` 已在 `label === null` 时渲染**既有轻量骨架**（Emblem + PulseBar，
  非新 UI）。本次把门闸改为 `if (label === null || !localeReady)`（`:117`）——
  语言未解析前不渲染任何页面，因此**不存在「用错语言渲染一帧」的可能**。
  代价 = 首屏多等一次本地 IPC 读设置（`get_shell_settings` → `settings::load` 是本地文件读，毫秒级）。
- **不选「`initialLocale` 预置」的理由**：那需要把语言在**文档加载前**注入
  （`initialization_script` / 构建期注入），会引入新的注入面与契约，而收益仅是省掉
  一次几毫秒的本地读；与「壳保持薄」不符。
- **兜底（必须有）**：`Promise.race` + `LOCALE_INIT_TIMEOUT_MS = 1500`（`:41`）——
  万一 IPC 挂起，门闸按时放行并按当前字典渲染，随后到达的解析结果仍会驱动一次重渲染；
  超时经 `lib/logger.ts` 记 warn（未用 console.*）。**不存在「永久停在骨架屏」的死锁路径**。
- **交接幕布（ADR-0014）不受损**：幕布由 `BootIndex` 挂载后的
  `__dshDockCurtain?.hide?.()` 撤下，门闸只把该时机推后几毫秒；幕布自带 12s 硬上限，
  且其设计目的正是「盖住新文档首帧之前的空档」，延后撤幕是安全方向。
