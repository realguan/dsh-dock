## 1. 机制证据：该 link 确实是符号链接（本机实证）

### 1.1 既有 engines 布局（本机真实数据）

```
engines/global/v11/4daac8d21495ae25ce2a440f439031ec8bd56f6a56dd5c8d07881223417c7547
    -> cfb2-18d426bbc0aba9e8-0          # ← lrwxr-xr-x 符号链接（23 字节指向）
engines/global/v11/cfb2-18d426bbc0aba9e8-0/   # ← 真实安装目录（node_modules/…）
```

即 pnpm 用「global package hash link」把**同一份全局安装**复用给不同 `PNPM_HOME`。
macOS 无感；Windows 建目录符号链接需 `SeCreateSymbolicLinkPrivilege`，普通账户没有 ⇒
`os error 5 / 拒绝访问`——与截图① 完全吻合。

### 1.2 **零网络复现台**（本次新建立，值得保留）

不必联网、不必装真 dsh：一个含 `bin` 的**本地包**用 `file:` 依赖即可触发**同一条** hash link。

```bash
# 建一个 dummy 包（含 bin），然后：
PNPM_HOME=/tmp/probe PATH=/tmp/probe/bin:$PATH \
  <内置 pnpm> add -g "file:/tmp/probe/dummy-pkg"
# ⇒ /tmp/probe/global/v11/<64hex> -> <short>-<ts>-0   （符号链接，与生产同形）
```

实测（内置 pnpm **12.3.1**，`src-tauri/resources/pnpm/darwin-arm64.tgz`）：
每个用例都是全新 `PNPM_HOME`，`global` 下恒有 **1 个符号链接** + 1 个真实目录，另有
`node_modules/<pkg>` 内部链接。**⇒ 复现不依赖网络，后续任何人可秒级重跑。**

### 1.3 归因：这是 pnpm **12** 的行为变化

- 上游 [PR #10912](https://github.com/pnpm/pnpm/pull/10912)：**"Global installs (`pnpm add -g pkg`)
  and `pnx` now use the global virtual store by default"** ⇒ v12 起全局安装默认走全局虚拟存储。
- 上游 [issue #13694](https://github.com/pnpm/pnpm/issues/13694)：**"[pnpm v12] Bug: Failed to
  create symlink (os error 1314) & Access is denied. (os error 5)"** ⇒ 与我们的现象同类，
  **是上游缺陷，不是我们配置写错**。
- 内置 pnpm 二进制内含 `enableGlobalVirtualStore` / `GLOBAL_VIRTUAL_STORE_DIR` /
  `ENABLE_GLOBAL_VIRTUAL_STORE` 等键名（`strings` 挖掘，见 §2），说明作者知道该开关存在。

## 2. 配置级解法的穷举尝试（**结论：本机未见可行解**）

### 2.1 候选键与结果

| 路线 | 写法 | 结果 |
|:---|:---|:---|
| env | `PNPM_CONFIG_ENABLE_GLOBAL_VIRTUAL_STORE=false` | ❌ 符号链接仍在 |
| env | `NPM_CONFIG_ENABLE_GLOBAL_VIRTUAL_STORE=false` | ❌ 仍在 |
| workspace | `enableGlobalVirtualStore: false` | ❌ 仍在 |
| workspace | `enable-global-virtual-store: false` | ❌ 仍在 |
| workspace | `virtualStoreOnlyBinaryResolution: true` | ❌ 仍在 |
| CLI | `--config.enableGlobalVirtualStore=false` | ❌ 仍在 |
| 参照 | `globalVirtualStoreDir: /tmp/x` | ✅ **被采纳**（目录确被创建）——但**不消除** `PNPM_HOME/global` 的那个链接 |

### 2.2 **阴性结果的可信度自证**（关键：先证管道通，再报"无效"）

报"某配置无效"之前必须先证**配置真的被读到了**，否则阴性结果毫无意义。两道自证：

1. **workspace 路线**：写入非法值 `nodeLinker: nonsense-value` ⇒ pnpm **硬报错**并指名文件：
   ```
   Error:   × load configuration
     workspace.yaml: error: line 1 column 13: unknown variant `nonsense-value`
     | nodeLinker: nonsense-value
   ```
   ⇒ `pnpm-workspace.yaml` **确实被读取**（这正是我们 `ensure_engine_linker` 写的那个文件）。
2. **env 路线**：`PNPM_CONFIG_GLOBAL_VIRTUAL_STORE_DIR=/tmp/x` ⇒ **目录确被创建**
   ⇒ `PNPM_CONFIG_*` env 注入**确实生效**。

两条自证都成立，故"`ENABLE_GLOBAL_VIRTUAL_STORE=false` 无效"是**可信的阴性结论**，
不是管道没接上。（对比：task-30/37 的教训——没有自证的阴性/阳性结果都不可信。）

> 诚实边界：`enableGlobalVirtualStore` 是否在**更晚的 pnpm 版本**上恢复生效、或是否只在
> 某些子命令路径上生效，**本机无法判定**——需真机 + 联网环境验证。

## 3. 已落地修复 ①：错误分类拆开（复现先行 → 绿）

### 3.1 复现先行：**哪条断言红**

新增 `boot_failure::tests::privilege_failure_is_not_classified_as_network`，
修复前 **红**：

```
test boot_failure::tests::privilege_failure_is_not_classified_as_network ... FAILED
thread '...' panicked at src/boot_failure.rs:194:13:
特权类失败被误判成网络不可用（用户会拿到『检查网络后重试』这种与真因无关的建议）：
dsh 引导安装失败（registry 均不可达）：npmmirror: tls handshake eof；npmjs.org:
link the global package install directory at C:\...\v11\db8a\2082 -> 拒绝访问。(os error 5)
```

**根因链（两处叠加）**：
1. `engines::install_dsh_global` 把两条 registry 的失败**合并成一句**
   「dsh 引导安装失败（**registry 均不可达**）：……」——文案里带 `registry`；
2. `BootFailure::from_legacy_detail` 的网络分支匹配 `registry` ⇒ 判为 `NetworkUnavailable`
   ⇒ 错误卡给「检查网络后重试」。**用户按建议重试必然再失败**（真因是权限）。

### 3.2 修复内容

| 文件 | 改动 |
|:---|:---|
| `boot_failure.rs` | 新增变体 `SymlinkPrivilegeRequired`；新增**判据函数** `is_symlink_privilege_detail`（`pub(crate)`，两侧共用）；`from_legacy_detail` **把特权判定放在网络判定之前**（顺序即语义，已注释+用例钉住）；新增稳定标记常量 `SYMLINK_PRIVILEGE_MARKER = "[symlink-privilege]"` |
| `engines.rs` | 新增 `InstallFailureKind` + 纯函数 `classify_install_failure` / `install_failure_message`；`install_dsh_global` 的成功聚合改为按类出文案（特权优先）；**逐条明细不吞** |

**为什么用"稳定标记 + 共享函数"而不是各自匹配自然语言**：ADR-0012 的教训是
**措辞即契约**——上游改一句文案分类就静默落兜底。两侧共用**同一个常量与同一个判据函数**
（task-40 的教训：重复实现必然只改一处），改这里 = 两边同时改。

**判定顺序**（本次缺陷的直接成因，已写成用例 `privilege_check_precedes_network_check`）：
引导失败的聚合文案里**同时**含 `registry` 与 `os error 5`；先判网络就会把特权类吸走。

## 4. 已落地修复 ②：错误卡可行动出路（Rust 侧）

`SymlinkPrivilegeRequired` 的文案（`boot_failure.rs`）：

- **标题**：`系统权限不足：无法创建符号链接`
- **建议**：`这不是网络问题：引擎需要创建符号链接，而当前 Windows 账户没有该权限。
  最省事的办法是改用「WSL」运行环境（在启动页选择，或在控制中心设为默认）——已装好的
  WSL 发行版不需要该权限。若必须用本地模式：以管理员身份运行本应用，或在「设置 → 系统 →
  开发者选项」开启开发者模式后重试。`
- **actions**：`["boot_in_wsl", "retry"]`（出路优先；`retry` 保留，用户照做后仍要重试）
- **kind**：`symlink_privilege_required`（序列化，供前端取本地化文案）

设计要点：**先否定错误方向**（"这不是网络问题"）——用户的自然排查方向是网络，但真因是权限；
不点破就会继续白费时间。

## 8. 中途的 gate 4 红：归因 + 顺带发现（**不属本任务范围，未改**）

> **最终状态**：该红**已解除**（现 381 passed / 0 failed）。本节保留，因为它暴露的**闸门脆弱性依然存在**，
> 且这是 task-36/37/39 那条「截断标记脆弱」线的**第四次显形**。

**当时的现象**：
```
test lifecycle::tests::production_spawns_go_through_lifecycle_seam ... FAILED
panicked at src/lifecycle.rs:1898:9:
以下生产代码绕过了 lifecycle 守卫 seam…：src/updates.rs:1563: .output()
test result: FAILED. 380 passed; 1 failed; 3 ignored
```

**归因（三步前提核对，非推测）**：

1. **不是我改的文件**：我的 diff 只有 `engines.rs` / `boot_failure.rs`；
   违规点在 `src/updates.rs`（**D5 的 rust-mgmt 正在改**）。
2. **不是我的改动引起的**：违规行是新加的**测试夹具**——
   `src/updates.rs:1227` `#[cfg(test)]` → `:1228 mod world_probe_tests {` → 该 `bash .output()`。
3. **是闸门自身的既存脆弱**（在我域内的 `lifecycle.rs`，记为顺带发现）：
   闸门截断标记是**字面** `"\n#[cfg(test)]\nmod tests"`，而 `updates.rs` 的测试模块名叫
   `mod packument_tests` / `mod world_probe_tests` ⇒ **标记匹配不到**
   （实测：HEAD 版与当时工作树版 `marker 出现次数 = 0`）⇒ **整个文件被当生产段扫描**。
   在 HEAD 上它是**潜伏**的（该文件当时没有裸 spawn，所以绿）；新测试一加就暴露。

**D5 作者的实际解除方式**：在该行前加**行内豁免标注**
（`// spawn-gate: exempt(测试专用…本模块名非 mod tests，截断标记覆盖不到它…2026-09-11)`）。
这是当前设计下**唯一可用**的机制——**恰说明根本问题是截断判据本身**。

**性质**：这是**误报**（false positive，可见红），不是漏防——但后果是
"任何在 `updates.rs` 里写 spawn 的测试都会红"，会诱导他人削弱闸门（用豁免标注绕过）。

**修法建议（属 `lifecycle.rs`，不在 task-42 writeScope，故未动手）**：把截断判据从
"匹配一个固定模块名"改成**"第一个顶层 `#[cfg(test)]` 条目"**，或直接复用
`network_gate.rs` 已成熟的**条目级** `cfg_test_ranges`（它天然支持任意模块名）。
**建议独立立项**（与本轮的 D1/D6 无耦合）。
