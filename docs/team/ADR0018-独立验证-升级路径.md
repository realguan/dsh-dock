## 3. T4 是否真走用户路径 → ✅ **是，且前置断言齐备**

**（a）走的是用户快速路径，不是 bootstrap**：T4 调 `crate::resolve::resolve_launch_engine_ready(…)`，而生产侧的调用链正是：

```text
executor.rs:248  probe_engine_if_ready(&self.data_dir, &self.path_env)     ← 就绪判定
executor.rs:255  tracing::info!("引擎环境已完整就绪，跳过环境检测与准备引擎步骤…")
executor.rs:256  resolve_launch_engine_ready(&self.data_dir, …, status.dsh.as_deref())
```
⇒ **就是你机器上「已就绪（升级用户）」走的那条**，全程不经 `bootstrap()` ✅

**（b）就绪前置断言存在**（避免「未就绪态下通过」）：

```rust
assert!(
    crate::engines::probe_engine_if_ready(&data_dir, "").is_some(),
    "夹具前提：引擎应判就绪（否则真实链不会走 ready 路径）；status={:?}", …
);
```
✅ 且失败时会打印 `probe_engine` 全文，可诊断。

**（c）夹具确实构造了「旧形态」**：起始 shim 写入 `# legacy v1.2.2 launcher (direct entry, no bootstrap)`，T4 先断言该前提（`stale.contains("legacy v1.2.2")`）再验证刷新 ✅

## 8. 对 rust-core 自报「与 T1 的张力」的裁定 → ✅ **处置成立，且比他的表述更强**

他的说法：「按『删 ④′』执行，T1（跑引导路径断言）被 T4 取代；T1 说的『指向 bootstrap』是 **Windows 专属**形态，本机断言的是**平台当前形态**。」

**我独立核对后的结论：处置成立**，但「被取代」这个措辞**低估了现状**——T1 的意图**并未消失，而是被保留**：

| 关注点 | 现状 | 证据 |
| :--- | :--- | :--- |
| **Windows 形态**（shim 指向 bootstrap、不得直连入口） | **仍在，且被强化** | `windows_shim_points_at_bootstrap_not_entry` 存在并断言：含 `dsh-boot.mjs`、**不含** `lib\bin.js`、保留 `%~dp0node.exe` 与 `%*`；另有 `windows_shim_shape_is_exact` 把目标名**绑定常量** `format!("\"%~dp0{DSH_BOOTSTRAP_NAME}\"")` |
| **本机（macOS）平台形态** | 由 T4 以**平台条件期望**断言 | `expected_shim_content()`：`cfg!(windows)` → `dsh_shim_windows()`，否则 → `dsh_shim_posix(node, entry)` ⇒ 断言「**当前平台的正确形态**」而非硬编码「指向 bootstrap」 |
| **就绪路径行为** | T4 新增覆盖 | §3 |

⇒ **这是正确的分工**：Windows 专属形态由 Windows 专属断言守（在 macOS 上仍可跑，因为它断言的是**纯常量文本**）；平台无关的「就绪路径必须刷新」由 T4 用平台条件期望守。**不构成「把断言删到只剩绿的」**——4 条 T 用例 + 原有 Windows 断言**共存**，且我上轮 §7.2 建议的常量绑定已落（见 §8.1）。
**我唯一会建议的措辞订正**：把「T1 被 T4 取代」改为「**T1 的平台无关部分由 T4 承接；Windows 专属部分原样保留**」——因为两者测的是**不同维度**，说"取代"容易让人误以为 Windows 形态断言被删。
