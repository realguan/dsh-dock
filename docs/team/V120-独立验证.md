## 6. 我发现的残余缺口（如实登记，不阻塞提交）

### 6.1 ⚠️ 跨层 seam 的「序」是**手抄常量**——我构造出了反例

**现状**：`clientUpdateSeam.test.ts` 用**手抄**的 `WINDOWS_SEQUENCE` / `NON_WINDOWS_SEQUENCE` 回放真实 `applyUpdateEvent`；`updater.rs` 侧有两条**源码文本**判据，但只钉两个特定关系（首个 Downloading 早于 Installing、首条 set_state 早于 blocked_check）。

**我的反例（实测）**：在**真实** `run_download_and_install` 里插入一条前端表**不含**的迁移（模拟"Rust 改序"）：

```console
### 注入：在 Installing 之前插入 set_state(ClientUpdate::UpToDate)
### 哈希 34cc15a4bd8ccb26 → 08787f5dca8270d7 ✅ 生效
$ cargo test --lib updater::
  … 12 个用例全部 ok（含 emitted_sequence_advances_monotonically /
    apply_emits_download_before_install / apply_emits_visible_state_before_blocked_check）
### 复原=34cc15a4bd8ccb26 OK  残留=0
```

⇒ **Rust 改序后，Rust 全部 12 条测试仍绿；前端 seam 测试也不可能发现**（它不读 Rust 源码，`grep import` 确认只有 vitest/store/types 三行 import）。**即：新增一条相位发射对，两侧都不会红**——而 D6b 正是这个形态的复发（Rust 加了 `Checking`，前端没跟上）。

**为何这不是「无法可解」**：本仓库**已有跨层机器闸门的先例**——`updater.rs::app_update_event_name_matches_frontend_constant` 用 `include_str!("../../frontend/src/types/events.ts")` **从 Rust 侧读前端源码**。故同一范式可闭合本缺口：让 Rust 测试**从源码提取 `run_download_and_install` 的 `set_state` 顺序**并与 `transition_allowed` 逐对校验（或前端测试 `?raw` 读 `updater.rs`）。

**我的判定**：**残余缺口成立、可解、成本低**。但——
- D6b **修复本身有效且已被我两态证实**（§3.1），本缺口属「防线完整性」而非「修复不成立」；
- 故我**判为「通过 + 登记残余」**，而**不**判 fail。若 lead 要求"必须机器闭合"才可提交，则应另立小任务；**建议登记进 `docs/team/待裁定清册` 并在 v1.2.x 收口**。

### 6.2 附：一处流程自查（我自己犯的 M8 级错误，已改正并留痕）

我的 D6b 夹具 v1 把"破损表"作为参数传入，但生产 `applyUpdateEvent` 读模块常量 ⇒ **两态等价、测试绿得毫无信息量**。我**先自证两态输出相同**才发现，改为就地变异真实常量后复现成功（§3.1）。**教训：写"变异测试"时，必须先证明变异真的作用于被测路径。**
