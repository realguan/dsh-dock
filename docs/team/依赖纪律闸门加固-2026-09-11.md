## 3. 修复：九项禁符表 + 词边界硬化

### 3.1 判据

```rust
const FORBIDDEN_DEPS: &[(&str, bool)] = &[
    ("crate::shell::", false), ("crate::boot::", false), ("crate::ui::", false),  // ① 内联全路径
    ("use crate::shell", true), ("use crate::boot", true), ("use crate::ui", true), // ② 引入形态
    ("shell::", false), ("boot::", false), ("ui::", false),                          // ③ 裸前缀
];
```

| # | 形态 | 例子 | 原表 | 现表 |
| :-- | :--- | :--- | :-- | :-- |
| ① | 内联全路径 | `crate::shell::parse_detected_url(t)` | ✅ | ✅ |
| ② | **引入形态**（rustfmt 更倾向的写法） | `use crate::shell;` | ❌ **洞** | ✅ |
| ③ | **裸前缀**（② 之后调用点形态） | `shell::parse_detected_url(t)` | ❌ **洞** | ✅ |

### 3.2 为什么需要词边界（`path_token_hit`）

直接 `contains` 会带来**双向**问题，且"误报"的危害不只是多红一次：

| 边界 | 用途 | 不加的后果 |
| :-- | :--- | :--- |
| **前边界** | 裸前缀 `shell::` 不得命中 `my_shell::` | 误报 → 有人为过闸**删掉禁符**（"合理地削弱闸门"） |
| **后边界** | `use crate::shell` 不得命中 `use crate::shell_extra;` | 同上 |
| 后边界的**例外** | `crate::shell::` / 裸 `shell::` **不能**要求后边界 | 其后随的是被调用项名（标识符）⇒ 一律误判为不命中 ⇒ **又变成漏防** |

`path_token_hit` 对每次命中检查前后边界；被边界否决时从下一字节继续找（重叠匹配也覆盖）。
**固化用例** `dependency_gate_matcher_covers_all_three_forms`：10 个正例（含 `use crate::shell::{a, b};`
与 `use crate::shell as sh;`）+ 6 个负例（`crate::child_cmd`、`lifecycle::spawn`、`crate::shell_extra`、
`crate::ui_kit`、`my_shell::foo()`、`reboot::now()`）。

> 为什么单独测匹配器：闸门的价值全在"覆盖所有书写形态"，而边界逻辑很容易写错——
> 写错的后果与 task-36 的洞**同类**（看着在守、实际漏一种写法）。故把它钉成纯函数断言。

### 3.3 报错信息一并改进

原实现逐个禁符 `assert!`，**首个命中即中断**，看不到全部命中。现先收集 `violations` 再断言，
一次列出**所有**命中（形态 + 命中行），缩短排查路径——见 §4 变异 A 的双命中输出。

## 5. 次要残余（E3 部分回退）：分析成立，且比报告更宽

任务要求核实 qa-verify 的「E3 第 1 层在部分回退下不红」并登记（**不修**）。我用插入点级模拟逐点核对：

| 回退点 | 输出逐字节 | 第 1 层（计数） | 第 2 层（源码参数化） | 判定 |
| :--- | :--- | :--- | :--- | :--- |
| ① `rm -f {stop} {ready}` 前缀 | 同 | 绿 | **红** | 第 2 层检出 ✅ |
| ② `tee {ready}` | 同 | 绿 | 绿 | **两层皆绿** ⚠️ |
| ③ `while [ ! -f {stop} ]` | 同 | 绿 | 绿 | **两层皆绿** ⚠️ |
| ④ 尾部 `rm -f {stop} {ready}` | 同 | 绿 | 绿 | **两层皆绿** ⚠️ |

**核实结论**：
1. **qa-verify 的分析成立**——「回退点取值与常量相同 ⇒ 输出逐字节不变 ⇒ 第 1 层计数仍为 3 ⇒ 不红」
   完全正确；
2. **延迟检出属实**：此后一旦改常量，被回退的那一处不跟随 ⇒ 输出中旧值出现 1 次、新值 2 次
   ⇒ 第 1 层计数 = 2 ≠ 3 ⇒ **红**（模拟确认）。故属**延迟检出，非永久漏检**；
3. **refinement（本文新增）**：残馀范围**比报告描述的更宽**——报告称"第 2 层兜底"，
   但实测**第 2 层只守住回退点 ①**（它断言的是格式串**开头** `"rm -f {stop} {ready};{prep}\`），
   ②③④ 三处**两层皆不红**。
4. **危害评估**：回退点取值与常量相同时**行为仍正确**，风险是未来漂移——而那次漂移**会被第 1 层
   抓到**。故属"延迟检出"的已知残余，不是静默永久失效。
5. **本任务不修**（按指令）。若将来要收紧，最直接的做法：在第 2 层追加**生产段占位符计数断言**

**为什么漏**：分组形态里 `shell` 与 `crate::` 之间隔着 `{`——`use crate::shell` 模式不命中；
而 `shell` 后面没有 `::`——裸前缀模式也不命中。

**这正是本任务自身的教训重演**：**闸门只防「当时见过的那种写法」**。三种形态是任务列举的，
第四种不在其列；且两种候选修法各有取舍，**故我按范围不动手，登记请裁定**：

| 选项 | 做法 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| **P-1（推荐）** | 对生产段**抹空白后**解析 `crate::{…}` 组，把组内项展开为 `use crate::<项>` 再套同一套模式 | 覆盖分组 + 多行分组 + 别名 | 引入一个小型 `use` 树解析（~15 行），自身可能出错——故须配匹配器单测 |
| **P-2（更严）** | 禁「裸标识符 `shell` / `boot` / `ui` 作为独立词」出现在生产代码 | 一举覆盖**所有**形态（含未来写法） | 假阳性面大：局部变量名、字符串如 `"dsh-shell.log"` 都会命中（现仓为 0，但会随代码演化） |

**我的倾向**：P-1。P-2 虽最彻底，但"过严 → 被合理地削弱"是同一族风险（见 §3.2 的误报论证）。

## 0. 一句话

**停止打补丁是对的**——但复核发现 lead 表中形态 4 / 5 **并未真正绕过**（它们被旧闸门的
**调用点**模式与 `use crate::shell` 子串模式拦住了）。**真正的绕过维度是「别名」（`as`）**，
它把"写法枚举"变成了**正交维度**：任意 import 路径 × 任意别名 = 无穷变体。
这反而**更强地**支持换不变式——因为要补的不是"第 N 种写法"，而是**无穷种**。

## 1. 修正 lead 的形态表（实测复核，非静态推演）

| # | 形态 | lead 判定 | **我实测** | 为什么 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | `crate::shell::X()` | ✅ 拦 | ✅ 拦 | — |
| 2 | `use crate::shell;` + `shell::X()` | ✅ 拦 | ✅ 拦 | — |
| 3 | `use crate::{child_cmd, shell};` | ❌ 漏 | ⚠️ **分情况**：**只写 import（无调用）→ 漏**；**带 `shell::X()` 调用 → 拦**（调用点命中裸 `shell::`） | 旧表含裸 `shell::` |
| 4 | `use super::shell;` + `shell::X()` | ❌ 漏 | ❌ **不成立：拦** | 拦住它的是**调用点**的 `shell::`，与 import 形态无关 |
| 5 | `use crate::shell as sh;` + `sh::X()` | ❌ 漏 | ❌ **不成立：拦** | `use crate::shell` 是该行的**子串**，且后随空格 ⇒ 后边界满足 |
| **3'** | `use crate::{child_cmd, shell as s};` + `s::X()` | （未列） | ❌ **漏（实测确认）** | import 行无 `use crate::shell` 子串；调用点 `s::` 不在表内 |
| **4'** | `use super::shell as s;` + `s::X()` | （未列） | ❌ **漏（实测确认）** | 同上 |

**3' / 4' 的确认方式（真注入，非推演）**：从 `git show HEAD:src-tauri/src/lifecycle.rs`
取回**旧闸门**（形态黑名单版）作对照，注入后旧闸门 **`test result: ok`（放行）**，
且注入代码可编译。两次注入均 `trap` 还原 + sha256 校验（新版本已复位）。

> **结论修正**：绕过家族不是"某几种写法"，而是 **`as` 别名**这一维度。
> 只要 `as` 存在，就能同时避开"import 行含模块名后缀"与"调用点含 `shell::`"两类模式。
> 这正是**形态枚举法在原理上不可完备**的实证——枚举的是写法，而别名是**正交轴**。

## 2. 新判据：不变式（与书写形态无关）

```rust
/// 判据 = 模块名本身作为**裸标识符**出现 ⇒ 与写法无关
const STATE_HOLDING_SIBLINGS: &[&str] = &["shell", "boot", "ui"];
```

**论证**：任何对该模块的引用——内联 / `use` / 分组 / `super::` / `as` 别名 / `pub use` /
宏内路径——**都必须在某处写出模块名本身**。模块名是**语法形态无关的不变量**，写法是无穷变体。
⇒ 判据从"枚举写法"改为"数模块名"，**一次覆盖全部已出现与未出现的形态**。

**词边界**（`bare_word_hit`）：`word` 两侧都不得是标识符字符。
- 不误报：`shell_extra` / `shellfish` / `my_shell` / `reboot` / `shell_count` / `ui_scale`；
- 必须命中：`use crate::shell as sh;`（两侧是 `:` 与空格）。

**代码视图**（`production_code_lines`）三层处理，缺一层都会出问题：
1. **CRLF 归一**（v1.1.1 教训）；
2. **截断测试段**（测试里故意造这些标识符做对照——本用例自己就是）；
3. **抹注释与字面量**——**复用 task-30 已测的 `structural_bytes`**（行注释 / 可嵌套块注释 /
   普通·原始·字节字符串 / 字符字面量与生命周期），保留换行 ⇒ **行号不变**。
   复用而非新写词法器：重复实现只会多一处出错点（task-34 的 `br"…"` 教训）。

## 3. 取舍：**删除**旧三形态判据（合并为单一不变式）

**理由**：
1. **严格被包含**：不变式覆盖旧表全部能力（旧表能拦的，模块名必出现 ⇒ 不变式也拦）；
2. **留着一份有洞的判据是负资产**：旧表已知漏 3'/4'，与不变式并存会给人"两处口径"的错觉，
   且极易诱发"再加一个模式"的补丁冲动——**那正是本闸门三次复发的成因**；
3. **诊断力未损失**：不变式报出**行号 + 整行**，比旧表的"命中哪个模式"更直接。

⇒ 净效果：判据行数更少、覆盖更全、维护面更小。`FORBIDDEN_DEPS`（9 项形态表）与
`path_token_hit`（含"某些模式要后边界、某些不要"的易错逻辑）一并删除，仅保留边界判定。

```

截断后生产段是否含该依赖  : false
⇒ 闸门判定                : 绿（放行 = T1 成立）
```

**修法（方案 ②）**：`production_code_lines()` 改为

## 4. 顺带：重复面是否仍在扩大（结论）

现状两份「词法掩码 + 定位」：

| 位置 | 词法器 | 定位/排除 | 需求 |
| :--- | :--- | :--- | :--- |
| `lifecycle.rs` | `structural_bytes` → `Vec<bool>`（code vs 非 code） | `item_spans` + **截断** `production_code_lines_of` | 扫**自己**，测试模块在文末 ⇒ 可截断 |
| `network_gate.rs` | `classify` → `Vec<Lex>`（Code/Literal/Comment 三态） | `item_ranges` + **条目级** `cfg_test_ranges` | 扫**别的文件**，测试模块可能**夹在中间** ⇒ 必须条目级 |

**结论（一句）**：**本轮未扩大，反而少了一处**（删掉 T1 用例的复刻闭包）；
但 `production_code_lines_of` **不能**被 `network_gate.rs` 直接复用——两者**需求不同**：
后者扫的是**其它文件**，其测试模块可能位于文末之前的任意位置（该模块有专门用例
`production_code_after_mid_file_test_module_is_still_scanned` 钉住这一点），故必须**条目级排除**
而非截断。**真正可共用的是底层词法器**（`structural_bytes` 的 bool 掩码 vs
`classify`+`structural_mask` 的三态）——即 task-30 已登记的那条去重候选，**仍待独立立项**，本轮不做。
