## 5. bootstrap 两平台落位（POSIX 无消费者）—— 取舍评判 ✅ **成立，但存在更干净替代**

**rust-core 的理由**：若只在 `cfg!(windows)` 写，macOS 上该函数无调用者 ⇒ `dead_code` 撞 `-D warnings`，且无法本机单测。
**我的评判**：
1. **理由成立**：本机（macOS）`cargo clippy --all-targets -- -D warnings` 是 CI 闸门，`dead_code` 会红 ✅
2. **代价可接受且我已实测其无害**：POSIX 侧多一个 1.4 KB 惰性文本。我核了两条发现路径**不会**被它干扰：
   ```text
   find_engine_tool("dsh") 候选 = dsh.exe / dsh.cmd / dsh  → "dsh-boot.mjs" 不匹配   ✅
   find_versioned_fallback: prefix="dsh-" 余部="boot" → 非 16 位 hex ⇒ 不匹配        ✅
   ```
   且 POSIX 启动路径逐字未变（§3）⇒ **不违反 ADR §2「不扩大分叉面」**（该文件在 POSIX 无消费者、不改行为）✅
3. **更干净的替代（可选，非必须）**：`#[cfg(any(windows, test))]` 门控 `dsh_bootstrap_mjs`/`write_dsh_bootstrap`（本仓库**已有先例**：`guest.rs::guest_prep!` 正是 `#[cfg(any(windows, test))]`）。这样 release-POSIX 构建里函数根本不存在（无 dead_code），测试仍可在本机跑。
   **但我认为当前方案更优**：`any(windows, test)` 需把调用点也 cfg 门控，会让落位逻辑出现「测试态与发布态不同」的分裂——而当前实现**两平台逻辑单一、行为一致、本机可测**，代价只是一个惰性文件。**故我支持保留现状**（若 Lead 偏好零冗余文件，替代方案如上，一行级改动）。

### 7.2 ⚠️ 发现：`DSH_BOOTSTRAP_NAME` 与 Windows shim 字面量**未被任何测试绑定**（我自创 M4）

```text
const DSH_BOOTSTRAP_NAME = "dsh-boot.mjs";                    // engines.rs:112（写文件用）
dsh_shim_windows() 内含硬编码字面量 "%~dp0dsh-boot.mjs"        // engines.rs:108（shim 目标）
测试：windows_shim_shape_is_exact 断言**字面量**；write_dsh_bootstrap 用**常量**
      ⇒ 没有任何断言要求「常量 == 字面量」
M4 实测：只改名常量 ⇒ **408 全绿**（无红）
```

**后果**：若将来重命名该常量，`write_dsh_bootstrap` 会写新名文件，而 `dsh.cmd` 仍指向旧名 ⇒ **Windows 上 dsh 指向不存在的文件、启动失败，且全套测试静默**。
**严重度**：低概率（需有人改常量）× 高影响（Windows 首启不可用）× **静默**。
**一行级修法（建议，非阻塞）**：在 `windows_shim_shape_is_exact` 里把字面量断言改为绑定常量：

```rust
assert!(
    shim.contains(&format!("\"%~dp0{DSH_BOOTSTRAP_NAME}\"")),
    "Windows shim 必须指向 bootstrap 常量名：{shim:?}"
);
```
（同族教训：ADR-0017 的 `dsh_entry_js → shim` 接线当时也**只由一条测试**守——已在上一轮报告 §6.2 登记；本处是同一家族的新实例。）

### 7.3 `js_code_only` 剥离器的两处已知盲区（当前内容安全，登记待观察）

我逐行读过该函数（逐字节实现）：
- **不识别字符串字面量**：若将来在**字符串里**写 `//`（如 `"https://…"`），剥离器会把该行 `//` 之后的内容整段删掉 ⇒ 可能造成**假阴性**（断言找不到本存在的语句）。**当前 bootstrap 的字符串均不含 `//`**（入口串是 `"../dsh-runtime/…"`，消息串里只有单个 `/ symlink`）⇒ **当前安全**；我会在报告里登记为「新增字符串含 `//` 时需复查」。
- 只处理 `//` 与 `/* */`：**不处理 `#!` shebang**（本是 JS 文件，无此需求）——**无影响**。

| **B1** | **Windows 真机未验** | 本机全部证据来自 **macOS**。**平台机制不同**：Windows 的 `EPERM/symlink` 由「缺 `SeCreateSymbolicLinkPrivilege`」触发，而 macOS **无此限制** ⇒ 我在 macOS 上验的是「**代理模式确实零软链**」这一**结果**，**不是**「Windows 上不再 EPERM」这一**因果**。⇒ **macOS 的「0 软链」不能替代 Windows 真机验证**。真机判据（ADR §6）：`%USERPROFILE%\.dsh\profiles\node_modules` 下无符号链接 + 本地模式能进工作台 |
| **B2** | **绊线只覆盖我们这条启动路径** | 绊线包在 bootstrap 的 `try { import; runCli }` 外。若 dsh 将来在**别的入口/别的进程**建链接（如某个子命令 fork 出的进程、或 `dsh.cmd` 被旁路调用），**不触发**本绊线 |
| **B3** | **proxy 与 symlink 的条目集合不完全相同** | ADR §5 已登记（proxy 只代理「可解析出入口」的包）。我实测 plain 186 条目 vs proxy 184 条目 ⇒ **差 2 条**，与 ADR 的「不完全相同、判定可接受」一致，但**这 2 条是什么、是否影响功能，我未逐条判定** |
| **B4** | **依赖 dsh 未公开内部判据 `process.pkg`** | ADR §5 已登记为接受的取舍；绊线（§2）是缓解。**上游一旦变更，本机无自动告警**，只能靠绊线在用户侧报出 |
| **B5** | plain 模式的 `dsh web:` 未在窗口内观测到 | §1.2 已记录（不影响核心判据） |
| **B6** | `js_code_only` 对字符串内 `//` 的盲区 | §7.3（当前内容安全） |
