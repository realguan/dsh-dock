## 1. 问题 1：裸 `taskkill` 的对照证据与修复

### 1.1 修复前后

| 位置 | 修复前 | 修复后 |
| :-- | :-- | :-- |
| `lifecycle.rs:897`（`reap_pid`，Windows 回退路径） | `let mut cmd = Command::new("taskkill");` | `let mut cmd = crate::child_cmd(Path::new("taskkill"));` |
| 对照：`shell.rs:244`（**同一动作**） | `crate::child_cmd(Path::new("taskkill"))` | 不变 |

### 1.2 为什么这是真缺陷（不是风格问题）

`child_cmd` 的两个职责（`lib.rs:64-79` 原文）：

1. **Windows 上 `.cmd/.bat` 不能直接 spawn**（`CreateProcess` 不认批处理），必须包 `cmd /C`；
2. **一律 `quiet_cmd`**（原文注释：「黑色终端窗口问题」）。

`reap_pid` 是**启动期孤儿清扫**与**硬杀回退**都会走的路径（用户可感知：启动时扫到孤儿就会触发），
裸起 `taskkill` 在 GUI 进程里**会闪黑窗**。且这属 AGENTS §4.1 正面违反（「Windows 子进程一律经
`crate::child_cmd`」）。

### 1.3 不成环的确认（lead 已核实，我复核了依赖方向）

| 事实 | 证据 |
| :-- | :-- |
| `child_cmd` 定义在 **crate 根** | `lib.rs:68` `fn child_cmd(bin: &Path) -> Command` |
| `shell.rs` 依赖 `lifecycle` | `shell.rs:101` `crate::lifecycle::spawn(...)` |
| 故反向调 `crate::shell::*` 会成环 | 我**没有**这么做 |
| 调 `crate::child_cmd` 不成环 | 子模块调祖先模块的私有项合法（`shell.rs:244` 已是先例） |

修复处已写纪律注释：**不得**改调 `crate::shell::*`（会成模块环，并破坏「`lifecycle` 是零
`crate::` 依赖的叶模块」这一单向性前提——而该前提正是 §2 把本文件纳入扫描面的地基）。

> 参数构造 `/PID /T /F` 仍留在本地（与 `shell::windows_kill_args` 的合并 = task-29 §3.2 选项 A）
> 属**独立意图**，按 lead 指令暂不动。

## 2. 问题 2：闸门盲区与条目级豁免

### 2.1 盲区的准确形态

| 项 | 修复前 | 修复后 |
| :-- | :-- | :-- |
| `SOURCES`（`lifecycle.rs:1852-1868`） | 13 个文件（boot / commands/window / engines / executor / ipc / plugins / profiles / resolve / sessions / shell / updater / updates / lib） | **14 个**（补入 `src/lifecycle.rs`，见 `:1859`） |
| 本文件的合法 spawn | 因整个文件不在面内而"天然豁免" | **条目级**豁免（4 条，见 §2.2） |

> 盲区的危害不止"漏一处"：它是**结构性的**——seam 的属主文件恰恰是**最可能新增 spawn**
> 的文件（新角色的守卫接线都写在这里），却唯一不受自己的闸门管辖。

### 2.2 豁免表（集中、条目级、最小化）

| 文件 | 函数 | 摘掉后应报行数 | 为什么**必须**绕过 seam |
| :-- | :-- | :-- | :-- |
| `src/lifecycle.rs` | `fn spawn` | **3** | seam 本体：守卫式 spawn 的唯一实现（两处降级早退 + 主路径） |
| `src/lifecycle.rs` | `fn run` | **1** | seam 本体：`Command::output()` 的守卫版（`wait_with_output()` 是其等待动作） |
| `src/lifecycle.rs` | `fn launch` | **1** | 生命线 watcher（`Lifeline::launch`）**必须**不经 seam：它的职责正是壳死收口子进程，若被登记/守卫，**清扫会把 watcher 自己当孤儿收掉** |
| `src/lifecycle.rs` | `fn reap_pid` | **1** | 清扫器本体：`taskkill` 回退**不能**经 seam（清扫在启动早期运行，再登记一层只会制造自指）；已改走 `child_cmd` 满足 §4.1 |

**为什么是条目级而非整文件排除**：整文件排除**正是本盲区的成因形态**——把「这个文件可以随便来」
换成「**这几个函数是 seam 本体，该文件其余部分一律照扫**」。此前 `lifecycle.rs` 受到的正是
事实上的整文件排除。

**`hits` 字段的设计**（一次钉死两侧腐化）：

- **非空** ⇒ 该条目仍在使用（不是腐化的空条目）；
- **恰好** ⇒ 豁免区间**没有过宽**（扩大到邻接函数会让该计数变大）。

由 `spawn_gate_exemptions_are_live` 断言，`spawn_gate_exemption_entries_are_well_formed` 保证
每条可解释（理由须点明与 seam 的关系 + `YYYY-MM-DD` 日期 + 无重复条目）。

### 2.3 行内标注机制保留（有意）

`// spawn-gate: exempt(理由)` 的**行内**机制保留未动——`updater.rs:98` 依赖它
（`reap()` 里的 `reqwest::Error::status()` 是**读状态码**，不拉起任何进程）。两者分工：

- **条目级集中表**（本文件）→ 函数粒度清晰、可自检、可精确计数的场合；
- **行内标注**（其它文件的极个别场合）→ 函数粒度太粗、只有一行需要豁免时。

### 2.4 实现要点：区间定位必须先做词法

豁免要"精确到函数"，就得算函数体的花括号区间。而 `"}"`（字面量）与 `// }`（注释）里的花括号
**不是结构**——被骗到的后果**不对称**：

- 区间偏小 → 误报（**可见红**，可接受）；
- 区间偏大 → **吞掉邻接函数的违规**（静默漏报 = 本缺陷的成因形态）。

故按字节实现词法掩码 `structural_bytes`（行注释 / **可嵌套**块注释 / 普通与字节字符串 /
原始字符串 / 字符字面量，并区分字符字面量与生命周期 `'a`），再按掩码配对花括号。

> **实现期自测抓出的一个真 bug（已修 + 已加回归测试）**：首版把识符检查放在推进下标**之后**
> （`p += 1` 跳过 `b` 再判 `!is_ident(b[p-1])`），于是 `br"…"` 的 `b[p-1]` 恰是那个 `b` 本身
> → 判据恒假 ⇒ **字节原始字符串从未被识别**，其内部花括号会被当成结构字符 → 区间偏大 → 静默漏报。
> 已用独立脚本确认该判据恒假，修法与 `network_gate.rs` 同构（先看 `b[i-1]` 再决定是否推进），
> 并加 `spawn_gate_extent_finder_handles_byte_raw_strings` 钉住。

## 6. 顺带排查（只读，**只记不修**，请 lead 裁定）

### 6.1 `lifecycle.rs` 生产段剩余的 `Command::new`：**仅 1 处**

| 位置 | 代码 | 归属分析 |
| :-- | :-- | :-- |
| `lifecycle.rs:649` | `Command::new("/bin/sh")`（`Lifeline::launch` 内，`#[cfg(unix)]`） | **不属 AGENTS §4.1 违反**：§4.1 管的是 **Windows** 子进程（`.cmd/.bat` 包装 + 防闪窗），而此分支**只在 unix 编译**、且 `/bin/sh` 不是批处理脚本。在 unix 上 `child_cmd` 等价于 `Command::new(bin) + quiet_cmd`（后者在 unix 是 no-op，`lib.rs:62`），故改不改**行为相同** |

**它是否应该豁免**：**必须豁免**，且理由不是"省事"而是**语义必需**——
watcher 的职责是壳死后收口子进程；若它自己被 `lifecycle::spawn` 登记/守卫，
① 生命线会让它在壳死时被收掉（**自我毁灭**），② 启动期清扫会把它当孤儿收掉。
故 `launch` 的条目标注为「必须绕过 seam」。

**建议**：可选的**纯整洁性**改动——把 `:649` 也改走 `crate::child_cmd`（unix 上行为等价，
统一入口）。价值低、风险低，**由 lead 决定是否立项**；本轮按指令只记不修。

> 另注：`lifecycle.rs:1189` 的 `Command::new("/bin/sh")` 在 `#[cfg(test)]` 内（测试模块，
> 故意制造裸 spawn 做对照），**不属生产段**，闸门按设计不扫。

### 6.2 闸门判据与 `Command::new` 的关系（澄清一条容易误解的点）

闸门判据是 **spawn 动词**（`.spawn()` / `.output()` / `.status()` / `wait_with_output()`），
**不是** `Command::new` 本身。这是**正确**的：`Command::new(...)` 后交给 `lifecycle::spawn`
正是规范用法，若按 `Command::new` 判会全量误报。变异 C 演示了这一点——
修复前的裸 `taskkill` 是被它后面的 `.status()` 抓住的。

### 6.3 与 `network_gate.rs` 的一处重复（已知，建议另立任务）

两个闸门各有一份"词法掩码 + 函数区间定位"（`network_gate.rs` 的 `classify`/`item_ranges` 与
本文件的 `structural_bytes`/`item_spans`）。原因：`network_gate.rs` 整体是 `#[cfg(test)]` 且
helper 私有，本任务范围**禁止改它**，故只能同构重写。

**建议**（不属本任务）：把这对 helper 提到一处中立的 `#[cfg(test)]` 共享模块，
让两个闸门共用——否则将来修词法 bug 要改两处（**本轮的 `br"…"` bug 就正是这种重复的代价**：
若两份代码同源，它不会只错一份）。**只记不动**，等 lead 排期。
