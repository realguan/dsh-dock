## 4. R4（Linux 目标 clippy）为何是「不可执行」而非「代码有问题」

**判定为环境限制，判据三条（均为实测）**：

1. **失败发生在依赖的 build script 阶段**，不是 dsh-dock 自身的 lint：
   `error: failed to run custom build command for \`glib-sys v0.18.1\``（`Compiling glib-sys` → `gdk-sys`/`gobject-sys`/`atk-sys` 全部同样报错）
2. **原文直接指名原因**：
   `warning: glib-sys@0.18.1: pkg-config has not been configured to support cross-compilation.` +
   `Install a sysroot for the target platform and configure it via PKG_CONFIG_SYSROOT_DIR and PKG_CONFIG_PATH, or install a cross-compiling wrapper for pkg-config`
3. **宿主确实不存在这些 Linux 专属库**（逐个查询）：

   ```console
   $ for p in webkit2gtk-4.1 javascriptcoregtk-4.1 gtk+-3.0 libsoup-3.0 ayatana-appindicator3-0.1; do
       pkg-config --exists "$p" && echo "$p: present" || echo "$p: ABSENT"; done
   webkit2gtk-4.1: ABSENT
   javascriptcoregtk-4.1: ABSENT
   gtk+-3.0: ABSENT
   libsoup-3.0: ABSENT
   ayatana-appindicator3-0.1: ABSENT
   ```

   → macOS 上根本没有 Linux 的 WebKitGTK/GTK3 sysroot；`grep -L` 式核对 `grep -c` 本机 `/opt/homebrew/lib/pkgconfig/` 对 `webkit|javascriptcore|soup|gtk+-3|ayatana|appindicator` **零命中**。

**与既有认知的一致性**：`docs/broadcasts.md`（2026-09-11 返工条目）已记载「Linux 目标无法在 macOS 上跑 clippy：glib-sys/gdk-sys 缺 WebKitGTK pkg-config，属环境限制」——**我独立复现了该结论，判据相同**。

**为何不影响 v1.1.1 的交付信心**：CI 的 `ubuntu-latest` job **原生**（非交叉）执行 `cargo clippy --all-targets -- -D warnings` 并通过（见 `docs/team/v1.1.1-验收取证-2026-09-11.md` §2）。**本机这条的替代证据 = CI Linux 原生结果**，但**它不能替代「本地改动后的 Linux clippy」**——见 §5 R1 的口径提示。

## 5. 与 CI 口径的差距（逐条，含影响面）

| # | 差距 | 事实 | 影响面 / 谁能补 |
| :--- | :--- | :--- | :--- |
| **R1** | **本地 Windows clippy 是交叉编译，CI 是原生的另一个 ABI** | 本地 `--target x86_64-pc-windows-gnu`（MinGW/GNU ABI）；CI `windows-latest` job 在 `build.yml:133` 跑**裸** `cargo clippy --all-targets -- -D warnings`，即 **MSVC ABI**。两者都会编译 `cfg(windows)` 代码，但 toolchain/ABI/link 阶段不同 | **真实缺口的替代证据是 CI**。这正是 v1.1.1 首次构建红的教训（`cargo check` 不跑 lint）：**本机必须用 `clippy` 而非 `check` 跑交叉目标**（本轮已照做）。但**交叉 gnu ≠ 原生 msvc**，新增 Windows 专属代码时**不可只凭本机交叉绿就断定 CI windows 会绿** —— 补法：推 master 让 CI 三平台验一遍（这正是 v1.1.1 返工后维护者定的收尾方式） |
| **R2** | **本地 Linux clippy 不可执行** | 见 §4（缺 WebKitGTK/GTK3 sysroot） | 只能由 CI ubuntu-latest 原生覆盖，或本机装 Linux sysroot / 容器（当前无）。**任何改动 linux-only 分支时，本机无法给出绿证** |
| **F1** | **`pnpm install --frozen-lockfile` 本轮跳过** | `node_modules` 已存在（384 M），未重跑 | 若 `pnpm-lock.yaml` 与 `package.json` 不一致，本地闸门不会发现（CI 每轮跑 `pnpm install --frozen-lockfile`）。**本轮 diff 未动 `package.json`/lockfile**，风险低；需要时补跑一次即可 |
| **F2** | **本机未跑 CI 的 Python 套件** | CI ubuntu job 另有 `python3 -m unittest discover -s scripts/tests`（tag run 输出 `Ran 9 tests in 0.004s`） | 本任务口径未要求；`scripts/` 无改动，风险低。**未跑 = 未验**，不声称绿 |
| **R3** | **timing 受热缓存影响，不可作性能基线** | `src-tauri/target` 21 G 热缓存：R1/R2 为 0–1 s（`Finished in 0.28s` 表示 cargo 指纹命中、未重编译）。R3 做了真实 check（21.53 s），R5 真实编译并执行（20.61 s） | 耗时数字**只代表本机热缓存**，不可与 CI 冷构建对比。**结论（退出码/用例数）不受影响**——cargo 指纹在源码变动后会失效并重编 |
| **R4** | **磁盘余量偏紧** | 25 Gi 可用 / 95% 已用；`target` 已占 21 G | 若为他人生成新 target dir 或全量重建，可能触顶。**建议：需冷跑基线时先清理 `src-tauri/target` 或用独立 `CARGO_TARGET_DIR`（并留意磁盘）** |

## 8. 本基线的使用方式（给团队）

1. **改码后对比**：跑 §3 / §6 同款命令，比对**三个不变量**——① 所有退出码为 0（R4 除外，环境限制）；② `cargo test` 用例数 = 290 + 你新增的 `#[test]` 数 − 你删掉的数；③ 前端 `Tests` / `Test Files` 数变化能被你的 diff 解释。
2. **数字对不上就是信号**，优先怀疑「测试没被扫到」（例如新增文件不在 `src/__tests__/` 下、或测试文件命名不匹配 vitest 默认 include）。
3. **发布前不要只信本机**：R1/R2 两条差距意味着 **Windows MSVC 与 Linux 原生 clippy 只有 CI 能给出权威结论**——这正是 v1.1.1 首次构建红的成因链。
