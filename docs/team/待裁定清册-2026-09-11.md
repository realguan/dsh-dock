### C3 `defaultProfile` 语义措辞 vs 实现【已裁定并登记 ✅ 2026-09-11】

- **发现**（qa-verify task-21）：AGENTS §6 原写「None/**失效值**读取侧兜底 `web`」，
  与实现不符——`commands/profile.rs::get_default_profile`（`:164`）**原样返回** stored、
  无归一化；其自身注释写的是「None = 未设置，**消费方**兜底 web」。全仓 `?? "web"` /
  `unwrap_or("web")` 的兜底**只覆盖 None**。「失效值」实际靠**上游清除**（删除
  `profile.rs:137` / 重命名 `:97` 把引用置 None）——手工编辑 `settings.json` 留下的
  stale 值会绕过它。
- **裁定（lead，2026-09-11）= 改措辞，不补归一**。理由：
  1. **行为本身就是对的**——`resolve.rs:659 consume_default_profile` =
     `stored.filter(n => candidates.contains(n))`，非候选值返回 `None`；
     `executor.rs:299` 的 None 分支「按常规流程启动」+ `needs_selector=true` ⇒ 失效值
     **出选择器、不自动启动 web**。「不消费 + 让用户选」比「猜一个 web」更诚实。
  2. **补归一反而是退步**：把 stale 值静默改写成 `web` 会**用一次写操作掩盖用户数据
     问题**，且引入「读取即写入」的副作用。
  3. 成本：仅 1 行措辞（AGENTS §6），§11 预算内完成（改动后 **249/250 行、§6=40**）。
- **已采取的动作**：AGENTS §6 该行改为「None 由消费方兜底 `web`，失效值不消费＝
  出选择器；删除/重命名同步引用」。
- **残留**：`frontend/src/pages/BootSelector.tsx` 注释引「None / 失效值」略宽于实现
  （新代码 `?? FACTORY_DEFAULT_PROFILE` 只覆盖 None）——随 task-25 一并校正。

### G2 【待裁定】要不要补 Linux arm64 / Windows arm64

- **不再是「做不到」**：GitHub 已于 2025-08 让 arm64 托管 runner
  [正式可用](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)，
  `ubuntu-24.04-arm` / `windows-11-arm` 可作 matrix 项。截止今日「只有 x64」的
  真实理由是**用户面与交叉成本**，不是平台能力：Windows ARM64 设备可经 **x64 仿真**
  跑现有包（`README.md` 已如此声明）⇒ 属「用仿真覆盖」而非「不支持」。
- **代价排序（低→高）**：
  1. **Linux arm64 最便宜**：`fetch-pnpm-bundle.sh` 已接受 `linux-arm64`、
     node 表已有该键、runner 可用 ⇒ 基本等于「加一个 leg + feed 加一键」。
  2. **Windows arm64 多一步**：必须先修 G3。
- **不做**同理可判：桌面 Linux arm64 与原生 Windows arm64 需求面窄，仿真/社区构建已覆盖。

### G3 【隐患·响亮失败】`win32-arm64` 映射跑在打包支持前面

- **事实**：`updates.rs::engine_pnpm_bundle` 对 windows+aarch64 映射 **`win32-arm64`**，
  但 `scripts/fetch-pnpm-bundle.sh` 的平台白名单只有
  `darwin-arm64|darwin-x64|linux-x64|linux-arm64|win32-x64`，
  对 `win32-arm64` 直接 `echo "不支持的平台名" ; return 2`。
- **不是上游缺口**（2026-09-11 实测）：`@pnpm/exe.win32-arm64` 在 npm 上**存在**
  （registry HTTP 200，六个平台全 200）⇒ **纯属本仓脚本的白名单遗漏**，一行可修。
- **失败模式 = 响亮**（已核）：消费点 `engines::stage_pnpm_from_bundle` 走
  `tar -xzf <bundle>`，文件不存在即非零退出并返回错误 ⇒ **不是静默**，
  但会在**运行时**（引擎引导）才发现「内置 pnpm 从未随包发出」。
- **为何现在无症状**：我们不构建 Windows ARM64 ⇒ 该映射从未被求值生效。
- **建议**：① 采纳 G2 任一 arm64 方案时**先**修此白名单；
  ② 或（零成本预防）现在就补白名单 + 一条单测，使「映射」与「打包支持」集合一致；
  ③ 或反向收窄 `engine_pnpm_bundle` 的 windows 分支使其与白名单一致（但会**丢失**
  上游已支持的能力）——**倾向 ②**。
