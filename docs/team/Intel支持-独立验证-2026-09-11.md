## 3. A 部分：对抗角度逐条结论

### A1 —— `if: matrix.native_arch` 是否让某 leg **静默跳过** Unit tests？ → **不会（4 leg 全部可判）**

YAML 真实类型（非字符串真值）：

```text
macos-latest             native_arch=true   (TrueClass)   => RUN Unit tests
macos-latest-x86_64      native_arch=false  (FalseClass)  => SKIP Unit tests
windows-latest           native_arch=true   (TrueClass)   => RUN Unit tests
ubuntu-latest            native_arch=true   (TrueClass)   => RUN Unit tests
```

⇒ 仅 x86_64 leg 跳过，且**不是静默**：该 leg 有显式替代步骤 `Compile tests for target arch (no run)`（`if: matrix.native_arch == false`，`cargo test --no-run --target x86_64-apple-darwin`），并有注释说明理由（arm64 runner 上**运行** x86_64 测试二进制依赖 Rosetta，不保证预装）。
**判定**：**不是静默跳过**——跳过附带显式补偿步骤 + 说明；且该 leg 的 **clippy 带 `--target`**（真正的 lint 覆盖未被削减）✅
**残余边界**：x86_64 leg **不执行**测试（只编译）。若 Intel 上有**运行期**特有失败（如 Rosetta 相关、字节序无关但依赖 runtime 行为），**该 leg 不会发现**——这是有意的取舍，已在 workflow 注释中说明（执行面由原生 leg 覆盖）。

### A3 —— 打标步骤边界：无 `.sig` 容错？重复执行？ → **无 .sig 容错 ✓；重复执行会「双重打标」（低危）**

我用**打标步骤的原文逻辑**在 `/tmp` 夹具上复演 4 个场景：

| 场景 | 初始 | EXIT | 结果 | 判定 |
| :--- | :--- | ---: | :--- | :--- |
| **无 `.sig`**（`--no-sign` 的 PR/branch 构建） | `DSH Dock.app.tar.gz` | 0 | `DSH Dock_aarch64.app.tar.gz` | ✅ **容错正确**（`if [ -f "$f.sig" ]` 守卫） |
| **重复执行**（对已打标目录再跑） | `DSH Dock_aarch64.app.tar.gz{,.sig}` | 0 | **`DSH Dock_aarch64_aarch64.app.tar.gz{,.sig}`** | ⚠️ 双重打标（见下） |
| 无任何 tarball | `bundle_dmg.sh` | **1** | `::error::NO_TARBALL_FOUND` | ✅ 响亮失败 |
| 多个 tarball | 两个 `.app.tar.gz` | 0 | 两个都被打标 | ✅ 按预期逐个处理 |

**重复执行的危害评估（实测）**：双重打标名 `DSH Dock_aarch64_aarch64.app.tar.gz` **仍能被 feed 正确映射**（`darwin_target_for` 按子串匹配 → 仍 `darwin-aarch64`）⇒ **不会发错架构**，仅资产名变丑。
**在 CI 中不可达**：每个 leg 跑在**一次性 runner** 上，打标步骤每 job 至多执行一次。**仅在本地/重试复用工作区时可能出现**。
**判定**：**低危，不建议本轮改**（若将来要加护栏，一行 `case "$base" in *_aarch64|*_x86_64) skip' 即可）。

### A4 —— 表达式在 `rust_target` 为空串时是否真的**不带** `--target`？ → **证实（空串正确）**

按 GitHub 表达式语义（`a && b || c`）做 JS 等价复演：

```text
rust_target="aarch64-apple-darwin"  -> clippy 参数="--target aarch64-apple-darwin"
rust_target="x86_64-apple-darwin"   -> clippy 参数="--target x86_64-apple-darwin"
rust_target=""                      -> clippy 参数=""        ← 不带 --target ✅
```

⇒ **空串产出空参数** ✅。且 4 个 leg 均**显式定义** `rust_target`（YAML 已核），不存在「键缺失」分支。
**残余（仅记录）**：若将某 leg 的键删掉（`null`），GitHub 宽松相等会把 `null != ''` 判为**假**（`null`→0、`''`→0）⇒ 仍**不带** `--target`，**退化为安全方向**，不会误加参数。
**并记录一处纯外观差异**：空串时命令变为 `cargo clippy  --all-targets …`（**双空格**）与 `cargo test `（**尾随空格**）—— shell 语义**完全等价**，无功能影响。

### A5 —— Windows/Linux leg 的命令与路径是否**逐字未变**？ → **⚠️ 结论：功能等价，但**并非**逐字未变（6 处差异，已逐条定性）**

我按「表达式求值 + 分支展开」逐 step 比对（旧基线 `542275e`）：

| 步骤 | 差异 | 定性 |
| :--- | :--- | :--- |
| `Rust clippy gate` | `cargo clippy --all-targets` → `cargo clippy  --all-targets` | **纯外观**（双空格），shell 等价 ✅ |
| `Unit tests` | `cargo test` → `cargo test ` | **纯外观**（尾随空格）✅ |
| `Fetch bundled pnpm` | 新增 `elif [ -n "${{ matrix.pnpm_platform }}" ]` 分支 | Windows（`RUNNER_OS=Windows`）走原第一分支；Linux（空串）走原 `else` ⇒ **行为等价** ✅ |
| `Build unsigned installers` | 包进 `if rust_target 非空 … else` | Windows/Linux（空串）走 `else` ⇒ `cargo tauri build --no-sign` **与旧版逐字相同** ✅ |
| `List bundle outputs` | 包进 `if rust_target 非空 … else` | Windows/Linux 走 `else` ⇒ `find target/release/bundle -type f \| sort` **与旧版逐字相同** ✅ |
| `Build signed installers (macOS)` | 新增 `PNPM_TGZ=…` + `cargo tauri build --target …` | **仅 macOS leg 执行**；arm64 leg 的 `PNPM_TGZ` = `darwin-arm64.tgz`（**等于旧硬编码值**）✅ |

⇒ **判定**：**Windows/Linux 的功能行为未变**（三处 `if/elif` 均解析回旧命令，两处纯空格差异无语义）。**但「逐字未变」这个更强的说法不成立**——报告如实区分：**功能等价 ✓ / 文本逐字 ✗**（2 处空白 + 4 处分支包装）。
> 这一点值得留意：lead 的自述是「命令与路径逐字相同」。**若将来有人按「文本逐字」做审计（如 diff 断言），会得出相反结论**，故我按实测口径记录。

### A6 —— `darwin_target_for` 的 marker 顺序有无歧义？ → **真实资产名无歧义；marker 集合自身无子串包含关系**

**（a）自动枚举 marker 两两包含关系**：`universal / x86_64 / amd64 / x64 / aarch64 / arm64` 六者**两两互不为子串**（脚本输出无告警）✅ —— `x64` 虽是 `x86_64` 的**子串**，但方向相反（`x64 ⊄ x86_64` 的匹配受「先列先中」顺序保护，见下）。

**（b）真实 CI 产出的两个名字**：

```text
dsh dock_aarch64.app.tar.gz  -> darwin-aarch64
dsh dock_x86_64.app.tar.gz   -> darwin-x86_64
```

互不误判 ✅

**（c）合成「同时含两个 marker」的名字（对抗）**：

```text
dsh dock_aarch64_x86_64.app.tar.gz  -> darwin-x86_64   ← 顺序：x86_64 在 aarch64 之前
dsh dock_x86_64_aarch64.app.tar.gz  -> darwin-x86_64
dsh dock_universal_arm64.app.tar.gz -> darwin-universal ← universal 优先，符合注释
dsh dock_amd64_arm64.app.tar.gz     -> darwin-x86_64
```

⇒ **确实存在「先列先中」的顺序依赖**（`_DARWIN_ARCH_MARKERS` 的声明顺序），但：
- **代码注释已显式声明顺序敏感**（`# 顺序敏感：universal 是特例要先判`）；
- **CI 实际产生的名字恒为单一 marker**（由 `asset_arch` 决定），故**现实不可达**；
- **`universal` 优先于其它 marker 是正确方向**（避免把 universal 包误判成单架构）。
**判定**：**无实际歧义**，顺序语义已文档化 ✅ 但**记录为潜在脆弱点**：若将来 CI 产出名同时含两 marker，结果由顺序决定而非报错——建议（非阻塞）在 `darwin_target_for` 里对「命中多个互斥架构 marker」返回 `None` 交由完整性检查拦下，即把隐式顺序升级为显式失败。

## 5. N3 的量化证据（体积机制）
