## 1. 缺陷（ADR-0018 §1，本次独立复核）

dsh 启动时在 `$DSH_HOME/profiles/node_modules` 建模块 fallback 条目：普通 node 模式下用
**`fs.symlinkSync`**（Windows 普通账户 ⇒ `EPERM: EPERM, syscall: 'symlink'`）。

**独立复核了 ADR 引用的全部源码锚点**（真实 `@deepseek-ai/dsh@0.1.5-rc.2` 安装树）：

| 事实 | 复核结果 |
|:---|:---|
| 判据函数 | `dsh-app-boot/lib/index.js:485` `function isPackagedExecutable() { return process.pkg !== void 0; }` |
| 调用点 | 同文件 `:612` `entries: !isPackagedExecutable() ? […` —— **全文件仅 1 处调用** |
| 分支 | `:613 kind: "symlink"`（非打包） / `:619 kind: "proxy"`（打包） |
| dsh 入口 | `dsh/lib/bin.js:141 async function runCli()` · `:168 if (import.meta.main) await runCli();` · `:170 export { runCli };` |

⇒ ADR §1 的描述与**真实安装树逐条吻合**（含「必须显式调 `runCli()`」的理由：`:168` 被
`import.meta.main` 把守，被 import 时为假）。

## 2. 实现（`engines.rs`，唯一改动文件）

### 2.1 bootstrap（`dsh_bootstrap_mjs()` 纯函数 → `write_dsh_bootstrap()` 幂等落位）

三步（ADR §4.1，逐条对齐）：

```js
process.pkg ??= { dshDock: true };                        // ① 选中 proxy 分支
const entry = new URL(
  "../dsh-runtime/node_modules/@deepseek-ai/dsh/lib/bin.js",
  import.meta.url,                                        // ② 相对 bootstrap 自身解析
);
const mod = await import(entry.href);
await mod.runCli();                                       // ③ 必须显式调用
```

**绊线**（ADR §6「失败要响亮」）：

```js
if (err?.code === "EPERM" && err?.syscall === "symlink") {
  console.error("[dsh-dock] … dsh 判断打包体的内部依据（process.pkg）可能已变更——见 ADR-0018 §5 …");
  process.exit(1);
}
throw err;                                                // 其余错误原样上抛
```

### 2.2 Windows shim

```diff
-rem DSH Dock engine launcher (ADR-0017: shell-owned shim, not the pnpm global shim).
-"%~dp0node.exe" "%~dp0..\dsh-runtime\node_modules\@deepseek-ai\dsh\lib\bin.js" %*
+rem DSH Dock engine launcher (ADR-0018: bootstrap selects dsh's module-proxy mode).
+"%~dp0node.exe" "%~dp0dsh-boot.mjs" %*
```

CRLF / 纯 ASCII / `%~dp0` 相对 / `%*` 透传**全部保留**。

### 2.3 POSIX shim：**逐字不动**（ADR §4.2）

`dsh_shim_posix()` **零改动**；POSIX 仍直连 dsh 入口 ⇒ dsh 在 POSIX 走**默认符号链接模式**
（那里无特权问题，改了只会白 churn 481 个链接并偏离上游默认）。

### 2.4 bootstrap **两平台都落位**（一个有意的取舍，如实说明）

`ensure_dsh_runtime_layout` 无条件写 `dsh-boot.mjs`。理由：
① POSIX 侧无消费者，但它只是一份惰性文本，**不改变 POSIX 的启动路径**（分叉面未扩大）；
② 两平台一致落位使落位逻辑**无平台分支、可被本机单测覆盖**——若只在 `cfg!(windows)` 下写，
   macOS 上该函数无调用者 ⇒ `dead_code` 撞 `-D warnings`（本仓纪律）。
若 reviewer 认为「不用的文件不该落」，改为 `cfg!(windows)` 需同时接受 macOS 上无法单测该路径。

### 2.5 测试契约变更（**我是**改了既有断言，如实记录）

ADR-0017 的两条断言（`windows_shim_shape_is_exact` /
`both_platform_shims_target_the_same_relative_entry`）原断言「Windows shim 指向 dsh 入口」——
ADR-0018 **改变了这个契约**，故同步更新：
- `windows_shim_shape_is_exact`：目标改断 `"%~dp0dsh-boot.mjs"`（CRLF/ASCII/`%~dp0`/`%*` 原样保留）；
- 后者**更名**为 `both_platform_paths_target_the_same_relative_entry`，原意图（两平台最终
  **到达同一入口**）在新形态下重新表达：POSIX 直连入口，Windows 经 bootstrap 到达同一入口。

⇒ **不是因为断言红就删断言**，是契约变了、断言跟着变，且原意图被保留。

## 3. 核心判据：真实 dsh 以 bootstrap boot ⇒ `profiles/node_modules` 零软链（**实测**）

ADR §6 称这是「实现无关、直接验结果」的核心判据。**做了两次**：

### 3.1 手工 spike（实现**之前**做的，先拿到两态对照）

用真实 `@deepseek-ai/dsh@0.1.5-rc.2`，各自独立临时 `DSH_HOME`：

| 启动方式 | `profiles/node_modules` 软链 | 代理 `entry-*.js` | 结果 |
|:---|:---:|:---:|:---|
| **普通 node**（不置 `process.pkg`） | **481** | 0 | 起（`dsh web: http://127.0.0.1:3080/?token=…`） |
| **bootstrap**（置 `process.pkg`） | **0** | **1184** | 起（同上） |

⇒ **与 ADR §1 实验表的数字逐项一致**（481/0 与 0/1184）。这是本任务最强的证据：
**同一 dsh、同一布局，仅差 `process.pkg` 一个变量，结果从 481 软链变成 0**。

### 3.2 落成 `#[ignore]` 测试（用**生产函数**，可重复）

`engines::tests::real_dsh_boots_in_proxy_mode`：
- 用 `write_dsh_bootstrap()`（**生产函数，不是手抄副本**）落位；
- 自建临时引擎目录（真实 dsh 包 + 真实引擎 node 软链）；
- 临时 `DSH_HOME` ⇒ 调 bootstrap boot ⇒ 等**铺设稳定**（连续两次采样不再增长）后断言。

**实测输出**：

```
真实 dsh boot：软链=0 顶层条目=184 代理 entry-*.js=1184 进程存活=true
test result: ok. 1 passed
```

⇒ **软链 0 / 代理 1184 / 进程存活**，与 ADR 的 proxy 数字完全一致。

**隔离性（AGENTS §6）**：全程用临时 `DSH_HOME` + 临时引擎目录；**用户真实 `~/.dsh`
未被触碰**（实测其 `profiles/node_modules` 目录 mtime 仍为 9-11 11:32，早于本次运行）。

**判据强度**：断言落在**真实文件系统结果**（软链计数 + 代理文件存在），而非文本——
`#[ignore]` 是因为需要本机已装引擎，与 `lifecycle::tests::real_dsh_is_reaped_when_shell_is_sigkilled`
同一口径；运行方式写在测试文档注释里。

## 6. 未决 / 风险

1. **Windows 真机未验**（用户已裁定搁置）⇒ 口径「机制级修复 + 单元/契约级验证，**真机待复验**」。
   真机判据（ADR §6）：`%USERPROFILE%\.dsh\profiles\node_modules` 下**无符号链接**、本地模式能进工作台。
   本机证据止于 macOS 上的**两态实测**（软链 481→0）——**平台机制不同**（macOS 无该特权限制），
   故「macOS 上 0 软链」**不能替代** Windows 真机验证。
2. **依赖 dsh 未公开内部判据 `process.pkg`**（ADR §5 已登记）：今日该判据 1 处调用、
   语义单一；上游变更时由**绊线**报出而不是静默退化。但绊线只在**我们这条启动路径**上生效——
   若 dsh 改在别处建链接（不走 `ensureSymlink`），绊线不会触发。
3. **proxy 与 symlink 的条目集合不完全相同**（ADR §5 第 2 条，如实登记）：proxy 只为
   「可解析出入口」的包建代理，既无 `exports` 也无 `main` 的包会被跳过。判定可接受
   （dsh 官方打包形态下同样如此）。
4. **`dsh-boot.mjs` 在 POSIX 上是惰性文件**（§2.4）：不影响 POSIX 启动路径，但确实是一份
   未被引用的落盘物。若 reviewer 要求「不落无用文件」，需接受 macOS 上该路径无法单测。
5. **上游报告**：ADR §5.1 要求的 upstream issue 草稿已在
   `docs/team/ADR0018-上游缺陷报告草稿.md`（**非本任务产物**，我未改动）。
6. **本机无 `dsh-runtime` 新布局**：核心判据是靠临时构造的引擎目录 + 真实 dsh 包完成的；
   ADR-0017 的 `install_dsh_project_local` 真机安装路径**未在本次一并复验**（属 ADR-0017 范围）。

# 追加：task-61 / T-B6 —— 绑定 `DSH_BOOTSTRAP_NAME` 与 Windows shim 目标（M4 收口）

> 来源：qa-verify task-60 的**自创变异 M4**。发 v1.2.3 给用户做 Windows 真机复验前的最后一收口。
> 改动文件：`src-tauri/src/engines.rs`（本文件追加）。

## A1. 缺陷（独立复现，**改前**）

`DSH_BOOTSTRAP_NAME`（写文件用）与 `dsh_shim_windows()` 里**硬编码的字面量** `%~dp0dsh-boot.mjs`
（shim 指向的目标）之间**没有任何绑定**。

**复现（改动前）**：把常量值改为 `dsh-boot-2.mjs`、shim 字面量不动 ⇒

```
$ cargo test
test result: ok. 408 passed; 0 failed; 4 ignored     ← exit 0，完全静默
```

⇒ **缺陷证实**。后果：壳写出 `dsh-boot-2.mjs`，而 `dsh.cmd` 仍指 `dsh-boot.mjs`
⇒ Windows 上 dsh 指向不存在的文件、启动失败，**而全套测试静默**。

## A2. 修法：**构造上单一来源**（首选方案，未退化为断言绑定）

`DSH_BOOTSTRAP_NAME` 提到 `dsh_shim_windows` 之前，函数返回类型由 `&'static str` 改为 `String`，
目标名经 `format!` 取用：

```rust
pub(crate) const DSH_BOOTSTRAP_NAME: &str = "dsh-boot.mjs";

pub(crate) fn dsh_shim_windows() -> String {
    format!(
        "@echo off\r\n\
         rem DSH Dock engine launcher (ADR-0018: bootstrap selects dsh's module-proxy mode).\r\n\
         \"%~dp0node.exe\" \"%~dp0{DSH_BOOTSTRAP_NAME}\" %*\r\n"
    )
}
```

⇒ **「shim 指向的文件」与「壳实际写出的文件」不可能不一致**——不是靠断言事后发现。

**为何没有用退路**（task-61 允许的 `format!` 绑定）：`&'static str` 只是原来的便利返回类型，
改成 `String` 的代价仅为 2 处调用点（`write_dsh_shim` 的 `.as_bytes()`、测试里的绑定），
**没有任何理由退化为"并列字面量 + 断言绑定"**。
**原有意图全部保留**（未"改红了就删"）：CRLF / 纯 ASCII / `%~dp0node.exe` / `%*` 四项断言逐条仍在。

## A3. 新增 2 条断言（不只是"经常量断言"，而是**端到端解析 + 落盘核对**）

| 断言 | 判据形态 |
|:---|:---|
| `windows_shim_target_is_the_file_we_actually_write` | ① 目标名经常量在构造上生成；② **从 shim 文本里解析**出目标名（不读常量）→ 断言该名对应的文件**确实被落位**；失败时打印**实际落盘文件名列表** |
| `windows_shim_target_parser_follows_the_name` | 解析器自检：换任意名字也必须解析正确（防"解析器只认写死的一个名字"） |

**为什么从 shim 文本解析而不是直接读常量**：断言的对象必须是**shim 真正指向的东西**，
而不是我们以为它指向的东西。这样任何一侧divergence 都会被抓到（见 A4 双向证伪）。

## A4. 变异证伪（逐案单跑 + 哈希自证 + byte-exact 复原 + 残留 0）

| # | 变异 | 时期 | 期望 | 实测 |
|:--|:---|:---|:---|:---|
| **M4（原始）** | 只改常量值，shim 字面量不动 | 修复**前** | 全绿（缺陷存在） | ✅ **408 passed / exit 0** —— 静默 |
| **A4-1** | 修复**后**再改常量值 | 修复后 | 响（改名不再静默） | ✅ **3 failed**（见下"诚实说明"） |
| **A4-2（M4′）** | shim 侧重新硬编码**与常量不一致**的名字 | 修复后 | 绑定断言红 | ✅ 红（`engines.rs:2542`「shim 目标必须由 DSH_BOOTSTRAP_NAME 生成」） |
| **A4-3（M4″）** | **写**侧落到别的名字（shim 仍指常量名）= **qa-verify 描述的原始后果形态** | 修复后 | 绑定断言红 | ✅ 红（`engines.rs:2558`「Windows shim 指向 `dsh-boot.mjs`，但该文件并未被落位（实际落盘：`["dsh","dsh-boot-written.mjs"]`）」） |

### ⚠️ 诚实说明：修复后"改名 ⇒ 红"的 3 条红，**不是**新绑定断言抓的

`A4-1` 的 3 条红来自**改动前就已存在**的字面量断言：
`windows_shim_shape_is_exact`（`:1990`）· `windows_shim_points_at_bootstrap_not_entry`（`:2211`）·
`both_platform_paths_target_the_same_relative_entry`（`:2021`）——它们各自钉着 `dsh-boot.mjs` 字面量。

**这 3 条是"改名要响"的信号，不是"desync 被抓"的信号**；真正抓 desync 的是新的绑定断言
（A4-2/A4-3 已双向证伪）。task-61 的验收口径「改后应红」由这两组共同满足，但**归因必须分清**——
否则会误以为新断言在抓改名（它其实是派生式、改名后仍绿）。

**是否要把这 3 条也改成派生式**（让改名静默）？**保留现状**，理由：
① bootstrap 文件名被 **ADR-0018 §4.1 明文写出**，改名属"应被察觉的契约文本变更"，响是合理的；
② 3 条断言各自还钉着 CRLF / ASCII / `%~dp0node.exe` / `%*` 等**与名字无关**的意图（task-61 §"不要改红了就删"）；
③ 它们构成改名的第二重响铃，成本仅为"改名时需同步更新期望值"。
