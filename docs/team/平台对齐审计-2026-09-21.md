# 平台对齐审计（2026-09-21）—— 依据 `AGENTS.md` §0 红线 3

> **触发**：维护者 2026-09-21 指令「根据最新的宪法，检查一下哪些功能没有多平台对齐」。
> **判据**：红线 3 —— 适配目标 = **macOS（arm64 / x86_64）· Windows（x64，含 WSL2 客体模式）· Linux（x64）**；
> **只要技术允许就必须都适配**；确有技术不可能 → 该面**显式报错并说明原因**（禁静默降级、禁假实现）；
> 收窄矩阵须**维护者裁定 + ADR**。
> **证据口径**：代码给 `文件:行号`，依赖能力核对到 **crate 源码**（不引二手结论）；
> 每条标注 **【已核实】**（本人读码 / 读 crate 源确认）或 **【静态推断】**（源码链推得、**未真机验证**）。
> **没有证据的一律写「未确认」**。

## 0. 判定分类

| 类 | 含义 | 处理 |
|:--|:--|:--|
| **A｜真缺口** | 技术上可做（有对应 OS 原语 / 同一 API / 现成原语），却只做了单平台或单模式；或**静默降级** | 按红线 3 **应当补齐**，除非另有裁定 |
| **B｜正当差异** | 平台原生语义不可搬（键位、红绿灯、WSL 机制本身），且**已显式说明** | 保持；不得退化为静默降级 |
| **C｜待裁定** | 产品取舍 / 需真机验证才能定方案 | 需维护者拍板 |

## 0.5 方法与边界（诚实声明）

- **扫描口径**：`src-tauri/src` 平台条件编译分叉（**402 行**原始命中：生产 208 / 测试 160 / 纯注释 34；按 `#[cfg|cfg!(`+`env::consts::OS` 计），归并为 **24 个功能面**；前端 `frontend/src` + `frontend/injected` 的**全部**平台语义使用点（只有 6 个文件触碰）。
- **信号**：全仓 `cfg(target_os = "linux")` = **0 处**（`cfg(windows)` 121 · `cfg(unix)` 96 · `cfg(target_os="macos")` 15）。**Linux 从来没有专属分支**——它的行为全部落在 `cfg(not(macos))` 与 `cfg(unix)` 的"顺带覆盖"里。这既是它现状良好的原因（复用 unix 实现），也是下面 A1 这类"没人替 Linux 想过"的根因。
- **方法**：分叉按功能面聚类 → 逐簇问「是否导致某平台缺一个用户可感能力 / 是否静默降级」→ 存疑处回 **crate 源码**核对（tauri 2.11.5 / tauri-utils 2.9.3 / tauri-runtime-wry 2.11.4 / tauri-bundler 2.9.4 / libappindicator-sys 0.9.0，本地 registry 实读）。
- **边界**：本档是**静态证据审计**，不含真机运行 —— 而"Linux 从未有人运行过"正是 §7 登记的缺口。凡结论依赖运行时行为者，均标【静态推断】。
- **本轮修正了两处首版误判**（见 §6.1、§5）：前端 typecheck **不是** Linux-only；Linux 托盘**不是**"已就位"。

## 2. A｜真缺口

### 2.1 【最严重】Linux 缺 `libayatana-appindicator3` ⇒ 托盘初始化 **panic** ⇒ 启动即崩

**【已核实】** 三条证据链：

1. **crate 层就是 panic**：`libappindicator-sys-0.9.0/src/lib.rs:14,19,31,36` 用 `libloading` **dlopen** 尝试四个名字，全失败即 `:41,50` `panic!(...)`。
2. **调用链**：`tauri` tray → `tray-icon` 的 gtk 实现 `AppIndicator::new` → `libappindicator_sys::LIB`（`Lazy`）⇒ **首次建托盘即 panic**。`Cargo.toml:65` 的 release `panic = "abort"` 让它直接 abort —— `src-tauri/src/lib.rs:253-256` 的 `if let Err(e) = … { warn! }` **拦不住 panic**（注释承诺的"降级 warn 不阻断启动"在"缺库"这条路径上不成立；它只覆盖"无 dbus 会话/无 StatusNotifier 宿主"，见 ADR-0007）。
3. **包没声明依赖**：因为是 **dlopen**，二进制里**没有 DT_NEEDED** ⇒ ① `tauri.conf.json` 的 `bundle` 段键为 `active/targets/createUpdaterArtifacts/icon/resources/macOS/windows`——**没有 `linux` 块**（【已核实】），故 deb `Depends` / rpm `requires` 为空；② AppImage 打包（linuxdeploy）也不会把它带进去。
4. **CI 永不触发**：`.github/workflows/build.yml:157,537` 与 `boot-smoke.yml:327` 都 `apt-get install libayatana-appindicator3-dev` —— 装了库，绿灯恒亮。

**为什么这最严重**：它是**唯一一条"用户什么都看不到、应用起不来"**的缺口，且恰好落在最没有人真机验过的平台（§7）。发行版默认装 appindicator 的很多（GNOME 系通常带），但**最小安装 / 非 GNOME 桌面 / 精简容器**会缺。

**补齐（两步，都小）**：
- 声明依赖：`tauri.conf.json` 加 `bundle.linux.deb.depends: ["libayatana-appindicator3-1"]` 与 rpm 对应项；AppImage 一并落库。
- 代码侧**前置探测**（在 `panic = "abort"` 下 `catch_unwind` 无效）：建托盘前用 `libloading::Library::new("libayatana-appindicator3.so.1")` 试加载，失败 → 跳过托盘 + **可见提示**（不是 panic、也不是只写 warn）。

### 2.2 Windows 登记表孤儿清扫的第二层防线**结构性失效**【静态推断】

**【已核实】结构**（`src-tauri/src/lifecycle.rs`）：

- 非 unix 的 `attach` 是**空实现**（`:551-558`，注释自陈"std 无 `pass_fds` 等价物"）——子进程**不持有**登记锁；
- 父进程在 spawn 后立刻 `drop(reg)`（`:436-440`），注释写明"父持有会让判据恒为真"；
- 判据是 `try_lock` 结果：`Ok(()) => RegistrationVerdict::Stale`（`:721`）。

⇒ 在 Windows 上**没有任何进程持有那把锁** ⇒ 清扫恒判 `Stale` ⇒ 对"仍活着的孤儿"只会**删登记、不杀进程**（`:766`）。
**测试也印证**：三条涉及"活孤儿持锁"的用例全带 `#[cfg(unix)]`（`:1249/1282/1320/1343`），Windows 上唯一跑的那条正是 `sweep_deletes_stale_registration_without_killing_anything`。
**后果放大项**：Job Object 的三层失败只 `warn`（`:301/313/340`）——那正是登记表要兜的"job 赋值失败"降级路径；此时 Windows 硬杀收口**两层全失**，而 `:554-557` 的注释宣称第二层有效（**注释不实**）。

**【静态推断】**：未在 Windows 真机复现（§7 的真机验证现为搁置状态）。
**补齐**：`DuplicateHandle` + `STARTUPINFOEX`/`HANDLE_LIST`（`windows-sys`）让子进程真正继承锁句柄；或至少把"降级"做成用户可见，并把注释改成事实。

### 2.3 WSL 客体档 5 项未下沉（Windows 内部的模式不对称）

红线 3 明写适配目标是「Windows（x64，**含 WSL2 客体模式**）」；同一个 Windows 用户在两种模式下拿到不同能力，是**最大的一簇**：

| # | 能力 | 显式报错位置 ✓ | 文案自称原因 | 原语现状（实际） | 判定 |
|:--|:--|:--|:--|:--|:--|
| 1 | `list_experimental_capabilities` | `src-tauri/src/commands/plugin.rs:229` | 需补客体侧 **profile 读**原语 | **已有** `guest::read_files`，`plugins.rs:92` 已在客体档用它读清单 | **A** |
| 2 | `apply_official_patch_row` | `commands/plugin.rs:83` | 需补客体侧 **patch 写**原语 | **已有** `guest::write_home_files` + `backup_file`；`mcp.rs:1334-1335` 已在客体档写 patch | **A** |
| 3 | `remove_official_patch_row` | `commands/plugin.rs:162` | 同 2 | 同 2（反向 + 回读自证） | **A** |
| 4 | `probe_mcp_server` | `commands/console.rs:262` | 需在客体内部 spawn 服务器命令 | 机制在：`executor.rs:1216` 已有客体侧 stdin 管道投递 + 命令执行 | **A** |
| 5 | 安全模式（进入/横幅/退出） | `commands/boot.rs:268` | 需补客体侧 patch 写原语 | 同 2 | **A** |

**关键判据**：5 项**没有一项是"技术不可能"**——文案自己写的是"需补客体侧 X 原语**后方可启用**"，而 `guest.rs` 的 `read_files` / `write_home_files` / `backup_file` / `dsh_cli_script` / `list_dir` **已在用**（profile 全生命周期已下沉，`commands/profile.rs:31-271`）⇒ **实现债**。
**必须保留**：5 处错误文案都给了**可行动替代路径**且**绝不回落宿主**（改错 profile 比报错严重）——补齐时留作兜底，不得为"看起来支持"而静默降级。

### 2.4 凭据文件的 `0600` 加固在 Windows 上**静默不生效**

**【已核实】** `credentials.rs:290-299` 把权限收紧整段包在 `#[cfg(unix)]`；Windows 分支**不存在**（全仓搜 `icacls`/ACL 加固零命中）。
**而文档无条件下承诺**：`README.md:183`「保存时**强制 0600 文件权限**」· `README.md:215`「凭据以 **0600 权限**仅存本机」· `AGENTS.md` §6「`.credentials.yaml` 保持 **0600**」。
**反差**：客体侧**反而**有 `chmod 600`（`guest.rs:254`）——即"Windows 宿主不如它管的 WSL 客体"。
**判定 A**（红线 3 明禁的静默降级）。**风险量级不夸大**：Windows 上文件落在 `%USERPROFILE%\.dsh\`，NTFS 默认继承 profile ACL（通常仅本人 + SYSTEM/Administrators），**不是** Unix 0644 那种"同机他人可读"；但**不保证**如此，而文档写成了强保证。
**二选一**：① Windows 侧显式设 DACL（`icacls` / `SetNamedSecurityInfoW`）；② 三处文档改为"Unix 严格 0600；Windows 依赖 profile 默认 ACL"。

### 2.5 日志台：**读错世界** + `dsh` 源指向无人写入的文件

**【已核实】** 三处叠加：

1. `commands/console.rs:53 get_app_logs` 是 `console.rs` 里**唯一没有** `mgmt::current_world` 分发的命令（`:37/:69/:85/…/:221` 全部有），直接 `crate::resolve::user_dsh_home()` ⇒ **WSL 客体档下读宿主世界日志**；这与 `docs/adr/0016` 的"控制台 100% 支持 WSL 客体模式"声明**冲突**（文档与代码不符）。
2. `diagnostics.rs` 的 `"dsh" => app_data.join("dsh.log")`：**全仓无人写入该文件**（真实日志是 `shell.rs:72` 的 `dsh-shell.log` 与 `executor.rs:807` 的 `dsh-wsl.log`）⇒ 该 tab 恒"暂未生成"（**三平台一致**）。
3. `diagnostics.rs` 用严格 UTF-8 `read_to_string`，**未走**已存在的 `resolve::read_log_auto`（UTF-16LE 探测）⇒ Windows 客体档（`wsl.exe` 重定向输出恰是 UTF-16LE）**必然读失败**。

**判定 A**：①是"读错世界"（静默给错结果，比报错更坏），②③让日志台整块失效。
**补齐**：`read_app_logs` 加 World 分发（照抄 `console.rs:37` 模式）+ 源改指两个真实日志 + 解码换 `resolve::read_log_auto`。

### 2.6 `render-product.sh` 的快照档在 Windows 上把 `node.exe` 落成无扩展名文件

**【已核实】** `scripts/render-product.sh:56` `cp -f "$NODE_BIN" "$snap/node/bin/dsh-node"`，`:78` manifest 同名字面量 `"nodeBin": "dsh-snapshot/node/bin/dsh-node"`，**脚本无任何平台分支**。
Windows 上 `$NODE_BIN` = `node.exe` ⇒ 落成名为 `dsh-node` 的文件（无 `.exe`）⇒ `shell.rs:50` 的 `is_file()` 通过，但 `shell.rs:58` 经 `child_cmd` 走 CreateProcess（无扩展名时自动追加 `.exe`）⇒ **找不到 ⇒ 错误卡**。
`docs/contract.md:19,27-28` 明写三平台各自注入自己的 Node（`node` / `node.exe`），脚本用法行也这么写 ⇒ **契约说三平台，脚本只做了一平台**。
**为什么 CI 不拦**：全仓 **CI 零引用** `render-product.sh`（它是装配方/打包期脚本）。
**【静态推断】**：`CreateProcess` 的扩展名追加行为未在 Windows 实机复现。
**补齐**：按平台落 `dsh-node.exe` 并同步 manifest 的 `nodeBin`。

### 2.7 "运行期取哪份 pnpm" 与 "CI 取哪份" 之间**没有交叉闸门**

**【已核实】** 两个独立真相源：

- 运行期求名：`updates.rs:1055-1074`（`cfg!(target_os)` + `cfg!(target_arch)` → `darwin-arm64` / `darwin-x64` / `win32-x64` / `linux-x64` …）；
- CI 取份：`build.yml:60/67/183` 由 **matrix 键**决定（`pnpm_platform: darwin-arm64` / `darwin-x64`）。

现有机器闸门（`scripts/tests/test_release_platform_matrix.py:76-86`）只断言「`engine_pnpm_bundle` 函数体内**全部字面量集合** ⊆ 白名单」——**把 `darwin-arm64` 与 `darwin-x64` 两个字面量互换，测试仍全绿**，而 Intel 包真机引导会去找错名（`tar -xzf` 失败，`engines.rs:651-660`，会响亮报错但**只在用户机器上**）。
**补齐（<20 行）**：`build.rs` 用 `CARGO_CFG_TARGET_OS` / `CARGO_CFG_TARGET_ARCH` 断言"本目标对应的 `<platform>.tgz` 确实在 `resources/pnpm/` 里"⇒ 把两个真相源钉在一起，**编译期**即红。

### 2.8 macOS Intel leg **一个断言都不执行**；macOS 无 boot 冒烟

**【已核实】** `build.yml:204` 的 `cargo test` 受 `if: matrix.native_arch` 限制；`macos-latest-x86_64` 的 `native_arch: false` ⇒ 走 `:217` 的 `cargo test --no-run --target x86_64-apple-darwin`（只编译）。
我首版判它 B（"Rosetta 不保证预装"是合理理由）；**改判 A**：`target_arch` 分叉确有 4 处（`updates.rs:1057/1063/1068` + `engines.rs:1739`），其 x86_64 分支**只有 clippy 编译**、从未执行；再叠加 `boot-smoke.yml` **无 macOS 作业**（仅 Windows / Win+WSL2 / Linux-xvfb，且 `workflow_dispatch` 手动触发）⇒ **Intel 架构在整条链上没有任何执行级验证**。
**补齐**：`macos-15-intel` 原生 leg（可用性未确认）或 Rosetta 跑测试。

### 2.9 WSL 档安全模式读宿主 home（低危）

**【已核实】** `executor.rs:107-110/361-363`（只有 Local 档覆写 `dsh_home`）+ `boot.rs:348` + `commands/boot.rs:150-151`（回落 `user_dsh_home()`）⇒ 客体档**静默读宿主世界**的安全模式记账（写入侧 `:264-271` 已显式拒绝）。形态违 ADR-0016 §2.6；影响低（只是横幅数字可能不对），但属"读错世界"这一类。

### 2.10 附：`mgmt.rs` 的 P0 兜底已成死码

`mgmt.rs:76 unsupported_in_wsl()` 与 `:102 require_local()` 均 `#[allow(dead_code)]` 且**全仓零调用点**（40 个 IPC 命令已逐条 world-aware；`unarchive_session` 是有意世界无关并写明理由）。唯一引用是 `frontend/src/__tests__/profiles.test.ts:109` **逐字复制**的文案 ⇒ 测试守着一句用户永不看到的话。

## 3. C｜待裁定

### 3.1 Windows/Linux 的沉浸式窗口：只做了"无等价物"的那半

**【已核实】crate 源码**：

| 事实 | 出处 |
|:--|:--|
| `TitleBarStyle` 文档首行 = "…displayed **on macOS**"；`title_bar_style` / `hidden_title` 在 tauri 里就是 `#[cfg(target_os = "macos")]` | `tauri-utils-2.9.3/src/lib.rs:161`；`tauri-2.11.5/src/window/mod.rs:766,787` |

### 3.2 Windows 的平台标记（`data-windows-titlebar`）
`immersiveChrome.ts:37-43` 现非 macOS 一律返回 `null`；而 dsh 官方另有 `html[data-windows-titlebar]` 一套桌面 CSS（**属性选择器**，可直接 `toggleAttribute`）。与 3.1 一并做；单独做有布局风险（在原生装饰下是否成立未验证）⇒ C。

### 3.3 架构维度（ARM64）
红线 3 现文写 x64。`win32-arm64` 在代码侧已备（`updates.rs:1063-1069` + pnpm 白名单 + G3 回归闸门），Linux ARM64 未提及。README:251 已**显式说明** Windows ARM64 经仿真运行、其余架构可自行构建（**非静默**）⇒ 现状态符合红线 3 的"不静默"要求；是否扩到 arm64 矩阵需维护者裁定。

### 3.4 「托盘常驻 / 最小化运行」**名不副实**（三平台一致）
**【已核实】** 全仓无 `ExitRequested` / `prevent_exit` / `prevent_close`（零命中）。按 `tauri-runtime-wry-2.11.4` 的行为：最后一个窗口 Destroyed → `ExitRequested` → 无人拦 → 退出 ⇒ **关主窗 = 应用退出，托盘一并消失**，与 `ui.rs:432` 注释「托盘常驻：窗口可关，任务台仍在」、`README.md:59,216` 的"托盘常驻 / 最小化运行"**不符**。
**补齐**：`RunEvent::ExitRequested => api.prevent_exit()` + `WindowEvent::CloseRequested` 里 `hide()`；macOS 无托盘需另行裁定（Dock 点击恢复或改文案）。

### 3.5 「全局快捷键」文案与实现不符（三平台一致）
**【已核实】** 无 `tauri-plugin-global-shortcut`、`tao` 未启 `global_shortcut`；实际是**页内** `keydown`（主窗注入脚本 `switcher.js:12-34` + 控制中心 React `QuickDshSwitcher.tsx:75-91`）。而文案写"**全局**快捷键"（`frontend/src/content/zh-CN.ts:1048`、`docs/RELEASE_NOTES.md:359`、`ui.rs:39` 注释），计划文档自己承认非 OS 级。窗口失焦即失效且**无提示**。ADR-0024 已裁"暂缓" ⇒ 二选一：改文案，或落插件 + 注册失败显式提示。

### 3.6 Linux 无托盘宿主时，About / 客户端更新入口不可达，而能力矩阵恒 `true`
**【已核实】** `lib.rs:253-256` 只 `warn`；`lib.rs:355` 是唯一 About 入口（`open_about` IPC 已删，`frontend/src/lib/tauri.ts:6`）；而 `frontend/src/lib/host.ts:63` 恒 `clientUpdate: true`（"壳客户端自更新与宿主无关，恒可用"）。在无 StatusNotifier 宿主的 Linux 桌面上（i3/sway 等）⇒ **用户既看不到更新、也打不开关于**。ADR-0007 曾判"可接受"，建议复核。

### 3.7 Windows 无 Authenticode 签名（成本裁定）+ README 缺 Windows 提示
macOS 侧 5 个 secret 全量校验、缺一即硬失败（`build.yml:265-291`）；Windows 侧全仓搜 `signtool`/证书 secret **零命中** ⇒ SmartScreen「未知发布者」。技术可做（Tauri `windows.certificateThumbprint`），卡证书采购 ⇒ C；**披露不对称**：README 有 macOS Gatekeeper 提示（`:257`），无 Windows 侧 ⇒ 零成本可补。
**更新链安全不受影响**：updater 用 Tauri 自己的 minisign `.sig`，**三平台都产**（含 deb/rpm/AppImage/msi/nsis/app.tar.gz）。

### 3.8 Linux 独有的悬空签名资产
`build.yml:498-506` Linux 只传 `**/*.sig`，而 macOS/Windows 的压缩 updater 资产随包上传 ⇒ Release 里留下没有对应资产的 `…AppImage.tar.gz.sig`（功能可用：feed 指原始 `.AppImage`，插件有 raw 分支）。零成本收敛：一并传 tar.gz 或过滤孤立签名。

### 3.9 Windows 包"必须含两份 tgz"未被闸门校验
`build.yml:181-183` Windows leg 固定取 `win32-x64 linux-x64`（第二份供 WSL 客体）；而闸门只查「leg 声明的份 ⊆ 白名单」，**不查 leg 是否取全** ⇒ 改成只取一份仍全绿，直到用户切 WSL 才炸（boot-smoke 的 WSL 作业能抓，但需手动触发）。可加一条 `leg → 必需份` 的映射断言。

### 3.10 三平台**一致缺失**的功能（非不对称，故不违红线 3，但登记备查）
开机自启（无 `tauri-plugin-autostart`）· 系统通知（无 notification 插件，只有应用内 `UpdateBanner`）· 深链接（无 `tauri-plugin-deep-link`/`urlSchemes`）· 文件选择器（无 dialog 插件）· 窗口大小/位置记忆（无 `window-state`，每窗 `.center()`）· 置顶 · 透明。

## 9. 与红线 3 的关系（结论）

- **"显式说明"这一条，仓库做得很好**：16 处 WSL 错误站位、WSL1 / Alpine 显式拒绝、所有已知差异都有可行动文案——**例外是 A2（注释不实）、A4（承诺与实现不符）、A5（读错世界）**，这三处正是红线 3 用"禁静默降级、禁假实现"点名要防的形态。
