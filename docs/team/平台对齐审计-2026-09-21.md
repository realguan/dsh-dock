# 平台对齐审计（2026-09-21）—— 依据 `AGENTS.md` §0 红线 3

> **触发**：维护者 2026-09-21 指令「根据最新的宪法，检查一下哪些功能没有多平台对齐」。
> **判据**：红线 3 —— 适配目标 = **macOS（arm64 / x86_64）· Windows（x64，含 WSL2 客体模式）· Linux（x64）**；
> **只要技术允许就必须都适配**；确有技术不可能 → 该面**显式报错并说明原因**（禁静默降级、禁假实现）；
> 收窄矩阵须**维护者裁定 + ADR**。
> **证据口径**：代码给 `文件:行号`，依赖能力核对到 **crate 源码**（不引二手结论）；**没有证据的一律写「未确认」**。

## 0. 判定分类

| 类 | 含义 | 处理 |
|:--|:--|:--|
| **A｜真缺口** | 技术上可做（有对应 OS 原语 / 同一 API / 现成原语），却只做了单平台或单模式 | 按红线 3 **应当补齐**，除非另有裁定 |
| **B｜正当差异** | 平台原生语义不可搬（键位、红绿灯、WSL 机制本身），且**已显式说明** | 保持；不得退化为静默降级 |
| **C｜待裁定** | 产品取舍 / 需真机验证才能定方案 | 需维护者拍板 |

## 0.5 方法与边界（诚实声明）

- **扫描口径**：`src-tauri/src` 共 **248 处**平台条件编译分叉（按文件：`guest.rs` 70 · `lifecycle.rs` 38 · `executor.rs` 33 · `engines.rs` 32 · `sessions.rs` 11 · `resolve.rs` 10 · 其余 ≤8）；前端 `frontend/src` + `frontend/injected` 的**全部**平台语义使用点。
- **判定方法**：把分叉按**功能面聚类**，逐簇问「该分支是否导致某平台缺一个用户可感能力」；有疑问的分叉回到 **crate 源码**核对（tauri 2.11.5 / tauri-utils 2.9.3 本地 registry 实读），不引二手结论。
- **已核对的"无事"簇**（两侧分支都在，属机制差异非功能缺失）：`engines.rs`（`pnpm.exe` vs `pnpm`、可执行位、成员命名）· `sessions.rs`（进程存活判定）· `resolve.rs`（PATH 分隔符、宿主解析）· `lifecycle.rs`（Job Object vs 进程组 + 生命线）· `shell.rs`（子进程与权限）· `boot.rs`（信号监护 Unix 侧，Windows 走 Job Object）· `network_gate.rs`（分叉在闸门自身的扫描逻辑，与平台功能无关）。
- **边界（未逐条列举的）**：`credentials.rs` / `plugins.rs` / `profiles.rs` / `ui.rs` / `updates.rs` 等 <8 处的分叉已按上表口径抽查，**未发现**除 §2.3、§3.1 之外的"单平台功能缺失"。
- **本审计是静态证据审计**：不含真机运行（那正是 §7 登记的缺口）。凡"技术上可做"的结论都给出了**具体 API 或现成原语**；给不出的，一律降级为 C 或标注"未确认"。

|:--|:--|:--|

**一句话回答"哪些功能没有多平台对齐"**：
真正对不齐的用户可感功能只有 **两类** —— ① **Windows 的 WSL 客体模式**下 5 项能力缺失（实验能力目录 / 官方挂载行增删 / MCP 探测 / 安全模式），② **Windows/Linux 的沉浸式窗口**（macOS 有、另两平台保持原生标题栏）。另有一项**安全承诺**在 Windows 上静默不生效（凭据 0600），以及一项**披露**缺口（Windows SmartScreen 无签名且无提示）。其余平台分叉经逐簇核对均为**正当的平台机制差异**。

## 2. A｜真缺口

### 2.1 WSL 客体档 5 项未下沉（Windows 内部的模式不对称）

`Windows（x64，含 WSL2 客体模式）` 是红线 3 明写的适配目标；**同一个 Windows 用户在"本地档 vs WSL 客体档"下拿到的功能不一样**，这是当前最大的一簇用户可感缺口。

| # | 能力 | 错误位置（显式报错 ✓） | 文案自称原因 | 原语现状（实际） | 判定 |
|:--|:--|:--|:--|:--|:--|
| 1 | `list_experimental_capabilities`（实验能力目录读） | `src-tauri/src/commands/plugin.rs:229` | 「需补客体侧 **profile 读**原语」 | **已有**：`guest::read_files`，且 `src-tauri/src/plugins.rs:92` 已在客体档用它读清单 | **A** |
| 2 | `apply_official_patch_row`（官方策展挂载行写入） | `src-tauri/src/commands/plugin.rs:83` | 「需补客体侧 **patch 写**原语」 | **已有**：`guest::write_home_files` + `guest::backup_file`；且 `src-tauri/src/mcp.rs:1334-1335` 已在客体档写 patch（含备份） | **A** |
| 3 | `remove_official_patch_row`（同上删除） | `src-tauri/src/commands/plugin.rs:162` | 同 2 | 同 2（反向：删行 + 回读自证） | **A** |
| 4 | `probe_mcp_server`（MCP 能力探测） | `src-tauri/src/commands/console.rs:262` | 「需在**客体内部 spawn 服务器命令**」 | 机制在：`src-tauri/src/executor.rs:1216` 已有客体侧 stdin 管道投递（规避 32K 命令行上限）+ 客体命令执行 | **A**（有跨子系统 stdio 语义工作量） |
| 5 | 安全模式（进入 / 横幅 / 退出） | `src-tauri/src/commands/boot.rs:268` | 「需补客体侧 patch 写原语」 | 同 2 | **A** |

**关键判据**：这 5 项**没有一项是"技术不可能"**——报错文案自己写的就是「需补客体侧 X 原语**后方可启用**」，而客体缝（`src-tauri/src/guest.rs`）里 `read_files` / `write_home_files` / `backup_file` / `dsh_cli_script` / `list_dir` 等原语**已经存在并在用**（profile 全生命周期管理已下沉，见 `src-tauri/src/commands/profile.rs:31-271`）。
⇒ 这是**实现债**，不是平台限制。红线 3 生效后不应再以「暂不支持」长期停留。

**正面样板（须保留）**：5 处的错误文案都给了**可行动替代路径**（在该发行版终端里直接跑 `dsh --profile <名> …`／切回本地模式），且**绝不回落宿主世界**（改错 profile 比报错严重）。补齐时这段"显式报错"要保留为兜底，不得为了"看起来支持"而静默降级。

### 2.2 附：`mgmt.rs` 的 P0 兜底已成死码（顺手发现，同一处代码）

`src-tauri/src/mgmt.rs:76 unsupported_in_wsl()` 与 `:102 require_local()` 都带 `#[allow(dead_code)]`，且**全仓零调用点**（现有命令改为逐条 `match current_world()` + 各自的 `World::Wsl` 分支）。
唯一引用是 `frontend/src/__tests__/profiles.test.ts:109` **逐字复制**的那句文案 —— 该测试守着一句用户永远看不到的话。
⇒ 建议二选一：接回为统一闸门，或连同前端 fixture 一并删除（避免"测试绿 ≠ 路径活"的假信心）。

### 2.3 凭据文件的 `0600` 加固在 Windows 上**静默不生效**（且文档无条件下承诺）

**代码**：`src-tauri/src/credentials.rs:291` 把权限收紧整段包在 `#[cfg(unix)]` 里；Windows 分支**不存在**——全仓搜 `icacls` / `DACL` / ACL 加固**零命中**（只有 tauri 自己的 ACL 概念，无关）。
**文档承诺**（都未限定平台）：

- `README.md:183`「保存时**强制 0600 文件权限**与原子写入」
- `README.md:215`「凭据以 **0600 权限**仅存本机 `~/.dsh`」
- `AGENTS.md:155`「`.credentials.yaml` 保持 **0600**、顶层仅三键、原子写」（§6 文件系统不变量）

**判定**：**A｜真缺口（且属红线 3 明禁的"静默降级"）**。技术上 Windows 有等价物（显式 DACL：`icacls` 或 `windows` crate 安全 API），并非不可能——现在是**既没做、也没说**。
**风险量级（不夸大）**：Windows 上文件落在 `%USERPROFILE%\.dsh\`，NTFS 默认会继承用户 profile 的 ACL（通常仅本人 + SYSTEM/Administrators），所以**不是** Unix 上 0644 那种"同机他人可读"；但它也**不保证**如此（组策略/漫游 profile/自建目录可变），而文档把它写成了强保证。
**补齐二选一**：① Windows 侧显式设 DACL（小改动，需 Windows 真机验一次）；② 或把三处文档改成"Unix 严格 0600；Windows 依赖 profile 默认 ACL"。

## 3. C｜待裁定

### 3.1 macOS 沉浸式标题栏：只做了"无等价物"的那半，有等价物的那半没做

**仓库现状**：`src-tauri/src/ui.rs:155-172` 用 `#[cfg(target_os = "macos")]` 设 `TitleBarStyle::Overlay` + `hidden_title(true)` + `Effect::Sidebar`；`frontend/src/injected/immersive-chrome.js:32` 与 `frontend/src/lib/immersiveChrome.ts:37-43` 同样以 `os === 'macos'` 为门。

**crate 源码核对（tauri 2.11.5 / tauri-utils 2.9.3，本地 registry 实读）**：

| 事实 | 出处 | 对仓库注释的裁决 |
|:--|:--|:--|
| `TitleBarStyle` 文档首行 = "How the window title bar should be displayed **on macOS**" | `tauri-utils-2.9.3/src/lib.rs:161` | ui.rs:151「Tauri 稳定版无 titleBarOverlay 等价物」**属实** ✓ |
| `WindowEffect` 含 `Mica` / `MicaDark` / `MicaLight` / `Tabbed…` / `Blur` / `Acrylic`，注释标注 **Windows 11 / 10 Only** | `tauri-utils-2.9.3/src/lib.rs:122-152` | **同一个 `EffectsBuilder` API 在 Windows 上有毛玻璃等价物** —— 现在只调了 macOS 的 `Effect::Sidebar` ⇒ **可做而未做** |
| `data-tauri-drag-region` 由 window 插件**默认模板**注入（`#[default_template("./scripts/drag.js")]`），无平台 cfg | `tauri-2.11.5/src/window/plugin.rs:243` | ui.rs:66「仅 macOS 生效」指的是**只有 macOS 注入它**；机制本身跨平台可用 |
| `WindowEffectState` 标注 "**macOS only**" | `tauri-utils-2.9.3/src/lib.rs:156` | Windows 侧的 `state` 无对应物（不影响 `effects` 本身） |

**逐平台可行性**：

- **Windows**：无边框 + 自绘窗口控件（`minimize` / `toggle_maximize` / `close` 均跨平台 API）+ **Mica/Acrylic 毛玻璃**（同一 `EffectsBuilder`）+ 拖拽区机制 ✓。**缺的是实现**，不是能力。
- **Linux**：无边框 + 自绘控件可做；**毛玻璃无 Tauri API**（合成器私有）⇒ 可做但"形不同"。
- **已知硬骨头**（代码里已写明，`immersiveChrome.ts:38-43`）：dsh 的 Windows 拖拽条是**伪元素 `::before`**，无法用属性映射，需另想办法（或与 dsh 侧解耦）。

⇒ **裁定点**：① Windows 是否排期补齐（毛玻璃这半代价小、自绘 chrome 这半代价中）；② Linux 是否只做无边框不自绘；③ 若决定不补，是否把「已知限制」从"macOS 专属"改写为**技术原因 + 后续计划**（现状措辞容易读成"能力所限"，而实际是"未做"）。

### 3.2 Windows 的平台标记：映射已就绪，被 v1 门挡住

`immersive-chrome.js:7` 只打 `data-platform="darwin"`；`immersiveChrome.ts:3-6` 明确 dsh 官方还有 `html[data-windows-titlebar]` 一套桌面 CSS（**属性选择器**，可直接 `toggleAttribute`）。
⇒ 决定补 3.1 时一并做；单独做有布局风险（在**原生装饰**下是否成立未经真机验证）⇒ 标 C。

### 3.3 架构维度：红线的"平台"要不要覆盖 arm64？

- README 已明写：**Windows ARM64 经系统仿真运行**（`README.md:244`、`:251`），非静默；
- 但代码侧 **`win32-arm64` 的 pnpm 落位名已登记**（`updates.rs::engine_pnpm_bundle`，并有 G3 回归闸门 `scripts/tests/test_release_platform_matrix.py:121`）⇒ 一旦加 leg 即可用；
- Linux ARM64 **未提及**（既无 leg 也无文档）。
⇒ 红线 3 现文写的是 x64。**若维护者认为 arm64 用户也在覆盖范围内**，需裁定并改红线文本；否则请在 README 保持"仿真运行"的显式说明（现状已满足"不静默"）。

### 6.2 macOS 签名/公证 vs Windows **无 Authenticode 签名** ⇒ **C（成本裁定）**

- macOS：5 个 secret 全量校验 + 缺一即硬失败（`build.yml:265-291`）⇒ 用户拿到的是已公证包。
- Windows：全仓搜 `signtool` / `Authenticode` / 证书 secret **零命中** ⇒ 用户双击会撞 SmartScreen「未知发布者」。
- **技术上完全可做**（有 OV/EV 证书即可，Tauri 侧配 `certificateThumbprint` + `digestAlgorithm`）；卡点是**证书采购与组织身份**，属商业决策 ⇒ C。
- **但披露不对称**：README 给了 macOS 的 Gatekeeper 提示（`README.md:257`），**没有** Windows 侧的 SmartScreen 提示 ⇒ 建议补一句（零成本）。
- 注：**更新链安全不受影响**——updater 用的是 Tauri 自己的 minisign `.sig`，三平台都签（`scripts/generate-latest-json.py` 的 `platforms` 映射齐全）。

### 6.3 引擎资产（pnpm 引导器）对称性：**已有机器闸门守住**

`scripts/tests/test_release_platform_matrix.py` 守三件事：壳会请求的平台 ⊆ 脚本能取（含 `win32-arm64` G3 回归）、uname 探测分支 ⊆ 白名单、CI leg 声明的平台 ⊆ 白名单。
⇒ 引擎资产侧**没有**"某平台能请求却取不到"的空洞（这正是 v1.1.1 前后踩过的坑，现已机器化）。

## 8. 建议的下一步（按性价比排序，待维护者裁定）

1. **凭据权限：先止损披露，再决定是否补 DACL**（§2.3）：三处文档要么补「Windows 依赖 profile 默认 ACL」，要么 Windows 侧显式设 DACL。**这是当前唯一"安全承诺与实际不符"的项**，代价最小、优先级最高。
2. **WSL 客体档 5 项下沉**（§2.1）：收益最大（同一个 Windows 用户直接多 5 项能力），原语已在，属纯实现工作；建议先做 1（只读，风险最低）→ 2/3（写 patch，复用 `mcp.rs` 已有客体写路径）→ 5（安全模式）→ 4（MCP 探测，跨子系统 stdio 需专门设计）。
3. **清理 `mgmt.rs` 死码 + 前端误导性 fixture**（§2.2）：几分钟，消除"测试守着一句永不出现的文案"。
4. **README 补 Windows SmartScreen 提示**（§6.2）：零成本；签名证书是另一件事（成本裁定）。
5. **Windows 沉浸式补齐立项**（§3.1）：先做**毛玻璃**（同一 API，代价小、观感立现），再评估自绘 chrome；依赖 §7 的 Windows 真机恢复。
6. **Linux 真机冒烟**（§7）：哪怕只跑一次 AppImage + deb，也能把"从未运行过"变成"跑过"。
7. **README 「已知限制」改写**（§3.1③）：把"macOS 专属"改成"技术原因 + 计划"，避免用户读成能力所限。

## 9. 与红线 3 的关系（结论）

- 红线 3 的三条要求——**都适配**、**不可能要显式说明**、**收窄要裁定 + ADR**——本次审计逐面核对后：
  - **"显式说明"这一条，仓库做得很好**：所有已知平台差异都有可行动文案（WSL 5 项甚至给了替代路径），没有一处静默假实现——**唯一例外是 §2.3 的凭据权限**。
  - **"都适配"这一条**有两处未达标：§2.1（WSL 模式 5 项）与 §3.1（Windows/Linux 沉浸式）。
  - **"收窄要裁定"**：现有收窄（macOS 专属沉浸式、Windows ARM64 走仿真、x64-only）**均有文档**，但没有一条走过**ADR**程序 ⇒ 建议在补齐或明确放弃时补一份 ADR 收口（红线 3 已把"删 leg / 删上传 / 删下载"纳入裁定范围，功能级收窄同理）。
