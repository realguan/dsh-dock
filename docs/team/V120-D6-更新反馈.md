## 2. 判据形态：为什么这两条用**源码顺序闸门**（与序列用例互补）

`run_download_and_install` 收 `&AppHandle`，内部跑**真实网络下载**；本仓**无 Tauri 测试基建**
（AGENTS §5 不引 dev-dependency）⇒ 既起不出运行时、也无法伪造下载。

而该缺陷的本质就是**发出的先后顺序**——判据自然就是"这两个 `set_state` 谁在前"。
故：**源码闸门管「谁在前」**（接线/顺序），**纯逻辑用例管「序是否合法」**（§3）。
两者与 qa-verify 的「收集 emitted 事件序列并断言顺序」判据**同构**（M8：不数调用次数、看序列）。

闸门细节：CRLF 归一（v1.1.1 教训）+ **只取函数体范围**（`find("pub fn …(")` → 下一个
`///` 段注释前），防被文件别处同名标识符误判为通过。

## 3. 修复内容

### 3.1 进入动作即发可见态

```rust
set_state(&state, &app, ClientUpdate::Checking);   // ← 新增：在 blocked_check 之前
let mut update = match blocked_check(&app) { … };
```

`blocked_check` 含 **10s 连接超时**（`:291` `connect_timeout`）+ packument 解析，此前这段
**零状态变更** ⇒ 用户点「下载」完全没反应。现先推 `Checking`（前端已有该相位的 loading 文案），
解析完成后从 `checking` 前进到 `downloading`/`installing` 均满足单调序
（`checking < downloading < installing`）。

**不新增相位**（避免契约形状变更与前端闸门返工）。

### 3.2 重排：`Installing` 移到下载之后（**本次核心**）

| | 修前 | 修后 |
|:---|:---|:---|
| 首次可见态 | 无（解析期间空白） | `Checking` |
| 下载前 | `Installing`（`:156`） | `Downloading{0, None}`（新增显式首帧） |
| 下载中 | `Downloading × N`（100ms 节流） | `Downloading × N` |
| 下载后 | —（已提前发过 Installing） | **`Installing`**（Windows 分支，下载完成 → 安装前） |

**Windows 分支**（`download` 与 `install` 分离）可精确在"下载完成"与"开始安装"之间发
`Installing` —— 这正是语义正确的时刻。

**非 Windows 分支**走 `download_and_install` **一体化 API**，**没有**"下载完成"可拦截点
⇒ 不预发 `Installing`（否则会造出 `installing` 与 `downloading` 交错的双相位），
真正安装态由 `Done → Relaunching` 承接。**两条分支的差异已在代码注释中写明**——
这是平台 API 形态差异，不是疏漏。

### 3.3 相位模型 + 倒退告警

新增（`updater.rs`，纯逻辑）：

- `UpdatePhase` 枚举 + `ClientUpdate::phase()`（取判别式）；
- `phase_rank()`：**唯一权威顺序**（`Idle < Checking < Available|UpToDate < Downloading
  < Installing < Done < Relaunching`；`Failed` 不参与序）；
- `transition_allowed(from, to)`：三条规则 —— ①**同相位幂等允许**（进度是重复事件；
  判非法会让进度冻结，正是 D6 的症状之一）②`Failed` 可从任意相位进入 ③允许回到
  `Checking`（重新解析）；其余要求单调前进；
- `set_state` 广播前**相位倒退告警**（`tracing::warn`，不阻断）——把"倒退"从**静默**变**可观测**。
  这正是本次缺陷此前无人发现的原因（先 `Installing` 后 `Downloading` 完全无声）。

**自测发现的一条真缺口（我的用例抓出来的，已修）**：只按 rank 递增会放行
`idle → downloading`（"没查过就开始下载"）。`reverse_transition_is_rejected` 首跑即在
这条上红 ⇒ 追加约束：`Downloading`/`Installing` **只能由已有更新可装的相位进入**
（`checking`/`available`/`downloading`/`installing`）。

### 3.4 顺带修正的文档头

模块头 `:36-38` 的状态机注释此前与实际发射序**相矛盾**（它写 `… → downloading →
installing →`，而代码恰好相反）。现已让**代码与注释一致**，并注明 `Done` 在
`Relaunching` **之前**是既有发射序、**不要"顺手"对调**（前端表依赖它）。

Lead 转达：`frontend/src/stores/clientUpdateStore.ts` 的 `TRANSITIONS` 已放宽为
`installing ⇄ downloading` 双向兼容，并用 `idle→done` 断言防止放宽成万能表
（其复现锚：修前丢弃 **5** 条事件、进度采样 `[10]` vs 期望 `[10,50,90]`）。

⇒ **本条在 Rust 侧的落点是相位模型本身**：`Downloading` 自环在
`transition_allowed` 里是**幂等允许**（规则 1），并由 `emitted_sequence_advances_monotonically`
（含 4 条连续 `Downloading`，其中 3 条为进度推进）与 `allowed_special_transitions` 双重钉住。

**跨层契约（给 T-F，供核对；本轮无需改动）**：
- 事件名 `app:update`，负载 = `ClientUpdate`（tagged by `phase`）；
- **发出序**（修后）：`checking → downloading(×N，含首帧 current=0) → installing → done → relaunching`
  （Windows 分支有 `installing`；非 Windows 分支**不**发 `installing`，由 `done`/`relaunching` 承接）；
- 任一相位 → `failed` 始终合法；
- `available|upToDate|done|failed → checking` 合法（重新检查）。

## 5. 交付项 4：apply 期间重新 check 是否必要？（**结论：必须保留**）

**现状**：`run_download_and_install` 入口先 `blocked_check(&app)` 拿到
`tauri_plugin_updater::Update` 句柄，再 `download` / `install`。

**能否复用已有的 `Available`？——不能。三条硬理由**：

1. **`Available` 里没有句柄**。`ClientUpdate::Available { latest, notes }` 只有版本号与
   发布说明（给前端渲染用）；`ShellState::client_update` 也只存 `ClientUpdate`
   （`boot.rs:153`）。真正可下载的 `Update` 句柄**从未被缓存**过——它是在 `run_check`
   的局部作用域里产生、返回前端只留相位快照。
2. **`Update` 不是可安全长期持有的值**。它由 `updater.check()` 解析而来，绑定当时的
   Release 元数据与 `download_url`；正是同一函数里 `mirror_download_url(&update.download_url)`
   要读/改写它的 `download_url`。长期缓存会引入"元数据过期但仍被下载"的风险。
3. **检查与下载之间可能隔任意久**。用户在 about 页看到 `available` 后可能几分钟后才点
   下载；期间上游可能已发新版或撤销 Release。重新 `check()` 是**唯一**能保证
   "下载的确实还是当前最新/仍存在"的措施。

**保留的代价与缓解**：`blocked_check` 有 10s 连接超时 → 这正是交付项 1 要解决的
**观感问题**；现已在它**之前**发 `Checking`，用户立即看到 loading，代价被掩盖。
另：写操作（`install`/`restart`）前的**再确认**在更新场景属正确取舍——
"多点一次网络往返换『下的不是旧包』"值得。

**若将来要省掉它**（不建议）：需在 `ShellState` 里缓存 `Update` 句柄 + 加 TTL + 在
`Available` 相位失效时驱逐。属**契约与状态模型变更**（`ShellState` 增字段），
**须先立 ADR**，不在本任务范围。

   若产品希望区分（如文案「准备中…」），需**新增相位** ⇒ 契约形状变更（前端 `UpdatePhase`
   联合类型 + `TRANSITIONS` + `ipc-shapes` 闸门），须走流程。本轮按"不新增相位"处理。
4. **spawn 闸门盲区**（task-42 §8 登记）本轮**未动**，按 Lead 要求等下一轮。
