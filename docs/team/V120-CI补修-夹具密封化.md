## 1. 任务一：机制复现（用**真实生产脚本**）

### 1.1 直接证据：`/etc/profile` 的 path_helper 行为（本机实测）

```console
$ grep -n "path_helper" /etc/profile
3:if [ -x /usr/libexec/path_helper ]; then
4:	eval `/usr/libexec/path_helper -s`
$ cat /etc/paths
/usr/local/bin          ← 首项
$ id -u   → 501（非 root）；/usr/local/bin 不可写；/usr/local/bin/node 不存在

$ env -i HOME=… PATH="/tmp/qa53/competitor:/usr/bin:/bin" /bin/bash -c '. /etc/profile; echo "$PATH"'
/usr/local/bin:/System/Cryptexes/App/usr/bin:/usr/bin:/bin:/usr/sbin:/sbin:…
  …:/tmp/qa53/competitor          ← 继承 PATH（含竞争者）被推到**最后**
```

⇒ **机制坐实两点**：① `. /etc/profile` 把 `/usr/local/bin` **前置到最前**；② 它把**继承来的 PATH 推到末尾**。这解释了旧夹具为何在 CI 上失守：夹具 shim 只经**继承 PATH** 进入，而 runner 的真 node 恰在 `/usr/local/bin`（前置）⇒ 真 node 胜出。

### 1.2 两态复现（4 态矩阵，跑**真实** `diagnostics_script`）

**取得真实脚本的方式（避免 M9「测的是自己的重实现」）**：临时注入一个导出用的 `#[test]`，把 `crate::guest::diagnostics_script("Ubuntu-20.04")` 原文写到 `/tmp/qa53/real-script.sh`，随即 `cp` 备份还原：

```console
### 注入哈希 18ae7595e7ab51ee → 918dda227812c46f ✅生效
test updates::zz_qa_script_export::zz_qa_dump_real_script ... ok
### 复原=18ae7595e7ab51ee ✅ byte-exact  残留=0
```

脚本开头逐字（**证实 source 顺序与最后前置**）：

```sh
DSH_ENGINES="$HOME/.dsh-dock/engines";. /etc/profile 2>/dev/null;. "$HOME/.profile" 2>/dev/null; . "$HOME/.bashrc" 2>/dev/null;
if [ -d "$DSH_ENGINES/bin" ]; then PNPM_HOME="$DSH_ENGINES"; export PNPM_HOME; PATH="$DSH_ENGINES/bin:$PATH"; export PATH;fi;
node_bin=$(which node 2>/dev/null || true); …
```

**矩阵结果**（竞争者 = 真 node v24.20.0，注入在 `.profile`；`自证断言` = 复刻 `053e156` 新增断言的表达式 `path.starts_with(&home)`；`版本断言` = 归一化后 == `24.18.0`）：

| 场景 | 脚本读到的 node 路径 | 版本 | 自证断言 | 版本断言 |
| :--- | :--- | :--- | :--- | :--- |
| **S0** 旧放法 · 无竞争者（= 修前本机现状） | `<root>/bin/node` | v24.18.0 | **红** | 绿 |
| **S1** 旧放法 · 竞争者@`.profile`（= CI 机制） | `<root>/competitor/node` | **v24.20.0** | **红** | **红** |
| **S2** 新放法 · 竞争者@`.profile` | `<root>/home/.dsh-dock/engines/bin/node` | v24.18.0 | 绿 | 绿 |
| **S3** 新放法 · 竞争者@`.profile`+`.bashrc` | 同上 | v24.18.0 | 绿 | 绿 |
| **S4 最大敌意**：竞争者同时在 **继承 PATH 最前** + `.profile` + `.bashrc` | 同上 | v24.18.0 | 绿 | 绿 |

- **S1 的 `v24.20.0` 与 CI 报错的 `left: Some("24.20.0")` 逐字一致** ⇒ 复现了 CI 失效值。
- **S0 说明「本机绿」是巧合**：旧放法在无竞争者时确实读到夹具（v24.18.0）——与本机 `/usr/local/bin/node` 不存在 + 本机真 node 恰为 v24.18.0 的双重巧合一致（我已独立核实这两个事实：`ls /usr/local/bin/node` = 不存在；`which -a node` 只指向引擎 bin，`--version` = v24.18.0）。
- **S4 是结构性结论**：脚本第 5 步 `PATH="$DSH_ENGINES/bin:$PATH"` 发生在**所有 source 之后**，故无论 `/etc/profile` 的 path_helper 前置了什么都无法插到它前面 ⇒ **新放法对 path_helper 免疫**（这比"再把竞争者往某个槽位放"更强）。

### 1.3 忠实度边界（如实标注）

**我不能**在 `/usr/local/bin` 放真 node（非 root + 目录不可写；path_helper 其余前置目录 `/Library/Apple/usr/bin`、`/usr/local/go/bin` 同样不可写或不存在）。故：
- 我用 `.profile`/`.bashrc`/继承 PATH 三个**同侧**槽位模拟竞争者，**复现的是因果机制（相对顺序），不是 CI 的绝对路径槽位**；
- 机制侧的**独立确认**来自 §1.1 的 path_helper 直接探针 + §1.2 S4 的结构性免疫；
- **决定性证据仍是 CI run**（§5）——按 M10/M11，本机绿不作证据。

### 3.3 `guest.rs` 的 6 个未密封用例：**经实测确认 PATH 不敏感（不是缺陷）**

它们跑生产脚本（含 `guest_prep!()`），但**只断言文件操作/平台字符串**，不断言 PATH 解析出的工具值。我用**敌意 PATH 实测**验证（`node`/`pnpm`/`dsh` 全被劫持为打印 `HOSTILE-9.9.9`）：

```console

$ PATH="/tmp/qa53/hostile:$PATH" cargo test --lib
test result: FAILED. 381 passed; 13 failed; 3 ignored

$ grep guest_script_output_parses_into_versions …             → test … ok   ← 被验夹具在敌意 PATH 下仍绿
```

⇒ `guest::` / `updates::` / `executor::` **在敌意 PATH 下全绿**（含被验夹具）⇒ 密封有效；`guest.rs` 那 6 条**确实不敏感**（我的代码阅读结论被实测确认）。

### 3.4 `sessions.rs` 的 13 条：**另一子类，非同类残留**

- 它们经 `find_system_node()` 把**真系统 node** 符号链接进 `engines/bin/node`，用真 node 跑会话扫描脚本；**注释明写**「找不到系统 node 则跳过」。
- 我的敌意 PATH 把"真 node"换成了**会打印垃圾的假 node**，故 13 条失败——这是**探针过激**（CI runner 上的 node 是**可用**的，不存在这个条件）。
- **反证其非硬依赖**：
  ```console
  $ env PATH="$HOME/.cargo/bin:/usr/bin:/bin" cargo test --lib sessions::     # 该 PATH 下确实无 node
  test result: ok. 33 passed; 0 failed; 0 ignored
  ```
  ⇒ **无 node 时优雅跳过**（33 绿），与注释一致。
- **分类**：这是「测试**需要一个可用的**宿主工具」的**既有、有意、有降级路径**的依赖，**不是**「夹具 shim 被宿主工具顶掉（经 profile source）」这一类，且不产生 CI 症状（它们不比对版本）。**仅登记为相邻脆弱性**，非缺陷。
