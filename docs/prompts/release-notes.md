# Prompt 模板：版本发布与 Release Notes 生成

> 适用场景：准备发布新版本、生成版本升级日志、更新 `docs/RELEASE_NOTES.md`。

---

## 任务 Prompt 模板

```text
【角色】
你是 DSH Dock（Tauri v2 跨平台桌面管理面板）的版本发布与文档专员。请遵循 AGENTS.md 规范与 docs/templates/release-notes-template.md 模板。

【输入信息】
1. 目标发版版本号：<!-- 例如 v0.9.5 -->
2. 基线范围（二选一）：
   - 自动获取（优先）：对比上一个 git tag 到当前 HEAD 之间的提交变更（git log）与 docs/broadcasts.md 最新记录。
   - 手动提供：<!-- 粘贴特定的 commit 列表、PR 摘要或改动记录 -->

【第一步（强制，不可跳过）】
先跑下面这条命令，拿到区间与应填清单，再动笔：

```bash
# ① 拿区间与应填清单（tag 未建时用 HEAD 预演——发版流程里通常如此）
python3 scripts/check-release-coverage.py HEAD --prev <上个 tag> --version <本版号> --print

# ② 写完全部正文与覆盖清单后，再校验一次（这一步就是 CI 会跑的那条）
python3 scripts/check-release-coverage.py HEAD --prev <上个 tag> --version <本版号>
```

`--version` 在预演时**必须给**：入参是 `HEAD` 或 sha 时推不出 `[vX.Y.Z]` 小节是哪一个，
脚本会直接报错而不是猜（猜会报出「缺少覆盖清单」这种指向错误原因的错）。

**为什么强制**：2026-09-29 的 v1.3.4 就是在这里栽的——发布日志凭记忆写，
区间内 10 个提交里 4 个用户可感知的改动（会话维护模块下线、安全模式删除、
实验能力裁剪、插件操作体验四连）**一条都没写**；而那 4 个提交已在 master 上放了
5 天、没有任何东西提示「尚未发布」。**只要作者看的是「最近的工作」，就必然漏。**

拿到命令输出后，**逐条**读区间内每个提交，判断它属于下面哪一类，并在正文里落实：
- 用户可感知（`feat` / `fix` / 破坏性 `refactor` / 功能增删）→ **必须**写进对应板块；
- 纯内部（CI / 依赖 / 纯重构 / 纯测试 / 纯文档）→ 不进正文，**但仍要出现在覆盖清单里**。

【最后一步（强制）】
在版本小节标题下方补一行覆盖清单（对用户不可见，供 CI 核对「账目是否平」）：

```markdown
## [vX.Y.Z] - YYYY-MM-DD
<!-- coverage: <上一步命令输出的完整哈希列表，逐字粘贴> -->
```

**清单必须落在发版前的最后一个提交里**，且单独成提交（不要和内容改动混在一起）：
- 混在一起时，那个提交既改了内容、又列不出自己 → 门禁正确判红；
- 清单**之后**再加任何提交，清单都会失效（区间变了）。这是刻意的——账目必须与区间同步。
  忘了也没关系：门禁的报错会**直接给出正确的那一行**，逐字粘贴即可。

只改 `docs/RELEASE_NOTES.md` 的提交由门禁自动豁免（承载清单的提交无法列出自己；
而只改发布日志的提交按定义不可能改变用户可见行为）。

【发版顺序（每次都会撞到，照做即可）】

```
① 内容提交（代码 / 文档 / 广播……）        ← 广播是内容提交，也算在这里
② 刷新覆盖清单：--print 取新行 → 粘贴进 RELEASE_NOTES
③ 提交清单（只动 RELEASE_NOTES.md）        ← 发版前最后一个提交
④ 打 tag
```

**广播（`docs/broadcasts.md`）也是内容提交**，按 AGENTS §10 通常写在最后——
它一提交，区间就变了，所以第 ②/③ 步必须排在它**之后**。忘了也不致命：
门禁报错会直接给出正确的那一行。

【过滤与提炼原则】
1. 过滤内部琐事：彻底忽略 CI/CD 配置微调、代码格式化、纯单测调整、纯依赖锁更新等终端用户无感知的琐碎改动。
2. 开发者/用户视角：以结果和价值为导向（“解决了什么”、“带来了什么新体验”），禁止生搬硬套底层函数名或裸提交信息。
3. 精炼前置：核心亮点（Highlights）控制在 1-2 句最核心的价值概括，便于桌面端更新弹窗首屏展示。
4. 动态保留板块：严格遵循 docs/templates/release-notes-template.md 结构；若某板块（如 Bug Fixes 或 Security）在本次版本中无对应改动，请直接省略该标题，不要保留空白或写“无”。

【格式硬契约（必须严格遵守）】
1. 一级标题格式必须严格为：`## [vX.Y.Z] - YYYY-MM-DD`（包含中括号与当前日期），确保 CI 脚本能够精准通过正则提取。
2. **标题下方必须紧跟覆盖清单** `<!-- coverage: … -->`，集合须等于上个 tag 到本 tag 的提交集合。
   由 `scripts/check-release-coverage.py` 在打 tag 时校验（多列/少列/漏写一律红）。
3. 保持专业工程克制风格，禁止大面积滥用非标准 Emoji。

【功能移除必须显眼（2026-09-29 补）】
删除用户可见功能时，**不得**埋在「体验与交互优化」里蒙混过去。要求：
- 单列一节 `### ⚠️ 本次移除的功能`，逐条写明**它原本做什么**、**为什么移除**、
  **替代出路是什么**（或明确说没有替代）；
- 若某能力是**往期版本宣传过**的（如 v1.3.0 的「已归档会话一键取消归档」），
  必须点名它来自哪个版本——用户是照着那版说明在用它的。

【执行输出】
1. 生成结构化 Release Notes Markdown 内容。
2. 将该小节内容追加写在 `docs/RELEASE_NOTES.md` 顶部（保持历史版本连续性）。
```
