# 模板：Bug 排查

> 用途：把「它坏了」变成 AI 可定位的结构化任务。核心是**证据链完整**：
> 现象、错误信息、已尝试方案缺一不可。

## 使用说明

1. **日志贴原文尾部 30–50 行**（数据目录 `dsh-shell.log`），别只贴你截选的报错行——
   根因常在报错前几行。
2. 「已尝试」必须如实填；没试过就写「无」。AI 会把已排除项从候选根因里划掉。
3. 强制「先假设后验证」两阶段：先给候选根因与验证方法，**人确认后再改代码**——
   防止 AI 在错误假设上直接糊补丁。
4. 平台相关 bug 必须写全四栏环境（mac/win/linux/wsl），这是本仓库最高频的坑源。

## 模板

```text
【角色】
你是本仓库的资深排查者。先读 AGENTS.md 相关章节，再基于我给的证据定位根因；
证据不足时列出需要我补充的信息，禁止凭空推测。

【问题描述】
<预期行为> vs <实际行为>
<出现频率：必现/偶发（概率）/仅特定条件>

【环境矩阵】
| 平台 | 版本 | 是否复现 |
| macOS | <…> | |
| Windows | <…> | |
| WSL 发行版 | <…> | |

【错误信息】
<日志尾部原文 / 弹窗文案 / boot:error payload 原文>

【已尝试方案】
1. <做法> → <结果：无效/有变化/更糟>
2. …

【约束】
- 允许改动：<文件范围>；其余只读。
- 疑似涉及共享区（lib.rs / capabilities）→ 我会先发占用声明，你先不要输出改动。

【输出要求】
阶段一（现在）：≤3 个候选根因，按可能性排序；每个附「验证方法」
（跑什么命令 / 加什么日志 / 看哪个文件）；
等我回复确认后进入阶段二：最小化修复 + 复现该 bug 的回归测试 + commit 草稿。
禁止在未确认前直接给修复代码。
```

## 已填示例

```text
【问题描述】
预期：点「检查更新」后托盘菜单显示「升级到 x.y.z」。
实际：按钮转圈约 3 秒后恢复，菜单无变化。必现于公司网络，家宽正常。

【环境矩阵】
| Windows 11 23H2 | 公司网络(代理) | ✅ 复现 |
| macOS 14.5 | 家庭宽带 | ❌ 正常 |

【错误信息】
dsh-shell.log 尾部：
（粘贴原文）

【已尝试方案】
1. 关闭系统代理 → 无效
2. 手动访问 APP_RELEASE_FEED 的 latest API → 浏览器可打开

—— 阶段一典型产出：
候选 1（高）：代理环境下 ureq 未配置 proxy，直连被防火墙静默丢包 →
验证：日志搜 `timeout` vs `refused`；用 `HTTPS_PROXY` 环境变量起壳对比。
候选 2（低）：镜像链排序在企业 DNS 下解析失败回退超时 → 验证：抓 DNS 查询。
```
