# ADR-0001：dsh 就绪等待采用进程存活感知

- **日期**：2026-08-26
- **状态**：已接受（2026-08-24 裁定，本 ADR 追溯补录）
- **提出人**：guan
- **相关方**：shell.rs / lib.rs 启动链
- **关联**：上游 ADR-0005（桌面终端定位）

---

## 1. 背景与问题

壳 spawn dsh 后需要判定「就绪」才能导航 WebView。早期做法是死等一个固定超时：要么等满全程（真失败也要白等到底），要么用日志关键字探测（dsh 前端改一行日志文案就误判）。Windows 冷启动尤其难：Defender 首扫 + Node 冷加载能把首次启动拖到远超预期，固定超时要么掐断合法慢启动、要么为兜底极端情况而把上限拉得过长。

## 2. 约束与硬指标

- 不阻塞 UI 线程：就绪等待在后台线程。
- 不阻塞退出处理器：重试/退出要能随时拿到会话做 teardown。
- 真失败秒报：dsh 进程中途退出不能等满超时。
- 不留孤儿：超时/退出要先收掉旧会话再报错。
- Windows 冷启动的合法慢启动不得被误判为失败。

## 3. 备选方案及评估

### 方案 A：进程存活感知（硬上限 + 卡死判定 + 退出即败）—— ✅ 最终采纳

- 思路：以「dsh 进程是否还活着」为主信号，日志增长为辅信号。硬上限兜底，进程退出立即判败，进程活着但日志长时间无进展判卡死。
- 优点：真失败秒报；合法慢启动只要进程活着且在输出就不误杀；退出处理器随时能 teardown（短锁轮询会话槽）。
- 代价/风险：卡死阈值（日志无进展时长）是经验值，需随真实日志节奏调。
- 对照约束：逐条满足（后台线程 / 短锁 / 退出即败 / teardown-before-error / Windows 冷启动宽限）。

### 方案 B：固定超时死等 —— ❌ 否决

- 思路：spawn 后 sleep 固定秒数即判就绪。
- 否决理由：违反「真失败秒报」与「不留孤儿」（进程早退也要等满）；Windows 冷启动上限拉得过长则拖慢正常路径。

### 方案 C：日志关键字探测就绪 —— ❌ 否决

- 思路：扫描日志出现特定行（如 `listening on http://...`）即判就绪。
- 否决理由：dsh 前端日志文案属上游实现细节，壳依赖它 = 跨边界耦合；上游改文案即误判。当前实现确实从日志解析端口地址，但那是「拿到 URL 导航」而非「判定就绪」——就绪语义仍由进程存活 + 日志进展驱动，不绑死具体文案。

## 4. 最终决策

就绪等待 = 进程存活感知：硬上限兜底 + 进程退出立即判败 + 日志长时间无进展判 `Stalled` + 超时/退出先 teardown 旧会话再报错。具体阈值与轮询实现见 `shell.rs::wait_for_ready` / `lib.rs`（`BOOT_TIMEOUT`、`BOOT_STALL`、`ShellState.session` 短锁轮询、`teardown_session`）。

## 5. 后果与后续行动项

### 正面后果
- 真失败秒报，合法慢启动不误杀。
- 退出处理器不与就绪等待争锁，重试不残留孤儿 dsh。

### 负面后果 / 新增债务
- `Stalled` 阈值是经验值，不同 dsh 版本日志节奏变化时可能需调。
- 就绪判定依赖进程存活 + 日志增长，不探测端口/健康端点（端口被占用等边界场景靠 dsh 自身报错退出走 `Exited` 路径覆盖）。

### 行动项
- [x] `wait_for_ready` 实现并带测试（shell.rs 9 个测试）。
- [x] 超时/退出路径先 teardown 再 `emit_boot_error`。

## 6. 复审条件

- Windows 冷启动基线显著变化（Defender 行为、Node 启动特性）→ 复评 `BOOT_TIMEOUT`。
- 改为端口 / 健康端点探测就绪 → 本决策重开（届时进程存活感知退为辅信号）。
- dsh 上游提供标准就绪信号（如 stdout 协议行）→ 复评是否替换日志进展判定。
