## 1. 背景与问题

### 1.1 事故（2026-09-10 实测，证据见 `docs/known-issues/问题记录-2026-09-10-会话写锁被孤儿dsh占死.md`）

用户在工作台打不开某个会话，错误为 dsh 引擎抛出的
`SessionAlreadyOwnedError: session "…" is already owned by an active write handle`；
可用恢复手段只有「删掉该会话 + 重启 dsh-dock」。实测取证：

- **锁的归属是 dsh**：每个会话目录 `<会话>/session.lock` 一把**内核级跨进程写锁**
  （POSIX 非阻塞 `flock(2)`；Windows 具名内核信号量），**刻意无过期**——「活着的持锁者
  一直持有，直到其进程退出；绝不设过期去剥夺一个卡住的写者」。壳侧全仓
  `session.lock` / `LEASE` / `flock` **零引用**（`state.session.lock()` 是 Rust 自己的
  `Mutex`，同名巧合）。
- **持锁者是壳的孤儿**：`pid 85156`，`PPID=1`（父进程已死被 launchd 收养），命令行
  `…/dsh-dock.dev/engines/…/@deepseek-ai/dsh/lib/bin.js --profile web --port 0 --no-open`，
  `lsof` 显示它持的正是报错那个会话的锁。
- **存量规模**：**11 个孤儿**（全部 `.dev` 构建，创建于 2026-09-09 17:18 ～ 2026-09-10 18:01），
  共锁死 ≥5 个会话，且与工作区无关（含 `ms_sast` 工作区）；一个孤儿可同时持有 2 把锁。
- **"重启 dsh-dock"从来不是解法**：锁由内核按**持锁进程存活**维持，壳重启不改变孤儿存活
  状态。「删会话」有效纯属 `sessions.rs` 的 `remove_dir_all` 顺手 unlink 了锁文件——
  **有损**（丢会话历史），不得固化为修复手段。

### 1.2 根因：三条路径叠加

1. **硬杀无可连坐**（真根因）：所有清理都挂在父进程**临死前跑代码**的路径上——
   `RunEvent::Exit`（`lib.rs`）、信号处理器（`boot.rs`）、`stop_dsh`（`shell.rs`）。
   `SIGKILL` / 强制退出 / 崩溃 / panic 面前 **全部失效**，而内核不会替你连坐。
   `cargo tauri dev` 的每次重编重启正是这条路径。
2. **无回收机制**：`reap_previous_session` 只看会话槽，槽中无则永远找不到逃逸者。
3. **放大器**：dev 与 prod **共用 `DSH_HOME=~/.dsh`** → dev 的泄漏锁死了正式包（1.1.0）的会话。

### 1.3 ADR-0014 的复审条件已被触发

ADR-0014 §3 方案 D 曾评估「进程组 / Job Object 收口」并**本次否决**，其 §6 明写：
> 「任何一次实机孤儿进程复现（该项一旦复现，**立即升级为方案 D 专项**）」

本次即该触发。但**照搬方案 D 会违反 ADR-0014 自己给出的否决理由**（见 §2.2），
故本 ADR 必须给出一个*缩小影响面*的替代设计，而非重启方案 D。

### 1.4 触发本决策的第二个需求（用户明确提出）

> 「如果我装了一个插件导致 dsh-dock 启动 dsh 时崩溃，**我不希望 dsh-dock 完全退出**；
> 我希望能在控制中心手动关闭或卸载那个插件，然后重载 profile 使 dsh 正常启动。」

该需求给本 ADR 追加一条硬约束（§2.4），并**排除了**一整类"省事"设计（§3 方案 E/F）。

## 2. 约束与硬指标

1. **不修改 dsh 源码**（AGENTS 红线 1）：不得 fork / patch dsh，不得让壳参与 dsh 的锁协议。
2. **不得连坐用户经 dsh 起的长驻后台任务**（**ADR-0014 §3 方案 D 的否决理由原文**）：
   「unix 侧会连带杀死用户经 dsh 起的长驻后台任务（dsh 的合法用法），属语义变更」。
   → 任何新机制的**作用域只能到「壳生的那个进程」**，不得扩到整棵进程组。
3. **壳与 dsh 严格 1:1**（AGENTS §6）：任何死亡模式下都不得留下活着的 dsh 子进程。
4. **壳必须比 dsh 长寿，且能对着死掉的 dsh 干活**（§1.4 需求）：dsh 崩溃后壳不得退出，
   控制中心必须可进、插件禁用/卸载/重载必须可用。
   → **看门狗语义严格单向**：`壳死 → 子死` ✅；`子死 → 壳不动` ✅；`子死 → 自动重启` ⚠️ 仅由
   既有熔断器（60s 内 3 次）管，看门狗不得自维重启。
5. **优先不新增依赖**（ADR-0014 约束 3 口径）：平台原语如需 `windows-sys`，须在本 ADR 显式
   批准；优先裸 `extern "system"` + `#[link(name = "kernel32")]`。
6. **覆盖全部 spawn 面**：壳侧生产路径的 spawn 统一经 `crate::child_cmd`（AGENTS §4.1
   禁裸 `Command::new`）——守护必须落在该 seam 上，一处生效、全 app 覆盖（含 `dsh --dump-config`、
   `run_dsh_forward`、分钟级 `pnpm add -g`）。
7. **可测**（AGENTS §5）：bug 修复**复现先行**——先有能稳定复现「父被 SIGKILL → 子存活」的测试
   并见其红，再有实现让其绿；清扫判定与平台参数须为纯函数。

## 3. 备选方案及评估

### 方案 A：旁挂「单向生命线守卫」+ 启动期清扫 —— ✅ 最终采纳

- 思路（**不改变现有父子关系与 teardown 语义**，纯增量）：
  - **生命线**：壳创建一对管道，**写端自持、永不写**；把**读端**交给一个旁挂 watcher。
    壳以任何方式死亡（含 `SIGKILL`/崩溃）→ 内核关闭写端 → watcher 读到 EOF →
    对**壳生的那个子进程**（`pid` 白名单，非进程组）`SIGTERM` → grace → `SIGKILL` → 自行退出。
  - dsh 仍是壳的**直接子进程**，`stop_dsh` / 信号处理器 / `RunEvent::Exit` **一行不改**：
    watcher 只是"壳没机会跑清理代码"时的补位。
  - unix 用 `/bin/sh` 三行实现（零新二进制、零新依赖）；Windows 用 **Job Object**
    （§2.5 允许裸 FFI），因 Windows 无 `sh`。
  - **启动期清扫**（兜底层）：spawn 时在 `<data_dir>/procs/<pid>.lock` 持锁并让子进程继承 fd；
    壳启动时扫描——**能加锁的 = 陈旧文件（删）**，**加不上锁的 = 该子进程仍活着（真孤儿）** →
    `SIGTERM` → grace → `SIGKILL` + `warn` 留痕。判据是内核锁而非 pid → **PID 复用免疫**。
- 优点：作用域**只到壳生的进程**，天然满足 §2.2；不动既有生命周期代码（风险最低）；
  单点 seam（`child_cmd`）覆盖全部 spawn 面；清扫层同时管住**历史存量**与任何漏网。
- 代价/风险：多一个常驻 watcher 进程（unix，极轻）；fd 继承在 node 中的存活性**须复现先行验证**
  （若不成立，退化为 pid + 启动时间双校验）；Windows Job Object 使硬杀路径连坐整树。
- 对照约束：§2.1 不碰 dsh ✅；§2.2 watcher 只杀白名单 pid ✅；§2.3 硬杀路径补齐 ✅；
  §2.4 单向、壳不动 ✅；§2.5 unix 零依赖、Windows 裸 FFI ✅；§2.6 落在 `child_cmd` ✅；§2.7 可测 ✅

### 方案 B：整进程组 / Job Object 连坐（= ADR-0014 方案 D 原样） —— ❌ 否决

- 思路：`setsid`/`process_group(0)` + `kill(-pgid)`；Windows Job Object 连坐整树。
- 否决理由：**直接违反 §2.2**（ADR-0014 已记载的理由）——unix 侧会连带杀死用户经 dsh 起的
  长驻后台任务（如工作台里跑的 dev server），属语义变更。本 ADR 的方案 A 正是为绕开这条
  而设计的：**守护作用域收窄到「壳生的进程」，不扩到组**。

### 方案 C：`NODE_OPTIONS=--require <guard>` 注入子进程自退 —— ❌ 否决

- 思路：壳随附一个 JS guard，经 `NODE_OPTIONS` 注入 dsh，由 guard 监听生命线并自杀。
- 否决理由：`--require` 会注入**整棵 node 树**——包括用户从工作台里起的**任何** node 进程
  （这正是 dsh 的合法用法，与 §2.2 同一类风险）。guard 一旦有缺陷就砸掉用户项目脚本，
  **爆炸半径不可接受**；且它把壳的运行时资产耦合进用户的进程空间。

### 方案 D：壳去操作锁（删 `session.lock` / 加超时 / 主动"解锁"） —— ❌ 否决

- 思路：会话打不开时，壳删掉锁文件或提供"强制解锁"。
- 否决理由：**擅自改写 dsh 的数据协议**（违反 §2.1）。且 dsh 租约文档明确警告：POSIX 上删掉
  **活会话**的锁文件 = **直接丧失互斥**（"Removing a live session's lock file therefore forfeits
  exclusion on POSIX"），后果是**日志撕裂**。"删了就好使"极具诱惑力，故必须显式写入否决档。

### 方案 E：`dsh` 崩溃即退出壳（或看门狗双向：崩了就重启） —— ❌ 否决

- 思路：把 dsh 当被监管服务，崩了就拉起；连续失败就整体退出让用户重开。
- 否决理由：**直接违反 §2.4**——用户要的恰是"dsh 崩了壳还在，能让我去禁用那个插件"。
  双向看门狗还会与用户的排障动作打架（用户正要去禁用插件，它却在旁边疯狂重启 dsh）。

### 方案 F：只做启动期清扫（不加守卫） —— ❌ 否决为唯一方案（保留为兜底层）

- 思路：每次壳启动扫一遍孤儿并收口。
- 否决理由：**够不上"彻底"**——逃逸依然发生，且伤害持续到**下一次壳启动**为止；用户在一次
  会话内就已被锁死。清扫是必需的**兜底**，但不能是唯一防线。

## 4. 最终决策

采纳**方案 A**：把子进程生命周期的兜底从"父进程临死前跑代码"改为**内核/旁观者保证**——
unix 侧旁挂一个**单向生命线 watcher**（作用域 = 壳生的那个 pid，非进程组），
Windows 侧用 **Job Object**（`KILL_ON_JOB_CLOSE`，裸 FFI 不引依赖）；
两条防线之外再加**启动期基于内核锁的清扫**回收存量与漏网；
守护统一落在 `child_cmd` 这一唯一 spawn seam 上，从而覆盖全部 spawn 面。
**明确不做**：不改 dsh、不碰会话锁、不连坐进程组、不让看门狗反向影响壳的存活与重启策略。

## 5. 后果与后续行动项

### 正面后果

- 硬杀（`SIGKILL` / 强制退出 / 崩溃）不再产生孤儿 → 会话锁不再被无关进程占死，
  「删会话」这一有损自救手段退出历史；
- 用户 §1.4 的恢复流程（崩溃 → 控制中心禁用插件 → 重载 profile）在机理上成立，
  不再受"壳必须活着"这一隐含前提的破坏；
- AGENTS §6「1:1 生命周期」首次获得**机器可验证**的兜底，而非仅靠自觉；
- 覆盖到分钟级 `pnpm add -g` 引导——壳在下载中被强杀不再锁死 pnpm store。

### 负面后果 / 新增债务

- **平台语义不对称**（须显式接受）：unix 硬杀只连坐壳生的进程，Windows Job Object 连坐整树。
  但两边都只是**让硬杀与各自的正常停止路径对齐**（unix 今天只杀直接子 pid；Windows 今天
  `taskkill /T` 已是整树），**未引入新语义**；
- 多一个常驻 watcher 进程（unix）；
- Windows 需裸 FFI（`CreateJobObjectW` / `SetInformationJobObject` / `AssignProcessToJobObject`），
  可测性弱于纯函数，须靠实机清单兜底；
- Job Object 在"壳自身已被更外层 job 收编"（如某些 CI/终端）时可能赋值失败，须保留 `taskkill` 回退；
- **孙进程缺口（诚实登记）**：守卫作用域收窄到"壳生的那个 pid"后，**CLI 转发路径**的孙进程
  （`run_dsh_forward` → dsh → pnpm）不在守卫内，硬杀时可能残留并占住 pnpm store。
  该路径的孙进程是 pnpm/node（**不含用户任务**），故理论上可对该角色单独放宽到进程组——
  但需实施期实测确认 `dsh plugin install` 不会拉起用户长驻任务后才可放宽。
  **本次按"先保会话锁不发生"的最小口径实施**，该缺口随刀 5 一并实测裁定。

## 7. 实施前置实测（刀 0，2026-09-10 完成）

契约 §2.1 把「node 是否全程保留继承来的 fd」列为**实施前置**，两条互为因果的
行为实测结果如下（macOS 实机，node = 引擎 `v24.18.0`）：

| 实测项 | 方法与结果 | 对设计的影响 |
|:---|:---|:---|
| ① node 是否保留继承 fd | 父 `flock` 后以 `pass_fds` 传入 fd → `lsof -p <node>` 显示 `3u REG … proc2.lock`（**保留**） | ✅ 登记锁判据成立，**无需**退化为 pid + 启动时间双校验 |
| ② 该锁是否随**父** SIGKILL 存续 | `kill -9 <父>` → 子仍活，`flock(LOCK_EX\|LOCK_NB)` 仍报 **LOCKED** | ✅ 清扫判据的前提成立（孤儿持锁可被探测） |
| ③ 锁是否随**子**死亡释放 | `kill -9 <子>` → 再探测报 **UNLOCKED** | ✅ 收口后锁自动归还，无需触碰锁文件 |
| ④ 继承 fd 是否流入**孙**进程 | node 内 `spawnSync('sleep')` → 孙进程 `lsof` **无**该 fd | ✅ **登记锁与「壳的直接子进程」1:1 对应**，不会因孙进程存活而误判为孤儿 |

②③ 合起来正是本次事故的微观复现：**父死子活 → 锁被占据到子进程退出为止**。
④ 是额外收获，它把 §5「孙进程缺口」限定在**收口范围**上，而**不污染孤儿判定**——
即清扫不会因为"孙进程还活着"而误杀或漏杀。

> 结论：方案 A 的登记锁判据按**原设计**实施（不启用降级路径）。
> 实测脚本为一次性探针（未入库；结论已固化进 §5 测试闸门 2/3 与契约 §2.1）。

### 7.1 实施期推翻的一个实现细节（生命线通道形态）

方案 A 原文写的是"unix 用 `/bin/sh` 三行实现"。**首版实现（`pre_exec` 里
`dup2` 到固定 fd 3 + 脚本 `read _ <&3`）在实机上把正常运行的子进程杀掉了**：
`read` 没有阻塞而是立即失败，脚本据此误判"壳已死"→ 给子进程发 `SIGTERM`。
症状 = 真 dsh 一启动就吃 SIGTERM（signal 15），日志空白。

- **机理**：固定 fd 号依赖"目标号在子进程里恰好空闲且不会被随后关闭"，而这在
  std / 运行时的 fd 管理下不成立（实测：fd 3 在 `exec` 前被关掉）。
- **修法**：改为 **`Stdio` 通道**——生命线读端经 `Command::stdin()` 交给 watcher，
  `dup2` / `CLOEXEC` 由 std 保证，不依赖任何魔数 fd 号。
- **同时把失败方向改成安全**：脚本用 `cat >/dev/null || exit 0` 取代 `read`——
  `cat` 在 EOF 返回 0（该收口）、在**读错误**返回非 0（fd 异常 → **放弃收口**）。
  即"读不到生命线时宁可不收口，也绝不误杀"，收口另有启动期清扫兜底。
- **测试教训（更重要）**：首版验收测试**假绿**——它只断言"父被 `SIGKILL` 后子进程
  消失"，而"watcher 一开始就误杀"同样满足该断言。现已在断言前加**观察窗**
  （壳存活 ≥1.5s 期间子进程必须仍在），把"收口"与"误杀"区分开。

> 该细节已同步进契约 §2.2 与 §5 闸门；`watcher_script_contract` 测试显式禁止
> 回到固定 fd 号写法。

---

## 8. 复审条件
- dsh 上游为会话写租约引入**过期 / 抢占 / 可观持有者**语义（本 ADR 的"锁无解"前提消失）；
- dsh 上游自带父死自退（则壳侧 watcher 降级为冗余，可撤回）；
- 出现「用户经 dsh 起的长驻后台任务被误杀」的反馈（说明作用域收窄被破坏，§2.2 失守）；
- Windows Job Object 赋值在真实用户环境失败（裸 FFI 路线复审，改回 `taskkill` + pid 清扫）；
- 清扫层连续命中（说明守卫层有漏，须回到 §3 重新评估方案 B 的作用域设计）。
